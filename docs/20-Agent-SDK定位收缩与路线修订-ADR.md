## 结论摘要

1. **到头的不是 SDK，而是“按功能清单往上加”这条路。** 2026 年主流 Java Agent 框架相继正式发布（GA）。本 SDK 的通用能力已经不构成差异，包括 ReAct 循环、Schema 校验、预算控制、记忆和注解工具。
2. **还有空位、且本 SDK 已有雏形的，是运行治理。** 这里指一次运行可以挂起、需要审批、能被中止、事后可追溯。它对应企业当前最大的卡点：权限与合规。它也对应 2026-05-08 发布的《智能体规范应用与创新发展实施意见》中的要求。
3. **建议做四件事：**
   - **收缩定位**：把 SDK 收缩为“可嵌入 Spring 业务系统的智能体治理运行时”。
   - **管道用标准件**：改用 Spring AI、官方 MCP Java SDK 和 SKILL.md。
   - **用真实场景拿证据**：做坐席辅助只读试点，并用 Spring AI 实现一个对照组。
   - **按规则定去留**：第 6 周按事先定好的规则决定继续还是止损。

### 1.3 文档可信度

- **夸大**
  - README：“企业级高可靠”“毫秒级冷启动”“内置精确 Token 预算估算……彻底阻断 Token 爆炸”。
  - CHANGELOG 1.0.0：“首个企业级生产商用就绪基线”“生产场景验证矩阵（100% 通过）”，以及把 MCP 描述为“工业级”“高可用客户端”。
- **事实错误**：CHANGELOG 写外溢阈值“>2KB”，代码默认是 16384 字节。
- **低估**：使用场景手册和 CHANGELOG 说内置适配器“不是逐 Token 增量输出”，但代码已支持 SSE 增量回调。
- **过时**：评测工程 README 的“当前状态”仍说缺 6 项。其中场景注入、多轮 resume、真实模型入口其实已经实现。
- **可信**：`docs/使用场景手册.md` 中关于边界和并发的说明。

逐条位置见路线图附录 B。

### 1.4 值得保留的资产

1. **显式状态机。** 共 7 种状态，其中有两个挂起点：WAITING_INPUT（等用户补充信息）和 WAITING_APPROVAL（等审批）。它还支持目标修订和完成检查。这套挂起点和三样东西是同构的（推断）：
   - MCP 新版的“多轮输入请求”；
   - A2A 的任务生命周期；
   - 持久执行需要的挂起点。
2. **模型输出防护。** 能识别截断、重复 callId、参数超限和无进展循环。大结果会外溢到工作区。
3. **评测协议。** 证据编号（Evidence ID）、轨迹断言、确定性回放。这部分在外部评测工程里。
4. **依赖克制。** `agent-core` 只依赖 Jackson 和 JSON Schema 校验器。surefire 合计 380 个测试（2026-10-18）。

## 2. 推演

### 2.1 为什么会觉得“到顶了”

| 层次 | 原因 | 说明 |
| --- | --- | --- |
| 直接原因 | 功能清单驱动 | 清单做完后没有新的外部输入，方向感就没了 |
| 结构原因 | 没有真实使用者和真实数据 | 下游全是自建演示，任何功能都没被真正“用”过，也就没有暴露过问题。ADR-018 把下一步押在 Track B 上，而 IT 支持场景没有数据来源，路线因此停住 |
| 环境原因 | 通用能力被市场抹平 | 见 §2.2。继续加通用功能，不会成为别人选择本 SDK 的理由 |

**结论**：问题不在于“下一个功能做什么”，而在于“为谁、解决什么问题、用什么证明”。

### 2.2 市场：哪些被抹平，哪些还空着

**被抹平的部分（据调研，标注“已核实”的除外）**

| 框架 | GA 时间 | 与本 SDK 重叠的能力 |
| --- | --- | --- |
| Spring AI 2.0 | 2026-06-12（2.0.1 发布于 2026-08-21） | 工具调用循环；调用上限：单工具 40 次、总计 150 次（已核实）；工具检索；结构化输出校验；MCP |
| AgentScope Java 2.0（阿里） | 2026-07-10 | 三态权限引擎做审批、状态版本化加乐观并发、沙箱、A2A/MCP/AG-UI、Boot starter。**与本 SDK 正面重叠，且领先** |
| ADK Java 1.0（Google） | 2026-03-30 | ToolConfirmation 审批 |
| Koog 1.0（JetBrains） | 2026-05-21 | 检查点、OTel |
| Embabel 1.0 | 2026-07-20 | 规划；审批持久化刚起步 |

**还空着的部分**

- **审批闸门（已核实）。** Spring AI 2.0.1 核心不内置审批闸门。官方文档把“审批闸门”列为需要宿主自己接管工具循环的场景。本 SDK 的 Runner 正是这样一个外层循环。
- **持久执行（据调研）。** Java 侧还不成熟：
  - Temporal 的 Spring AI 集成仍是 Public Preview；
  - Dapr Agents 只有 Python 版；
  - 各框架的检查点格式互不兼容。
- **企业卡在治理和价值证明上（据调研）：**
  - IDC（2026-05）：62% 的企业把“数据权限与安全合规”列为跨系统执行的首要障碍；
  - IDC 另一份调研：52% 的企业认为 ROI 难以量化；
  - Gartner（2026-10-19）：只有 13% 的 CIO 认为已获得显著价值；
  - Gartner 预测：到 2027 年底，超过 40% 的 agentic 项目会因成本高、价值不清和风控不足而被取消。

**窗口在收窄（推断）。** 依据如下：
- AgentScope 已经有权限引擎和状态版本化。
- OpenAI Agents SDK 已支持持久会话恢复（据调研）。
- Embabel 正在做审批持久化（据调研）。

所以差异窗口要按季度算，不是按年算。

### 2.3 国内监管：需求已经写进文件

2026-05-08 发布的《智能体规范应用与创新发展实施意见》（已核实原文）提出了以下要求：
- “确保用户对智能体自主决策享有知情权和最终决策权，智能体执行操作不得超出用户授权范围”；
- “发展规则内嵌、行为围栏等技术”；
- 建立智能体行为“可验证、可追溯”的机制；
- 对敏感领域和重点行业实行“备案、检测、问题产品召回”。

对照本 SDK：

| 要求 | 已有 | 缺口 |
| --- | --- | --- |
| 不超出用户授权范围 | 工具白名单；`RiskLevel` 只有两档 | 没有可信上下文（租户、用户主体、权限范围），也没有策略 SPI |
| 用户的最终决策权 | WAITING_APPROVAL、reject、reviseGoal | 审批没有绑定审批人、参数哈希和策略版本；进程重启后审批丢失 |
| 拦截阻断 | cancel、STOPPED、预算上限 | — |
| 可验证、可追溯 | JSONL 事件、评测回放 | 没有只追加的审计日志；事件没有版本号和 traceId |

### 2.4 协议：管道不该自己追

- **MCP（已核实）。** 2026-07-28 版已经发布，核心变化是无状态化，去掉了协议层会话。本 SDK 的客户端还停在 2024-11-05、只支持 stdio（`McpProtocolConstants.java:11`）。中间落后 4 个版本，也接不上远程 MCP 服务。
- **官方 MCP Java SDK（据调研）。** 2.x 已 GA，支持 2025-11-25 版；2.2.0-M1 预览版支持 2026-07-28 版。
- **其他标准（据调研）：**
  - A2A v1.0 已 GA，由 Linux 基金会托管，有官方 a2a-java；
  - AG-UI 1.0 只有单一来源，可信度低；
  - SKILL.md 已经成为事实标准；
  - OTel GenAI 语义约定仍处于 Development 状态。
- **推断。** 一个人追协议一定会落后。协议层应该交给官方 SDK，自己只保留一层薄适配，负责把协议事件映射到状态机。

### 2.5 自身约束

- **人力。** 一个维护者加一个编码 AI。没有对外支持能力，也没有生态，对外推广通用 SDK 不现实（推断）。
- **现实用户只有两类：**
  - 维护者所在业务的产品线；
  - 已有 Spring 业务系统、需要在内部安全嵌入 Agent 的 Java 团队。
- **离得最近的真实场景：酒店/文旅呼叫中心的坐席辅助。** 它和 `hotel-concierge-agent` 样例属于同一领域。选它的理由：
  - 天然只读；
  - 天然由人做最终决策；
  - 指标可以量化：采纳率、处理时长、小结修改率；
  - 工具形态和现有 IT 支持试点一一对应，评测工程可以直接复用。

  能不能用，取决于业务负责人和数据负责人是否授权。

### 2.6 推论

1. **投入集中在“治理”这一层。** 这一层市场上还有空位、有监管在推，本 SDK 也已经有雏形。
2. **管道用标准件。** 模型调用、MCP、Skills、遥测都交给标准件，减少自己要维护的范围。
3. **用真实场景和对照组证明方向。** 方向对不对，要靠真实场景加对照组来证明，不能靠测试数量或演示。
4. **事先定好止损条件。** 如果拿不到真实使用者，或者和直接用 Spring AI 相比看不出差异，就停止扩展自研循环。

## 3. 选项与权衡

| 选项 | 内容 | 优点 | 致命问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. 继续做通用 SDK | 对标 Spring AI、AgentScope、ADK，补齐功能 | 惯性最小 | 一个人对抗大厂团队，只能长期追赶，做不出差异 | 拒绝 |
| B. 收缩为治理运行时 | 管道交给标准件；自研授权、审批、审计、中止、挂起恢复和评测回放 | 正好对准还空着的位置；维护范围变小；契合国内监管要求 | 窗口在收窄；AgentScope 已覆盖一部分 | **建议（主线）** |
| C. 做业务产品的引擎 | SDK 退到幕后，支撑一个垂直应用（坐席辅助） | 有真实用户和业务指标 | 主要工作量在应用层 | **建议（作为 B 的验证载体）** |
| D. 冻结 | 业务直接用 AgentScope 或 Spring AI；保留评测工程和治理经验 | 成本最低 | 放弃已有积累 | **止损预案** |
| E. 平台化 | 托管运行时、多 Agent、沙箱、UI | 叙事宏大 | 这是厂商的主战场，一个人做不了 | 拒绝 |

**什么情况下应该改选**

| 如果评估发现…… | 应改选 |
| --- | --- |
| SDK 主要用于学习和技术积累，不需要支撑业务 | D |
| 业务方明确不会授权任何真实数据，也没有可以自用的场景 | D |
| 团队愿意直接用 AgentScope Java，且它的权限引擎能满足审批需求 | D，把治理经验沉淀为 AgentScope 的扩展 |
| 未来 1–2 个季度有多人投入 | 仍选 B，可以把 3′、4′ 提前 |

## 4. 决策（提议）

1. **收缩定位。** SDK 从“通用单 Agent 执行引擎”收缩为“可嵌入 Spring 业务系统的智能体治理运行时”。自研范围只保留：授权范围、审批（可持久、可审计）、中止、挂起与恢复、评测回放契约。此条拟修订 ADR-018 §2 第 1 条。
2. **管道用标准件。** MCP 改用官方 MCP Java SDK；模型适配改为面向 Spring AI `ChatModel`；Skills 采用 SKILL.md；不再自研协议实现。此条拟修订 ADR-018 §2 第 6 条。
3. **更换试点场景。**
   - 首个真实试点改为“酒店/文旅呼叫中心坐席辅助（只读）”，由业务负责人和数据负责人授权脱敏数据。
   - IT 支持保留为 Track A 冒烟基线。
   - 授权未落地前，用“研发联调排障助手（自用）”兜底产生真实案例。
4. **统一 Track B 口径。**
   - ADR-018 正文写的是“真实只读端口”，以 `docs/19` §2.5 为准，明确包括“经授权的脱敏导出快照 + 只读适配器”。
   - 在线只读端口改为 2′（治理内核阶段）的退出条件。
5. **增加对照基线。**
   - 用同一评测集、同一模型、同一工具，跑一个 Spring AI 最小实现做对照，两者的差异必须能量化。
   - 对照实现放在 `agent-sdk-eval`，不进 SDK 仓库。
6. **提前两项已被证明的需求。**
   - 会话托管：3 个下游都自己写了，提前到 0′。
   - 审批的“挂起点持久化”：从原 Phase 4 提前到 2′。
7. **治理 SPI 与自研循环解耦。** 策略、审批记录、审计的契约，不依赖 `DefaultAgentRunner` 的内部状态。这样一旦需要，它们可以挂到 Spring AI 或 AgentScope 上继续用。
8. **止损。**
   - 第 6 周按规则决定去留（§7.1）。
   - 每季度检查 4 个外部信号（§7.2）。
9. **ADR-018 中继续有效的部分：**
   - 原则：先证据后能力、先信任后自治、先标准后厂商、先单 Agent 后编排；
   - §4 边界与红线；
   - §6 关键设计；
   - §9 明确不做。

## 5. 阶段路线（拟修订 ADR-018 §5）

> 0′–4′ 读作“零撇”到“四撇”，表示修订后的阶段，用来和 ADR-018 的 Phase 0–5 区分。
> 日期按 W1 = 2026-10-26 推算；如果本 ADR 接受得晚，整体顺延。
> 进不进入下一阶段，以阶段门证据为准，不以日期为准。

| 阶段 | 目标 | 计划时间 | 退出条件（摘要） |
| --- | --- | --- | --- |
| 0′ 止血与如实修正 | 处理密钥、文档，以及下游已暴露的缺陷 | W1–W2 | 下游删掉自写的 Runner 管理和估算器后测试仍通过；文档中没有不可验证的表述；没有明文密钥 |
| 1′ 真实证据 | 坐席辅助只读试点，加对照基线 | W2–W6，与 0′ 后半段并行 | 用例至少 30 条，其中真实案例至少 10 条；至少 1 位一线使用者对至少 20 个真实案例逐条盲评；越权工具执行 0 次；两组的对比结果已量化，再由 Gate 1 按 §7.1 决定方向 |
| 2′ 治理内核 | 授权范围、审批绑定、挂起点持久化、审计 | W7–W12 | 安全负向测试全部通过；审计能回答“谁、何时、依据什么、批准了什么参数”；重启后审批能继续；接通 1 个在线只读端口 |
| 3′ 标准件替换 | 官方 MCP SDK、ChatModel 适配、SKILL.md、OTel 开关 | W13–W16，遇春节顺延 | 能与远程 MCP 服务互通；自维护的协议代码减少；兼容测试通过 |
| 4′ 规模化 | 完整检查点、并发、配额、持久执行适配 | 按需 | 由真实试点的需求触发 |

**与 ADR-018 的对照**

| ADR-018 | ADR-020 | 变化 |
| --- | --- | --- |
| Phase 0 试点与评测 | 0′ + 1′ | 拆出“止血”；更换场景；增加对照基线；统一 Track B 口径 |
| Phase 1 信任边界 | 2′ | 并入原 Phase 4 的审批挂起点持久化；在线端口作为退出条件 |
| Phase 2 可运营 | 拆到多个阶段 | 见下方说明 |
| Phase 3 协议与互操作 | 3′ | 收窄为“换标准件”；A2A、AG-UI、多厂商模型适配、并行工具推迟到 4′ 或按需 |
| Phase 4 持久化与规模化 | 4′ | 挂起点持久化已提前；完整检查点按需做，优先评估 Temporal |
| Phase 5 | 不变 | 作为独立产品，不进 core |

原 Phase 2 的内容拆分如下：
- 模型重试边界 → 0′；
- 成本和用量统计 → 1′（进评测报告）；
- 事件 schema v1、失败分类 → 2′；
- OTel → 3′（带版本开关）；
- 评测进 CI → 3′（仓库目前没有 CI）。

各阶段的任务单、验收证据和回滚方式见[演进路线图](21-Agent-SDK演进路线图.md) §3。

## 6. 关键设计决策

### 6.1 定位边界

| 层 | 归属 | 内容 |
| --- | --- | --- |
| 治理内核 | SDK 自研 | 可信上下文、工具策略、审批绑定、挂起点持久化、审计、中止、评测回放契约 |
| 执行循环 | SDK 保留，可替换 | 现有的确定性循环和状态机；不再扩展通用功能 |
| 管道 | 标准件 | 模型调用用 Spring AI `ChatModel`；MCP 用官方 Java SDK；Skills 用 SKILL.md；遥测用 OTel |
| 业务 | 宿主应用 | 工具实现、数据接入、身份来源、审批人的组织关系、界面 |
| 不做 | — | 多 Agent 编排、沙箱、托管运行时、UI、自造协议、评测系统与行业夹具 |

### 6.2 会话托管（0′）

- **背景。** Runner 一次只接一个任务，starter 又默认注册了单例 Bean。结果下游各写了一套会话映射，并出现两类缺陷：会话从不淘汰，以及全应用共享一个单例。
- **决策。** 移除默认的单例 `agentRunner` Bean，在 starter 里提供会话托管组件：
  - 按会话获取 Runner；
  - 闲置会话按时淘汰；
  - 限制会话总数，超出上限时拒绝新会话；
  - 应用关闭时释放所有会话。
- **约束。**
  - 有等待中任务（WAITING_INPUT 或 WAITING_APPROVAL）的会话，在 `waitingTimeout` 到期前不得被闲置淘汰。
  - 2′ 有了持久化之后，等待中的会话可以淘汰，需要时再恢复。
- **新模块四问**（以组件形式落在已有模块中）：
  - 给谁用：3 个下游和后续宿主；
  - 在哪发布：`agent-spring-boot-starter`；
  - 依赖方向：starter → core；
  - 删除条件：Runner 原生支持多任务并发之后。
- **兼容。** 移除单例 Bean 是不兼容变更，CHANGELOG 要写迁移说明；hotel 同步迁移。
- **回滚。** 恢复这个 Bean，改为显式开关、默认关闭。

### 6.3 挂起点持久化（2′）

- **决策。** 只在 WAITING_INPUT 和 WAITING_APPROVAL 两个状态时持久化运行状态。这两个时刻没有进行中的模型调用或工具调用，状态边界清楚。
- **保存内容：**
  - 结构化会话记录，包括助手发出的工具调用和工具结果；
  - 待处理的调用和审批批次；
  - 预算计数；
  - TaskBrief、TaskPlan 和 goalVersion；
  - 工作区引用；
  - 场景、工具、策略的版本；
  - 可信上下文快照；
  - 事件序号。
- **约束：**
  - 现有 `ModelGateway` 的历史重载会把历史压成一段文本（`ModelGateway.java:17`），`ChatMessage` 也只有 USER、ASSISTANT、SYSTEM 三种角色（`ChatMessage.java:9`），都不能用来恢复。需要新增一个“按结构化会话记录恢复模型会话”的契约。不支持恢复的适配器必须明确拒绝，沿用 ADR-018 §6.4。
  - 恢复前要复核版本、权限和审批有效期。
  - 用乐观并发（版本号）防止同一个挂起点被重复恢复。
  - 不做模型调用中途的恢复，也不承诺分布式事务。
- **存储。** SPI 放在 core；JDBC 实现放在新模块 `agent-store-jdbc`。SQL 方言做成可替换的，方便适配信创数据库。
- **新模块四问（`agent-store-jdbc`）：**
  - 给谁用：需要审批跨重启保留的宿主；
  - 在哪发布：作为可选制品，随 SDK 一起发布；
  - 依赖方向：store-jdbc → core，不反向；
  - 删除条件：如果改由持久执行引擎（如 Temporal）承载状态，就废弃。
- **回滚。** 不配置存储时，行为和现在一致：状态在内存里，重启就丢。

### 6.4 治理 SPI 与循环解耦

- 三个契约（`ToolPolicy`、审批记录、`AuditSink`）都不引用 `DefaultAgentRunner` 的内部类型。
- “允许、拒绝、脱敏”这几类策略判定，可以做成工具调用的拦截器。
- “需审批”在外部框架里需要宿主自己接管循环，Spring AI 的文档也是这么要求的。
- 这样做的目的：一旦触发止损、改走 D，治理层仍然可以挂到 Spring AI 或 AgentScope 上复用。

### 6.5 试点场景、Track B 口径与证据等级

- **真实只读来源。** 按 `docs/19` §2.5，以下任一种都算：
  - 只读 API；
  - 只读账号或只读副本；
  - 经授权的导出快照（CSV、JSON、日志包）；
  - 测试环境的只读账号。
- **试点：坐席辅助（只读）。** 候选工具（待业务确认）：
  - 查订单或预订；
  - 查来电和工单记录；
  - 检索政策知识库；
  - 生成带证据引用的建议回复或工单小结，作为产物交给坐席，由坐席决定是否采纳。
- **数据要求。**
  - 业务负责人和数据负责人书面授权；
  - 按最小必要原则脱敏，脱敏规则要有签字人；
  - 快照和评测数据不进 SDK 仓库。
- **证据等级。**

| 等级 | 数据 | 能证明什么 | 能否作为 Gate 1“进入 2′”的依据 |
| --- | --- | --- | --- |
| `smoke-only` | 合成或脱敏样本 | 评测链路和 SDK 行为 | 不能 |
| `real-internal` | 维护者自用的真实数据，如脱敏后的联调日志 | 在真实数据上技术可行 | 不能，只能用来申请延长 1′ 一次 |
| `real-pilot` | 业务授权的真实数据，加一线使用者的评价 | 在业务场景中可用 | 能 |

### 6.6 对照基线

- **对照方式。** 用同一数据集、同一模型和参数、同一套工具适配器，指令意图也尽量一致。
- **对照实现。** Spring AI `ChatClient` 加工具，用它默认的工具循环，不加额外护栏。
- **比较指标：**
  - 安全类：越权工具拦截、敏感信息泄露；
  - 质量类：证据落地率、澄清正确率、任务成功率；
  - 业务类：坐席采纳率；
  - 成本类：单案例成本、P95 时延。
- **位置。** 放在 `agent-sdk-eval`，不进 SDK 仓库。
- **态度。** 对照组是为了回答“为什么不直接用 Spring AI 做”。如果差异不显著，就如实接受，按 §7.1 处理。

### 6.7 文档治理

- **权威文档：**
  - README（0′ 修订后）；
  - `使用手册.md`；
  - CHANGELOG（含勘误）；
  - `docs/使用场景手册.md`；
  - ADR-018（被本文修订的部分除外）；
  - 本文；
  - `docs/19`；
  - 演进路线图。
- **历史文档。** `docs/00`~`docs/17`、`docs/建议文档.md`、`docs/演进建议.md` 移入 `docs/archive/`，并加上说明横幅。
- **写作规则：**
  - 描述能力时，必须能指到源码或测试；
  - “已有”“计划”“应用负责”三类分开写；
  - 市场信息要标注日期和来源等级；
  - 不写“生产就绪”“金融级”“彻底”“精确”这类无法证明的词。

### 7.1 第 6 周去留判断（Gate 1，计划 2026-12-04）

| 结果 | 决定 |
| --- | --- |

## 8. 技术雷达（拟修订 ADR-018 §7）

| 档位 | 技术 | 性质 |
| --- | --- | --- |
| **Adopt** | 自研部分：确定性循环与状态机、JSON Schema 校验、HITL 审批、工作区外溢。标准件：Spring AI `ChatModel`；官方 MCP Java SDK 2.x（对应 MCP 2025-11-25）；SKILL.md；W3C traceparent | 自研 / 稳定标准 |
| **Trial** | MCP 2026-07-28（规范已发布，Java SDK 2.2 还在预览）；OTel GenAI 语义约定（仍处于 Development，需要版本开关）；A2A v1.0（按需）；OPA/Cedar 策略适配 | 标准，但处于实验阶段或按需采用 |
| **Assess** | AG-UI（版本信息可信度低）；Temporal Spring AI 集成（预览）；容器或 microVM 沙箱；多 Agent Handoffs | 实验 |
| **Hold** | 自研 MCP 协议实现；没有正当理由的自研模型 HTTP 客户端；把 Workflow/Swarm 放进 core；用 Redis 作为审批的唯一可信来源；对写操作做隐藏重试；自造前端或工具协议；没有证据的“生产就绪/金融级”承诺 | — |
| **只通过 SPI 对接，不绑定** | OpenAI Agents API、Claude Managed Agents、AWS AgentCore、Entra Agent ID、Okta XAA、国内云厂商的智能体平台 | 厂商专有 |

与 ADR-018 相比的变化：
- OTel GenAI 从 Adopt 降到 Trial，因为语义约定还没稳定。
- 自研 MCP 协议实现列入 Hold。

## 9. 影响与代价

- **正面：**
  - 投入集中在能形成差异的层；
  - 自己维护的协议代码减少；
  - 去留有真实证据支撑。
- **代价：**
  - 放弃自研 MCP 协议层（编解码、客户端、传输），这是沉没成本。`agent-mcp-adapter` 的主代码合计约 2000 行，其中工具适配层和 Skills 会保留，并不全部删除；
  - 移除默认单例 Runner Bean、拆分被复用的 `RUN_STARTED` 事件，属于不兼容变更；
  - 0′ 以修正为主，短期内“功能感”弱；
  - 试点依赖业务方授权，可能要等。
- **兼容策略：**
  - 沿用 ADR-018 §6.7；
  - 不兼容变更在 CHANGELOG 中给出迁移步骤；
  - 下游工程纳入 git，作为消费者兼容测试。

## 11. 回滚

- 本 ADR 主要改变的是投入方向和阶段顺序。代码改动小，且按任务分别提交，可以逐项回退。
- 替换 MCP 期间保留旧客户端，新客户端通过互通测试后才删除。
- 如果 Gate 1 证明业务价值来自通用能力而不是治理层，就写新 ADR，恢复“通用 SDK”定位或改走 D。
