# 总实施指南：从方案到可用 Agent

版本：v0.1 · 五阶段主体方案实施入口  
范围：汇总已有设计，不新增必做阶段，不编写或修改项目代码。

## 1. 剩余还有哪些阶段

**原定的五个主体阶段已经全部给出，没有尚未交付的必做主体阶段。**

这个目录已经包含总体说明、五阶段详细设计和各阶段实验。你可以直接按方案开始实现，不需要等另一套“第六到第一百阶段”。

但要区分：

- 方案齐备：已经描述要实现的机制、边界和验收。
- 实现完成：需要你依据实际工程逐项实现并运行测试。
- 可以交付：需要验证所选模型、工具、部署环境和真实任务。
- 完整企业产品：还取决于身份授权、数据合规、真实业务连接、容量与运维要求，不因五阶段文档齐备而自动成立。

本指南是阅读和实施索引，不替代各阶段详细契约；不复制所有规格，避免形成两份互相漂移的“标准答案”。本轮没有重新检查你的项目代码，因此不推断你已经实现到哪一步。

推荐路线：**一 → 二 → 三 → 四（可选）→ 五。**

想先做一个可靠的单 Agent，可走 **一 → 二 → 三 → 五**。第五阶段中的父子树恢复测试记为不适用，不能假称通过，也不用为了验收强行增加多个 Agent。

第三阶段内，关键词检索先于向量/混合实验，确认型偏好只存明确允许的内容。理解某项能力不等于所有任务都默认启用它；第五阶段同样不要求先接生产写接口。

## 3. 开工前确定应用方向与执行主体所需事项

不需要先确定登录、组织、租户和管理后台。应用方向可以先选，具体能力仍分阶段实现：

| 事项 | 建议做法 |
|---|---|
| 应用方向 | [14-场景选型](14-应用场景选型：为什么先做技术支持Agent.md) 保留候选比较；目前已沿单产品技术支持的调查与回复草稿方向展开设计，旧样例仍作核心回归，真实业务价值仍待验证 |
| 场景契约 | 阅读 [15-核心工作流](15-技术支持Agent：核心工作流与决策边界.md) 和 [16-工具与验收](16-技术支持Agent：工具契约、调用样例与验收.md)，先做虚构状态夹具及独立工具测试，再接同一 Runner |
| 工程 | 延续你已有的 Java 工程；以当前 pom 和实现为事实，不因早期建议擅自降级或重建 |
| JDK/依赖 | 主线使用 JDK 21，确认 IDE、终端和 Maven 实际使用的版本一致；模型依赖在接入时锁定兼容版本 |
| 模型 | 一个已经可访问、支持原生 Tool Calling 的模型；未选好时可先做脚本模型测试，但它不能替代真实模型验收 |
| 文件 | 独立虚构 input、受控 output/traces，第二阶段再加 work；不拿真实敏感资料做第一次实验 |
| 凭据 | 环境变量或受控本地配置，不进 Prompt、报告、日志和版本库 |
| 执行所有权 | 明确关闭框架隐藏的工具循环，由自己的 Runner 执行 |
| 开发单位 | 一次一个可验证的小步，先回归再进入下一步；已有实现通过验收就保留，不按文档类名机械重写 |

文档里的类名、包名和模型库示例是职责建议。必须遵守的是行为契约与边界，不是要求每个概念都创建接口、模块或微服务。

## 4. 第一阶段实施清单：先把循环打透

依次完成：

1. 让应用装配一个模型适配器和受限工具目录；先证明只调用模型不会暗中执行工具。
2. 用一个计数/只读测试工具跑通“模型请求工具 → 程序执行 → 原 callId 回填 → 模型继续”。
3. 支持同一响应多个工具调用、参数错误、取消、超时和明确停止；工具执行保持串行。
4. 接入 listWorkspaceFiles、inspectDataset、readReference、analyzeDataset、writeReport 五个样例工具。
5. 接入 requestClarification；用户答复继续同一 Run，不清空预算。
6. 加报告完成检查，检查实际引用而不是只看文件是否存在。
7. 运行 04 中的核心/适配集成、计算文件测试和真实模型实验，保存失败结果。

**进入第二阶段的关口：**能解释一次任务中每个工具为什么被调用，真实结果怎样回到模型；标准数字正确、文件边界有效、缺资料可以提问、任务可以停止。

关键手工核验值：线上净额 1100→700，差 -400，-36.36%；全渠道 2500→2400，差 -100，-4.00%。结论只支持两个指定两日窗口，不支持整月趋势或未经验证的广告原因。

不要用预填这些数字的假工具替代计算，也不要在 Loop 没跑稳前增加 RAG 或 Supervisor。

## 5. 第二阶段实施清单：长任务不靠无限历史

按依赖推进：

1. 建立明确 TaskBrief、goalVersion、deliverableKey，区分笔记和交付物。
2. 保存有界完整工具结果，向模型返回引用；通过 readWorkItem 回读，而不是重做原工具。
3. 加 PlanState/updatePlan，计划可调整但不能改变用户目标或权限。
4. 将完整执行记录与本轮模型视图区分，先做确定性整理，再做受预算约束的摘要。
5. 实现用户确认的有限目标修订，处理在途调用、旧问题与旧产物。
6. 加交付检查、具体缺项反馈和有限修正，最后运行 06 的长任务及对照实验。

**进入第三阶段的关口：**资料较长、说明冲突或用户把范围改为线上时，系统仍保留正确目标和证据；不会拿旧全渠道报告换标题，也不会把摘要说的“用户同意”变成权限。

测试压缩要验证实际提交给供应商的消息，而不是只看本地 List 变短。预算和原生消息组配对不能因压缩失效。

## 6. 第三阶段实施清单：同一个引擎换能力

1. 将资料分析方法整理为受控 Skill，保留原功能与检查器。
2. 做知识导入快照、关键词搜索和原文回读，得到可以追溯的知识证据。
3. 配置产品调研能力包及其完成检查，证明调研不被“必须有销售计算”绑死。
4. 用同一问题集比较关键词、向量和混合检索；有收益再选择默认策略。
5. 接入一个已批准的本地只读 MCP Server，验证真正的协议协商、发现、调用和错误处理。
6. 加少量用户确认的展示偏好，验证跨任务复用、当前要求优先和删除不复活。
7. 完成 08 的双场景及边界回归。

**进入后续阶段的关口：**同一 Runner 能执行资料分析和产品调研，差异主要落在能力配置、工具、资料和检查器；原文、业务观察、偏好、方法和模型笔记不混为一谈。

本阶段不自动安装第三方脚本，不做插件市场，也不因为 MCP Server 声称工具只读就自动批准。

## 7. 第四阶段实施清单：先证明值得拆分

这一阶段可以跳过，也可以作为学习分支保留。

1. 固定一个主角色和少量子角色，先串行完成一个子任务的委派和结果交接。
2. 子证据通过受控映射进入父 Run；不直接把子总结当事实，不解除跨 Run 访问检查。
3. 实现全树预算、子额度预留、最多一层委派和有限尝试。
4. 再开启最多两个独立子任务并行，检查各自模型会话、工作区和 callId 不串线。
5. 补统一提问、取消、修订屏障和部分失败处理。
6. 按 10 对照单 Agent、串行委派和并行委派，记录正确性、延迟与全部成本。

**进入第五阶段的关口：**能说明哪些任务因隔离/并行受益、哪些反而增加成本；父子都不能通过委派扩权、刷新预算或绕过根完成检查。

没有收益可以正式保持单 Agent。A2A 不是本阶段必需；固定工具并行也不等于实现了自主子 Agent。

## 8. 第五阶段实施清单：恢复前先确认事实

1. 增加本地事务状态、操作账本、配置清单和数据目录独占控制。
2. 持久保存模型原生响应与 Tool 结果，已提交的结果只重建消息、不再执行原工具。
3. 为报告/工作项建立文件提交清单，处理文件与数据库不能原子提交的窗口。
4. 实现显式恢复、PAUSED、待答问题与命令去重，不自动启动全部旧任务。
5. 持久化取消和目标修订屏障，保留预算、修正数和主动时间计量。
6. 用虚构回执服务学习动作确认、未知结果核实；不接真实付款或生产写接口练手。
7. 如启用了多 Agent，再实现原父子身份、预留额度、子检查点和汇聚的恢复。
8. 完成版本兼容、备份、容量和打包说明，运行 12 的故障实验和真实模型回归。

**主体交付关口：**正常任务能够完成，非终态中断任务能明确恢复或拒绝恢复；已发生动作不盲目重复，UNKNOWN 不冒充失败或成功，终态任务不原地复活。

特别注意三件事：

- 取消后可以只读核实旧动作，不能通过重发写调用“查询结果”。
- 确认到期不能把已经发出的操作改成未执行。
- 旧备份如果落后于原任务的后来执行/取消/修订，只可只读检查，不能直接续跑来回退事实和预算。

## 9. 不同阶段的约束怎样衔接

后阶段只覆盖明确声明演进的部分，不是“编号更大就推翻前面所有规则”。

| 主题 | 演进顺序 |
|---|---|
| 完成检查 | 第一阶段一个最新报告 → 第二阶段按当前goalVersion＋deliverableKey逐项检查 → 第三阶段按能力包判断所需证据 |
| 上下文 | 第一阶段不压缩 → 第二阶段记录与视图分离；原生消息配对和稳定规则始终保留 |
| 引用范围 | 第一阶段本Run资料 → 第三阶段知识快照进入本Run引用 → 第四阶段父子间受控重新绑定，不接受任意跨Run引用 |
| 预算 | 第一阶段16生成/30工具/300秒 → 第二、三阶段40/80/900 → 第四阶段全树共享同一总额 → 第五阶段跨重启保持且计入恢复尝试 |
| 状态恢复 | 前四阶段不承诺崩溃恢复 → 第五阶段只对符合条件的非终态任务显式恢复；终态仍不resume |
| 持久信息 | 知识/偏好持久化不等于任务恢复；第五阶段需要操作账本、消息、控制状态和内容清单共同成立 |
| 多Agent | 每实例仍只有一套Runner控制循环，根协调器不另起隐藏模型循环 |

这些是防止照不同阶段示例混写的提示，细节以对应正文为准。未被明确替代的安全、来源、取消与预算约束继续有效。

## 10. 怎么判断真的完成，而不是“代码写了很多”

每个小步只保留四类可查证结果：

- 当前实现范围与版本：这一小步增加了什么，不支持什么。
- 确定性测试：预期调用、状态、消息、数字和文件结果是否成立。
- 适配集成：被测模型/协议/存储路径是否真实经过，不能把它mock掉再声称兼容。
- 真实模型记录：成功、失败、依据、成本和停止原因全部保留。

各阶段的“进入下一阶段关口”是导航，不替代配套文件的完整验收矩阵。未实现或未测试写清楚；不适用项说明原因；不能把这份方案本身当成测试通过记录。

真实模型可每类先跑 3 次形成入门回归，但它不证明生产可靠性。尤其是越界执行、错误数字、伪造成功、重复副作用，不能用平均成功率掩盖。

如果你已经完成了一部分，先按对应验收定位缺口，不必从头重写。没有业务需求时，不先为了未来复杂场景创建大量接口、状态表或微服务。

## 11. 交给其他 AI 辅助实现时怎样切任务

不要一次要求“按全部文档生成企业级 Agent”。一次交给它一个小步，明确现有实现和不得扩张的边界。

可以使用以下任务说明结构：

> 本次只实现第X阶段的某一个小步。先阅读该阶段设计与配套验收，再检查当前工程；保留已有可用实现和依赖选择。只修改本小步需要的文件，不提前加入下一阶段能力或登录组织模块。实现指定正常路径及边界测试，说明实际运行了哪些验证、哪些尚未验证。不得用假模型/假工具冒充真实集成，也不得把未实现功能报告为已完成。

每次给出：目标、相关文档、当前已有能力、需要通过的验收项、禁止范围。工具函数先独立验证，循环用脚本模型验证，最后才让真实模型暴露策略问题。

如果实际工程与文档建议不同，先判断行为是否等价，不要求为了类名一致而重构。发现真正契约冲突再同步修订设计和测试，不一边写代码一边默默放宽边界。

## 12. 主体之后可能还要做什么

下面不是尚未交付的必做阶段，而是触发条件明确后才选择的后续工作。当前没有真实部署和业务需求，不能假装一份通用模板已经替所有企业决定了这些设计。

| 触发条件 | 后续工作 | 从主体哪里接入 |
|---|---|---|
| 选定真实业务场景 | 新工具、资料、能力包、真实任务评测；先只读再逐项评估写操作 | ToolCatalog、Skill、知识与CompletionCheck |
| 使用真实敏感资料或外部模型 | 明确可外发字段、访问授权、数据保留和删除、模型服务约束 | 模型输入、资料读取、存储与诊断边界 |
| 多人使用/对外提供服务 | 真实身份、对象级权限、会话与任务隔离、请求限流和受保护入口 | RunService、工具授权与工作区 |
| 需要稳定部署或更大容量 | 目标SLA、容量测试、监控告警、备份演练；再决定是否多进程/共享存储 | 持久执行、预算与运维接口 |
| 接生产写接口 | 按每个API核验权限、确认、幂等、只读核实和补偿 | 工具执行策略与操作账本 |
| 确需跨独立Agent协作 | 评估A2A、身份、结果查询与跨进程重复执行风险 | 委派协议边界，不直接照搬本地方法调用 |
| 工具/用户规模确实增加 | 再评估Gateway、配置界面、租户或计费 | 外围适配，不先改核心循环 |

其中数据安全、真实授权和业务副作用控制在对应场景下是上线前提，不是“可永久省略”的可选装饰；可选的是是否现在进入该场景，而不是进入后是否遵守这些边界。

应用方向可先按 [14-场景选型](14-应用场景选型：为什么先做技术支持Agent.md) 比较和确定，再按五阶段实现主体并逐步验证场景；无需等所有能力完成才考虑用途。原有样例保留作核心回归，新支持能力使用独立工具契约和检查器，不默默替换旧验收。剩下需要做的是实现与验证，不是继续凑更多阶段文档。
