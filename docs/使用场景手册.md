# Agent SDK 使用场景手册

日期：2026-10-07。适用分析基线：当前仓库 `1.1.0-SNAPSHOT`。

本文回答三个问题：SDK 是否只做单 Agent、一个 Agent 能具备哪些能力、怎样把这些能力用于真实业务。内容按当前源码区分“已有机制”“应用需要实现”和“当前不提供”，不把规划项或演示当作生产能力。

后续建设方向见[演进建议](演进建议.md)。根目录[使用手册](../使用手册.md)可辅助了解原有接入方式，但目前仍标注旧版本，且部分能力说明滞后；不要将其中所有描述直接套用到本版本。本文不替代后续与发布版本同步的完整 API 参考，也不表示本轮已完成运行验收。

## 1. 先回答：目前是单 Agent SDK 吗

**是。当前 SDK 以单 Agent 执行为核心，没有内置多 Agent Supervisor、通用工作流编排或跨节点任务调度。**

但这不意味着一个应用只能有一个 Agent，更不意味着一个 Agent 只能聊天。

- 一个 Agent 可以拥有多个工具和多项技能，完成多步任务。
- 一个应用可以配置多个不同场景，创建多个独立 Runner。
- 多个独立 Agent 可以由应用组合、顺序调用或分配到独立工作线程执行。
- Agent 之间的任务委派、结果交换、等待路由、总预算和失败传播，由上层应用负责。

应把 SDK 理解为“构建并运行 Agent 的组件”，而不是已经包含客服、酒店、CRM、数据平台和业务数据库的产品。

### 1.1 这几个概念不要混淆

| 概念 | 含义 | 不代表什么 |
| --- | --- | --- |
| ScenarioPlugin / AgentSpec | 目标说明、工具集合、运行限制、策略与完成检查 | 不是自动接通的业务系统 |
| AgentRunner | 执行任务及处理澄清、审批、取消等控制的运行器 | 不是多租户调度平台 |
| Run | 一次有状态的任务执行 | 不一定等于一条聊天消息，可能跨多次澄清和审批 |
| conversationId | 关联跨 Run 的对话历史 | 不是运行检查点，也不是授权凭证 |
| userId | 查找应用提供的用户画像等信息 | 不是身份认证或工具访问权限 |
| AgentRunnerFactory | 创建独立 Runner 的入口 | 不自动维护用户会话映射和集群路由 |

一个 Runner 同时只处理一个活动任务；WAITING_INPUT 和 WAITING_APPROVAL 也占据活动任务位置。当前存在不同冲突策略，但这些策略不会把一个 Runner 变成通用并发容器。

## 2. 一个单 Agent 可以有哪些能力

这些能力可以组合在同一个 Agent 中，但应根据业务只开放必要工具，避免把所有系统权限都集中到一个“万能助手”。

| 能力 | SDK 当前提供的机制 | 应用仍需提供 / 注意的边界 |
| --- | --- | --- |
| 理解目标、生成解释与建议 | 模型适配、场景 instructions、运行规则 | 选定可用模型；事实与权限不能只依赖模型判断 |
| 多轮澄清 | requestClarification、WAITING_INPUT、resume，及对话策略入口 | 用户界面、任务归属校验、回答路由 |
| 多步工具调用 | 模型—工具循环、参数校验、预算及错误处理 | 查询 API、数据库访问、计算或业务执行工具 |
| 读取和分析资料 | 工作区、证据与产物机制，文件分析样例 | 文件格式适配、授权输入、真实业务计算 |
| 大结果按需读取 | 工具输出外溢及工作区读取机制 | 外溢内容访问权限、磁盘容量与保留策略；不是无限上下文 |
| 结构化目标与修订 | TaskBrief、TaskPlan 数据结构及 reviseGoal 入口 | 目标/约束的业务含义与完成条件；计划对象不是工作流调度器 |
| 高风险动作等待批准 | RiskLevel、WAITING_APPROVAL、approve/reject | 正确风险标记、审批人身份与权限、幂等、提交回执 |
| 跨轮次记住对话 | ConversationMemory，内存及文件实现、压缩相关机制 | 可信会话标识、存储选择、保留期；压缩不保证永不遗忘 |
| 使用用户偏好 | UserProfileMemory 存取及运行时注入 | 偏好来源、提取/更新、授权和持久化策略 |
| 查阅 SOP / Skill | 技能注册、提示索引、consult_skill 工具及前置工具检查信息 | SOP 质量与步骤验收；这不是强制流程执行器 |
| 使用 MCP 工具 | MCP 工具适配、筛选与风险配置，stdio 和进程内传输 | 受信任 Server、命令/凭据配置、权限、实际协议兼容验证 |
| 展示任务进度 | RunStreamChunk 监听、状态及工具生命周期事件 | HTTP/SSE/WebSocket 服务与前端；内置模型适配器当前不是逐 Token 增量返回 |
| 判断任务是否达到要求 | CompletionCheck 读取真实观察与产物 | 业务验收规则；默认检查或自然语言“完成”不证明结果正确 |
| 停止与回收任务 | 运行预算、取消、等待超时检查、清理接口 | 调度清理、总会话数/队列限制、停止后的业务处置 |

一个 Agent 的实际能力由四部分共同决定：**模型能力、场景定义、被授权的业务工具、执行与验收规则**。只换一个系统提示词，不会自动产生数据库权限、真实数据或业务集成。

## 3. 哪些业务场景适合使用

下表中的工具名称是业务设计示例，不是 SDK 自带 API。除文件检查与资料分析样例外，不应理解为 SDK 已包含相应行业连接器。

| 场景 | 单 Agent 可以完成的目标 | 应用需要实现的工具举例 | 建议完成标准 |
| --- | --- | --- | --- |
| IT 客服 / 技术支持 | 了解问题、追问环境、查知识、读授权日志、生成排障建议 | 查询工单、检索知识、读取诊断摘要、提交处理记录 | 建议有证据；实际提交有回执；执行动作符合审批和权限 |
| 企业知识助手 | 检索制度和产品资料、比较信息、解释来源、不足时追问 | 受权限约束的知识检索、文档片段读取 | 关键结论有可访问来源；没有资料时不编造 |
| 客户资料助手 | 查询客户、归纳跟进记录、生成会前简报、提示缺失字段 | 授权客户查询、联系人摘要、跟进记录检索 | 客户身份与目标一致；字段来源可核对；不越权 |
| 商机辅助分析 | 基于真实记录识别信号、解释评级依据、给出下一步建议 | 查询线索、读取商机活动、计算规则指标 | 区分已知事实与推测；每条重要线索能追溯，不宣称商机必然成立 |
| 数据分析助手 | 对指定数据做筛选、聚合、对比并生成报告 | 数据集检查、受控查询、确定性统计、报告写入 | 数值由工具计算；时间/指标口径一致；报告引用实际证据 |
| 酒店 / 预订助手 | 追问日期和人数、查询房型与价格、说明政策、协助提交请求 | 库存报价、订单查询、订单提交、退款接口 | 价格与库存以业务系统为准；提交有幂等键和回执；必要时审批 |
| 单据 / 内部业务助手 | 收集材料、检查字段、解释规则、提交受控申请 | 材料读取、规则校验、申请查询与提交 | 必填项和资格由后端校验；SDK 不替代正式审批流程 |
| 文档 / 研究助手 | 读取授权资料、比较观点、整理摘要、生成带来源的草稿 | 文档读取、授权搜索接口、引用登记、文件生成 | 结论与来源一致；检索范围和未知信息明确 |
| 开发 / 运维辅助 | 解释代码或日志、生成修改建议、调用受控检查工具 | 仓库只读查询、静态分析、隔离环境测试、受控发布接口 | 权限明确；执行环境隔离；不能默认授予任意 Shell 或生产发布能力 |

### 优先选择哪类场景

起步优先选择“目标明确、数据来源明确、工具少、可以客观验收”的场景，例如只读客户查询、知识问答或排障建议。

先跑通只读闭环，再逐步加入写入。若业务一开始就必须创建订单、退款或操作生产系统，则审批、幂等与回执不是后续优化项，而是接入前置条件。

一个业务步骤很多，不等于必须拆成多 Agent。目标一致、权限域相近且结果能统一验收时，一个 Agent 配多个工具往往更简单。

## 4. 例子：一个技术支持 Agent 就能完成多步任务

用户提出：“昨晚升级后登录失败，请定位原因并给处理建议。”

可设计成下面的流程，这只是应用行为示意，不是 SDK 固定工作流：

1. **明确目标**：场景规定先诊断、不能擅自重启服务，完成检查要求证据与建议。
2. **补充信息**：缺少环境、时间段或错误码时，进入 WAITING_INPUT；应用向当前用户展示问题。
3. **读取资料**：查询当前用户能访问的工单、发布记录和脱敏诊断日志。
4. **参考 SOP**：查询适用排障步骤及所需工具；模型据此选择已授权的工具。
5. **分析与核验**：使用检索结果与诊断工具，不把日志中的指令当作权限，不编造“已检查”。
6. **需要执行时审批**：若确实要执行标记为 HIGH_RISK 的动作，进入 WAITING_APPROVAL；应用认证审批人并校验具体操作。
7. **记录真实结果**：执行工具返回业务回执；超时且提交状态不明时查询或人工核对，不盲目重试。
8. **检查交付**：根据真实 observations、artifacts 和业务条件完成验收，再向用户展示结果。

上述理解、检索、追问、SOP 参考、审批和报告都可以由一个 Agent 完成，不需要分别造一个“追问 Agent”“检索 Agent”“报告 Agent”。

如果整个业务包含独立团队长期处理、跨系统补偿、多个审批阶段或不同权限角色，则外层业务系统负责这些流程，把 Agent 作为其中的任务节点。

## 5. 将业务场景接入 SDK 的实际顺序

### 第一步：定义业务边界，而不是先写长提示词

至少明确：

- 服务谁，可信身份和租户从哪里取得。
- 哪个目标算完成，允许返回哪些无结果或需人工处理的结论。
- 允许读哪些系统、哪些字段、哪些文件。
- 是否允许写入；哪些动作必须审批，哪些完全禁止。
- 最大费用/时间、等待超时以及失败后如何交还用户。

### 第二步：提供真实工具

可以直接实现 Tool，或使用 `@AgentTool`、`@ToolParam` 和注解扫描能力减少样板代码。

每个工具都应具备明确输入与结果语义，并由应用完成：服务端权限、参数化查询、外部调用超时、敏感数据裁剪以及必要的幂等控制。写工具必须在真实提交后报告准确结果，不拿模拟对象冒充业务已联通。

RiskLevel 是受信任注册代码给出的分类，不是模型自动推断，更不是操作系统安全沙箱。声明为 READ_ONLY 不会阻止工具内部代码自行写数据；开发者必须确保声明与实现一致。

### 第三步：组装场景并显式设置完成检查

`ScenarioPlugin` 定义场景，`ScenarioPlugin.builder(...)` 可组装描述、instructions、工具、执行策略和 completionCheck；`addAnnotatedTools(...)` 可接入注解工具。

特别注意：**当前 builder 的完成检查默认返回满足。** 这提供开发便利，但不代表业务验收已经建立。需要业务可信交付时，应显式调用 `.completionCheck(...)` 设置检查，避免仅凭最终文本判定完成。

完成检查应检查真实证据与业务条件，例如“查询的是指定客户”“报告使用的是指定时间范围”“提交回执属于本次申请”。它不自动证明自然语言回答每一句都正确。

### 第四步：注册并管理会话

Boot 应用注册场景 Bean，通过 ScenarioRegistry 获取场景 spec。多用户入口使用 AgentRunnerFactory 创建并持有适当隔离的 Runner，不把一个默认单例 Runner 直接共享给所有用户。

应用维护可信的租户/用户/会话映射。默认 Factory 可共享模型、工具、事件和记忆服务，所以独立 Runner 不等于共享依赖中的数据已经自动隔离；会话和用户标识要有明确命名空间，共享业务服务也必须安全。

`run(...)` 用于提交任务；`chat(...)` 使用对话策略，在当前任务等待澄清时可将新文本路由成回答。该便利行为不是跨用户路由器，必须先确认请求属于同一可信会话；需要显式任务续答时使用 `resume(runId, answer)`。

### 第五步：按状态驱动应用界面

| 返回状态 | 应用应如何处理 |
| --- | --- |
| WAITING_INPUT | 展示 pendingQuestion，等待同一任务的用户回答 |
| WAITING_APPROVAL | 展示具体待批准动作，在后端完成审批人权限检查，再批准或拒绝 |
| COMPLETED | 展示通过配置的完成检查的结果与真实产物；不要将其当作自动事实认证 |
| STOPPED | 说明预算、策略或交付条件导致停止，决定调整目标或转人工 |
| FAILED | 展示安全错误信息并处理原因，不伪造成功 |
| CANCELLED | 告知任务已停止后续调度，保留已发生业务影响的说明 |
| RUNNING | 用于执行中的快照与事件展示；不代表 SDK 已提供异步 Job 提交平台 |

`RunResult` 当前提供 `snapshot()`、`message()`、`stopReason()`。快照、工具结果与待审批参数可能敏感，不应无鉴权完整返回到公网。

执行、续答、批准等入口可能持续阻塞至等待或终态；Web 应用需要自己的受控工作线程、任务查询和断连策略，不把大量长请求放进无限队列。

### 第六步：验证失败与资源边界

至少测试正常目标、缺参、无权限、工具失败、审批拒绝、取消、重复回答、上下文超限和等待过期。多租户应用还需测会话串线、错误 runId/approvalId 和共享记忆访问。

当前仍使用工作区资源。即使业务只访问 API，也要提供合法工作区配置；不能让模型或客户端随意指定工作区路径。会话结束时按生命周期关闭，另外制定历史与文件保留策略，不在每次 HTTP 请求返回后立即关闭等待中的 Runner。

## 6. 容易被误解的六个能力边界

### 6.1 审批挂起不是完整业务审批系统

实际枚举为 `READ_ONLY` 和 `HIGH_RISK`，不是任意多级风控规则。SDK 根据工具注册的风险分类挂起，提供批准/拒绝及待审批状态；审批人身份、授权规则和业务策略由应用提供。

approvalId 和 runId 是关联标识，不是权限凭证。用户追问的答案也不是审批授权。取消、拒绝或关闭都不能撤销已经在外部系统完成的提交。

### 6.2 RAG 可以接入，但 SDK 不是知识库产品

可以把现有知识检索服务包装成工具，让一个 Agent 检索并引用证据。向量数据库、文档解析入库、权限过滤、知识更新和来源链接维护由应用或知识服务提供。

不能因为模型能读工具返回文本，就宣称已有完整 RAG 平台；也不能把引用格式正确当作来源真实。

### 6.3 Skills 是可查阅的操作指导，不是强制工作流

当前技能机制能提供技能索引、SOP、元数据和缺失前置工具清单。`consult_skill` 返回指导信息，并不自动执行所有步骤，也不保证模型按步骤完成。

“必须先校验再提交”等关键规则，应由业务工具前置条件、可信授权和完成检查保障，不能只写进 SOP。

### 6.4 MCP 不是任意外部服务都可以直接连接

当前内置传输是本地子进程 stdio 和进程内传输，不能直接按已支持远端 HTTP/SSE/Streamable HTTP 客户端使用。需要其他传输时另行实现和验证适配。

MCP 可把外部工具桥接进场景，但不自动提供业务数据权限。只启动受信任程序、筛选必要工具、明确标记高风险操作，并保护命令配置和凭据。接通 MCP 进程不等于具备分布式高可用。

### 6.5 有记忆不等于自动画像或任务恢复

- 对话历史可存取，并有压缩相关实现；不能承诺无限轮次和关键事实永不丢失。
- 用户画像是按 userId 存取属性并注入提示词；当前不自动提取全部用户偏好，应用需要制定采集、更新、删除和授权规则。
- 默认会话记忆和画像使用内存；文件历史是可选实现，不是所有状态默认已落盘。
- 保存历史不能恢复原 Run 的待审批调用、完整模型内部状态和预算。当前不支持重启后恢复原任务。

### 6.6 有进度回调不等于已有真正逐 Token 流式输出

当前接口能提供运行状态、工具事件及文本回调，但内置 Spring AI 适配器的文本路径是先获取完整响应，再回调整段结果。

应用可以据此展示工具进度；若要求模型一边生成一边逐 Token 显示，需要另行完善模型适配器。SDK 不自带完整 Web API 或前端界面。对用户解释应提供清晰的操作摘要和证据，不承诺或默认展示模型内部思维过程。

## 7. 多个 Agent 怎么用，什么时候值得拆分

### 一个应用中可以有多个独立 Agent

例如，分别配置客户资料 Agent、技术支持 Agent、数据分析 Agent，并由应用按入口或受控路由选择。它们可以复用 SDK，但应有各自的工具许可、运行状态、会话和资源边界。

应用组合时应使用结构化结果和真实业务标识，而不是只靠一个 Agent 的自然语言声称“下一个可以执行”。传递前还要校验数据权限、结果状态和有效性。

### 优先保持单 Agent 的情况

- 目标属于同一业务任务，工具操作位于相近权限域。
- 可以用一组清楚的 instructions 和完成检查描述结果。
- 多步操作的主要区别是工具不同，而非执行主体和责任不同。
- 没有证据表明拆分能提高质量、隔离性或维护效率。

### 考虑拆成多个 Agent 的情况

- 各任务目标、工具权限或所需上下文差异明显。
- 任务需要独立评测、独立升级或由不同团队维护。
- 大上下文互相干扰，并且先做工具裁剪、检索和目标收敛仍不足。
- 应用能承担跨任务等待、审批、取消、费用和失败管理。

不是所有多步骤流程都需要多个 Agent。规则固定、必须严格按顺序执行的步骤，往往更适合普通代码或工作流；让 Agent 专注于语言理解、资料综合和需要模型判断的部分。

## 8. 当前明确不应承诺的能力

- 开箱即用的真实 CRM、酒店、工单数据库或企业账号体系。
- 内置多 Agent 自动分工、通用工作流、跨节点调度与高可用接管。
- 仅靠 RunSnapshot 或 JSONL 就能恢复原任务。
- 工具调用成功就等于业务目标完成，审批通过就等于提交必然成功。
- 只靠提示词、RiskLevel 或工作区路径校验实现完整权限隔离和系统沙箱。
- 自动保证最终答案无误、价格库存实时正确、商机真实成立或分析结论具备因果性。
- 取消会回滚所有已提交动作，或自动重试永远不会造成重复写入。

现有 samples 注册的主要场景是文件检查与资料分析，使用受控工具和虚构夹具；它们适合学习机制，不是已经交付的行业业务系统。

## 9. 最小场景设计卡

开始开发前，为每个场景填写下表，通常比先设计很多 Agent 更有效。

| 项目 | 要回答的问题 |
| --- | --- |
| 场景目标 | 用户希望完成哪一件事，成功和无结果分别是什么？ |
| 可信身份 | 谁可以用，租户、用户和任务归属如何验证？ |
| 数据与工具 | 允许调用哪些工具，能读写哪些数据？ |
| 禁止事项 | 哪些操作绝不能执行，哪些字段不能发给模型？ |
| 澄清与审批 | 缺什么信息要追问，哪些动作需要谁批准？ |
| 完成检查 | 如何使用真实工具结果、回执和产物判断是否完成？ |
| 运行预算 | 模型/工具次数、费用、主动时长、等待期和排队上限是什么？ |
| 生命周期 | 会话如何创建、路由、关闭，数据保留多久？ |
| 失败处置 | 超时、拒批、取消、重启和提交状态未知时怎么办？ |
| 验收样例 | 哪些正常与失败用例必须通过？ |

首个版本建议只做一个目标明确的场景，使用少量必要工具，验证完整闭环后再扩展能力。
