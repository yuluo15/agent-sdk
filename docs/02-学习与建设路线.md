# 学习与建设路线

不按 P0—P100 凑数量。围绕 Agent 能力分成五段，每次只详细设计准备实现的一段；其中多 Agent 是可选进阶，不是成熟系统的必经之路。

## 阶段一：让单 Agent 真正行动起来

**学习重点：**Tool Calling、Agent Loop、类似 ReAct 的行动—观察模式。

**建设内容：**一个模型、几个受控工具、一个 Runner、最基本的上下文与执行轨迹；命令行或简单 API 入口即可，不必先写完整 Web 页面。

**练习：**用资料分析任务验证它能够发现信息、调用工具、根据结果补查并生成产物。

**阶段成果：**不是一次模型回答，而是一条可看到真实工具执行、可停止、可重复运行的任务链路。

**先不做：**多 Agent、长期记忆、MCP 网关、向量数据库、管理后台。

## 阶段二：让单 Agent 能做更长、更复杂的任务

**学习重点：**上下文工程、规划与执行、工作区、基于反馈的修正。这些也是 Deep Agents 类系统值得研究的方向。

**按需要增加：**

- 计划：复杂目标先分解，执行中允许调整；简单问题不强制先规划。
- 工作区：保存长文档、统计结果和阶段产物，按需读取。
- 上下文压缩：保留目标、关键约束和证据引用，不机械截掉早期要求。
- 进度状态：区分已完成、待处理和缺信息，记录可继续的任务进展。
- 结果检查：核对文件、计算、引用和任务要求；不要让模型只靠“自我反思”宣布答案可靠。

**练习：**资料变多、字段有冲突、目标临时变化时，仍能完成任务或清楚说明无法完成的部分。

**阶段成果：**任务变复杂时，不靠无限加长 Prompt、无界循环或不断增加 Agent 数量来解决。

**提醒：**规划、反思和子任务都会增加模型调用。先比较实际收益，再决定默认启用哪些能力。

## 阶段三：让主体获得可复用的新能力

**学习重点：**RAG、记忆、Skills、MCP。它们解决不同问题，不是四种叫法相似的同一组件。

| 能力 | 用来解决什么 | 何时引入 |
|---|---|---|
| RAG | 找到当前问题需要的外部知识 | 文件按名读取已经不够，确有检索需求时 |
| 长期记忆 | 跨任务保留稳定偏好或经确认的事实 | 已证明重复输入带来明显成本时 |
| Skills / 能力包 | 封装完成一类任务的方法、模板与相关工具 | 不希望每次重写系统 Prompt 时 |
| MCP | 标准化连接外部工具与资源 | 要复用外部工具生态或独立服务时 |

能力包可包含任务说明、所需工具、示例、输出规范和小型测试集，不先建插件市场。技能说明按需加载，避免所有行业说明同时挤占上下文；说明文档本身不授予工具权限。

长期记忆不要自动沉淀所有聊天或模型猜测。先有来源、纠错和删除方式，再决定存哪些内容。

MCP 先接一个服务，证明工具能进入现有循环；多服务治理确实成为问题时，再设计 Gateway。

**练习：**保留同一个 Runner，分别装上“资料分析”和“知识调研”能力，比较是否需要修改核心代码。

**阶段成果：**通用性来自稳定的主体和可替换能力，不是一个巨大 Prompt。

## 阶段四：研究多 Agent，但先证明它有价值

**学习重点：**Supervisor、子任务委派、上下文隔离、并行协作；需要独立 Agent 互操作时再看 A2A。

推荐只从一个清楚的结构开始：

```text
主 Agent
  ├─ 数据分析子 Agent → 返回数据结论与证据
  └─ 资料研究子 Agent → 返回相关资料与限制
        ↓
主 Agent 汇总，并检查任务是否真正完成
```

不要一开始做任意 Agent 互相聊天的网状结构。

主 Agent 委派时给明确目标和必要上下文；子 Agent 返回结构化结果、证据与未完成项，而不是复制整段聊天历史。子任务只能使用被分配的工具范围，不能通过委派扩大能力。

**比较实验：**同一任务分别用单 Agent 和多 Agent，比较任务成功、耗时、Token 和错误。只有分工确有收益才保留。

需要确定步骤、分支和暂停恢复时，可以研究图编排；图不等于必须多 Agent，多 Agent 也不等于必须使用 A2A。

**阶段成果：**能说明为什么要拆，而不只是画出更多 Agent 方框。没有收益就保持单 Agent，并直接进入下一阶段。

## 阶段五：把 Agent 引擎做成能长期使用的工程

这里的工程化仍围绕 Agent 主体，不转去设计企业管理系统。

优先补齐：

- **持久执行：**保存任务状态和必要检查点，进程重启后知道从哪里继续。
- **暂停与恢复：**支持补充输入、必要确认、取消与恢复，不能只有同步聊天接口。
- **执行安全：**已有工具结果不盲目重做；实际写业务时处理幂等和结果不确定性。
- **配置与版本：**明确一项任务使用的模型、提示词、工具与能力包版本。
- **评测与调试：**保存回归任务集，观察成功率、产物依据、成本及失败原因。
- **封装与交付：**形成清晰的 Java 模块、稳定调用入口、配置方式和本地运行说明。

可靠性不是到这里才第一次考虑：阶段一就有边界和执行轨迹；这里将它们强化为可恢复、可测试、可维护的机制。

**阶段成果：**不仅“演示时跑通过”，还能够换任务、复现问题、控制成本、重启继续、避免重复副作用。

## 主体成熟之后，外围怎样长出来

按真实使用需求扩展即可：需要多人使用再接身份与权限，需要外部工具治理再加 Gateway，需要面向业务用户再做配置界面，需要多企业共享再谈租户隔离。

接酒店、餐饮、文旅时，优先扩展工具、知识、能力包和评测，不先改 Runner。若新场景总要改引擎，回头检查主体边界，而不是不断往核心加行业判断。

成熟 Agent 引擎是企业级项目的主体，但还不是完整企业产品；真正上线后所需的安全和交付能力不能省略，只是不在本轮抢占主线。

## 技术选择原则

- 主线保持 Java，不为学习 Agent 被迫多语言化。
- 第一阶段复用 Spring AI 的模型/工具能力，先掌握薄循环，不先押注庞大平台。
- 框架替你管理哪些步骤，必须能说清楚；不要既依赖黑盒自动循环，又重复实现一套循环。
- 深入学习 LangGraph 的状态与恢复思路、Deep Agents 的规划/工作区/子任务思路，但不按产品名堆依赖。
- 只有当前阶段出现清楚问题时，才添加对应组件。

## 先学哪些资料

以下是本轮查阅的官方资料，查阅日期为 2026-09-15。用于理解设计思路，不是某个版本 API 的实现承诺，也不是“最前沿框架排名”。

1. [Spring AI：Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html) — 理解模型提出调用与应用实际执行的分工，以及循环控制方式。
2. [LangChain：Agents](https://docs.langchain.com/oss/python/langchain/agents) — 对照学习模型、工具、状态和循环扩展点。
3. [Deep Agents：Overview](https://docs.langchain.com/oss/python/deepagents/overview) — 研究复杂任务中的规划、工作区、上下文管理和子 Agent；不代表简单任务也必须采用这套组合。

阅读框架资料时，始终回到同一组问题：**谁决定下一步？谁执行？上下文里有什么？何时停？结果怎样证明？失败后怎样继续？**

阶段一详细方案已于 2026-09-16 补充：[核心详细设计](03-阶段一：单Agent核心详细设计.md) 与 [工具契约、实验与验收](04-阶段一：工具契约、实验与验收.md)。先按这两份搭建最小循环，无需先确定登录、组织或既有业务系统。

第二阶段详细方案同日补充：[复杂任务与上下文工程](05-阶段二：复杂任务与上下文工程.md) 与 [长任务实验与验收](06-阶段二：长任务实验与验收.md)。提前阅读不意味着第一阶段已经实现完成；先打通基础循环，再增加计划、工作区、上下文管理和结果修正。

第三阶段详细方案：[RAG、记忆、Skills与MCP](07-阶段三：RAG、记忆、Skills与MCP.md) 与 [能力复用实验与验收](08-阶段三：能力复用实验与验收.md)。在同一个 Runner 上实现两个能力包，以可引用知识、已确认偏好和只读工具接入验证通用性。

第四阶段详细方案：[多Agent委派与协作](09-阶段四：多Agent委派与协作.md) 与 [协作实验、对照与验收](10-阶段四：协作实验、对照与验收.md)。从一个主 Agent、最多两个子 Agent 开始，先串行交接，再研究并行；预算按整棵任务树核算，证据跨实例重新绑定，用相同目标和资源上限对照单 Agent。A2A 不作为必选，持久执行在第五阶段展开。

第五阶段详细方案：[持久执行、恢复与工程交付](11-阶段五：持久执行、恢复与工程交付.md) 与 [故障实验、评测与交付验收](12-阶段五：故障实验、评测与交付验收.md)。以本地事务、操作账本和显式恢复为起点，验证已完成动作不盲目重做、未知结果先核实、预算和版本跨重启保持；多 Agent 只在启用时验收任务树恢复。

至此五阶段主体方案齐备，不代表代码已经实现或真实生产场景已经验收。先逐阶段实现和检验，再按具体使用场景扩展外围，不必为凑阶段数量继续建设通用管理平台。
