# 阶段五：故障实验、评测与交付验收

版本：v0.1 · 第五阶段配套实验  
配套：[11-阶段五：持久执行、恢复与工程交付](11-阶段五：持久执行、恢复与工程交付.md)

本文是后续实现与验收规格，没有创建数据库、启动服务、执行崩溃测试或修改项目代码。所有强制退出、文件故障和外部动作实验只在独立的虚构测试工作区进行，不作用于真实任务或生产系统。

## 1. 本阶段验收不是“重启后还有聊天记录”

需要同时回答：

1. 保存的目标、工具消息、证据、计划和预算是否一致？
2. 已完成的动作有没有重复执行？
3. 不知道是否完成的动作有没有被误判为未执行？
4. 用户取消、拒绝、修改目标和删除资料后，旧任务是否仍可能继续？
5. 真正不具备恢复条件时，系统能否明确拒绝，而不是生成一份看起来成功的答案？

先测试单 Agent，再测试可选父子任务树。未启用多 Agent 时，相关项目记“不适用”，不得记成“通过”，也不阻塞单 Agent 主体交付。

## 2. 复用现有任务，增加故障而不是增加业务

### 2.1 标准资料分析任务

沿用 04/06/10 文档中的两日销售夹具和两份交付：comparison_report、limitations_note。长说明、退款字段改名及无因果资料限制保持不变。

正常结果：线上净额 1100→700、-400、-36.36%；全渠道 2500→2400、-100、-4.00%。报告必须说明只覆盖两日窗口，并区分订单数变化与未证实的外部原因。

这次主要改变进程寿命和持久记录，不改变计算工具的公式，也不靠恢复时给模型塞标准答案。

### 2.2 独立测试数据目录

建议每个实验拥有独立 dataRoot，包含数据库、配置快照、输入、工作项、输出和诊断。数据库及内容目录用虚构数据，不与正在开发使用的目录共用。

恢复同一任务使用原 runId、数据库与内容目录；新的故障变体新开测试目录。测试中不允许通过换 runId、手工改计数或删除账本来“修复恢复”。

### 2.3 记录方式

每次保存：实验编号、应用构建和状态结构版本、模型/工具/Skill清单、注入位置、崩溃前最后已提交序号、恢复决定、工具实际次数、账本状态、预算和最终产物摘要。

区分两种试验：

- **脚本故障测试**：用确定的模型响应和可控时钟，断言准确次数与消息关系。
- **真实模型任务**：评价恢复后的正确交付、成本与拒绝行为，不要求逐字重现。

数字基线和故障注入开关只放测试设施，不能进入生产 Prompt 或由模型自行选择关闭安全检查。

## 3. 先验证事务事实，不急着杀进程

### 实验 A：保存并重新装载

完成一次正常分析，退出进程，再通过只读 inspect 查看：

- TaskBrief、goalVersion、计划 revision、最终答案与状态相同。
- 原 Assistant 消息和各 callId 响应仍成对，协议元数据没有变成普通文本。
- 产物和证据摘要与磁盘内容一致。
- 已用预算、修正数和来源观察时间没有归零。
- 对 COMPLETED 调用 resume 被拒绝，不再次调用模型或工具。

可以查询终态任务不等于可以继续它。

### 实验 B：提交失败的全有或全无

在事务提交前注入失败，分别针对：模型响应＋批次登记、工具结果＋消息回填、用户答案＋等待结束、目标修订＋计划失效。

重开数据库后，每组要么整体存在，要么整体不存在；不能出现“预算计了，但没有对应调用记录”或“goalVersion增加了，检查器仍看旧交付集合”。

故障恢复仍要检查实际外部副作用；数据库事务原子不代表事务外工具也自动回滚。

### 实验 C：日志不是恢复入口

在状态已提交、JSONL尚未导出时退出。恢复以数据库为准，缺少的事件可按序号补导出，不重执行工具。

另准备一个无对应数据库记录的伪造日志“写报告成功”行；不能由此登记 artifact 或判任务完成。日志是诊断，不是任意命令输入。

## 4. 在具体崩溃窗口逐个测试

使用测试驱动器启动专属子进程，在指定持久边界发出可观察通知后停止该测试进程，再启动新进程恢复。异常抛出可以覆盖事务测试，但不能完全替代真实进程终止。

| 故障点 | 崩溃后应观察到什么 | 恢复后禁止什么 |
|---|---|---|
| F01：PREPARED 已提交，尚未提交发起意图 | 操作明确未开始，可按原身份继续 | 新建重复逻辑操作 |
| F02：IN_FLIGHT 提交后、I/O 尚未调用 | 保守视为 UNKNOWN | 根据测试注入位置之外的猜测宣称一定未执行 |
| F03：工具真实返回、结果事务提交前 | 外部可能已完成，账本仍未知 | 直接重新执行写工具 |
| F04：结果和Tool消息已提交、CLI回执前 | 原结果已存在 | 为重新展示而重调工具 |
| F05：原生Assistant已保存、多工具只完成第一项 | 已完成项与待处理项可区分 | 从整批第一项重放 |
| F06：最终文件发布后、产物事务提交前 | 文件清单可核实同一产物 | 写第二份报告掩盖断点 |
| F07：最终答案和COMPLETED提交后、用户未看见 | 终态可查询、答案可再次展示 | 将查询当作重新执行 |
| F08：用户答案已保存、命令回执前 | 同commandId返回原回执 | 再次回填答案或启动两轮模型 |

每个窗口至少跑正常恢复与“恢复前用户已取消/修改环境”两种分支。F02证明保守分类是必要的：真实实现无法读取测试驱动器的内心来知道请求到底有没有发出。

## 5. 模型与原生消息恢复

### 5.1 响应已保存与响应丢失

脚本模型先返回两个 tool calls，分别测试：

- 完整响应已经提交：恢复后使用原调用及原 callId，模型请求计数不增加。
- 响应只在内存中，持久存储仅有发起意图：恢复可在授权与预算内重新生成一次，新的结果不要求与丢失响应一致，旧 attempt 仍计用。
- 只有截断响应：不能从日志中的半段 JSON 拼出可执行参数。

模型适配链必须关闭隐藏工具执行。若只调用模型适配器、不经过持久 Executor，业务工具实际计数应为零。

### 5.2 半完成工具组

Assistant 同轮调用 A、B、C。让 A 已持久成功、B 在只读执行时中断、C 还未执行：

1. A 的实际计数保持 1。
2. B 若无法找回结果，可按只读策略追加最多一次尝试，原 attempt 和新 attempt 都可见。
3. C 只在 B 解决且批次继续合法后执行。
4. 下一模型请求含原 Assistant 和三条正确对应的 Tool 响应。

外部写操作另测两种合法边界：若需要确认的写动作与 A/C 混批，返回 MIXED_EFFECT_BATCH，整批包括 A 都不执行；若写动作独占批次并在发出后成为 UNKNOWN，则在核实前不进入下一模型轮，也不让模型用“应该成功了”填补结果。

### 5.3 摘要不是检查点

让上下文已经压缩，再重启：TaskBrief、计划、真实证据与操作记录从各自持久状态恢复；摘要只是候选模型视图。

摘要记录缺失或版本不匹配时，可从合法完整记录按原上下文策略重建，额外摘要请求计预算；无法装下就明确停止，不丢弃权限和未回答调用。

供应商会话状态不可重建的变体应明确拒绝恢复。不得因为普通聊天模型通过测试就宣称所有模型原生协议都可恢复。

## 6. 报告文件与数据库不一致实验

### 6.1 发布成功、账本未确认

固定报告字节、artifactId 和预留路径，在最终文件发布后注入崩溃。恢复通过提交清单验证摘要，登记同一 artifact，原写操作的结果可重建。

断言：只有一个对应最终报告、没有新正文生成、没有 report-002 被当成原调用的“恢复结果”。已占用容量没有被重复预留或漏计。

### 6.2 暂存存在、最终未发布

- 正常非终态且目标仍有效：可以继续发布预留的相同内容。
- 恢复前取消：不继续发布，暂存内容保持非交付身份，交由明确清理流程处理。
- 目标已修订：旧内容不能作为新 goalVersion 交付。
- 暂存缺失且没有完整字节副本：报存储缺口，不让模型重新写一篇后假称恢复同一结果。

### 6.3 冲突、丢失与空间不足

在独立测试目录中分别设置：预留最终位置出现错误摘要文件、已成功产物缺失、工作区额度不足、数据库不可提交。

系统应拒绝成功交付，并保留诊断和已有文件；不覆盖冲突文件、不自动删除用户资料、不用旧 JSONL 成功行补成真实文件。

空间足够保存正文却不足以暂存＋最终副本的情况也要测。配额统计包括临时开销，不只看最终文件大小。

## 7. 用虚构回执服务学习外部副作用

这是一项受控教学实验，不连接生产 API、不发真实消息、不付款、不创建真实业务工单。若暂不接外部写工具，可以先用该实验理解边界，但交付说明必须标明“生产写动作尚未验收”。

### 7.1 独立、可核算的服务夹具

未来测试服务提供两个能力，是否通过 MCP 包装由实现阶段决定；即使使用 MCP，业务幂等契约仍由服务自己保证。

| 能力 | 输入与行为 |
|---|---|
| recordReceipt | 程序注入稳定 operationKey，业务参数仅 fixtureRecordId 和短标签；在服务自己的持久事务中登记一条虚构回执 |
| queryReceipt | 只读按 operationKey 查询最终/处理中/未知状态，不触发登记 |

同一 key＋同参数返回原 receiptId；同 key＋不同参数明确冲突。服务端保存参数摘要和键有效期，并有持久实际写入计数。服务的存储和进程独立于 Agent，以便 Agent 崩溃后仍可观察动作是否已经发生。

该夹具证明的是它自己的唯一键＋事务契约，不推广为任意 MCP 服务都有 exactly-once。

### 7.2 已生效，但客户端没收到结果

1. 用户确认该精确虚构动作。
2. Agent 提交发起记录并调用 recordReceipt。
3. 服务持久完成回执，但丢弃响应或在 Agent 保存结果前终止 Agent 测试进程。
4. 恢复看到 UNKNOWN，通过 queryReceipt 查原 key。
5. 收到匹配已应用结果后保存原 receiptId，继续原 callId，不再调用 recordReceipt。

断言：服务实际写入次数为 1，queryReceipt 增加只读核实次数，Agent 不因断线再生成第二个业务操作身份。

### 7.3 查不到不等于没执行

服务让旧请求仍在处理队列，查询暂时没有结果。正确行为是 BLOCKED/需要核实，而不是换 key 或重发写调用。

若要试验“明确未应用后重发”，服务必须能终结原尝试并返回不会迟到生效的终态；还须满足正文要求的当前意图、有效确认、工具契约和明确人工决定。单纯空查询或存在幂等键，均不能替代本阶段选择的这些前提。

### 7.4 取消后只核实，不补写

在 recordReceipt 未知时取消根任务。服务可分别最终应用/最终未应用，系统仅通过只读查询补充真实事实，根仍 CANCELLED。

不得调用 recordReceipt 来“问一下同键结果”：如果原来没生效，这次调用可能首次生效。撤销另有授权和契约，本实验不提供通用 undo。

### 7.5 确认边界

测试确认过期、参数改变、目标版本变更、用 `/answer` 冒充批准、同 commandId 内容改变以及恢复时反复点击批准。

只有匹配的当前 actionFingerprint 才允许首次执行。已批准但 UNKNOWN 的操作仍需核实，不因再批准一次就允许重发。

分别测试发起前到期与发起后到期：前者可记 NOT_EXECUTED；后者保留 IN_FLIGHT/UNKNOWN 并核实，不能因用户确认已过期就伪造未执行结果或提前结束原 callId。

## 8. 暂停、等待和目标修订跨重启

### 8.1 澄清问题恢复

让 Agent 通过 requestClarification 询问指标适用范围，保存 WAITING_INPUT 后退出。

重启先做恢复检查，显示相同 questionId 和原 callId，不自动发模型请求。用户答复持久化后继续原 Run，预算保持；重复提交原 commandId 只返回已有回执。

临时将状态记录为 WAITING_INPUT、但关联问题缺失的损坏变体应阻塞，不能生成一个新问题掩盖损坏。

### 8.2 主动暂停

在模型请求中发 pause：回执先是“暂停已请求”，实际响应到达并保存后、未启动其新工具时，系统进入 PAUSED。重启后不自动继续；resume 校验通过才执行待处理调用。

如果模型/工具尚未真正退出，不能宣称安全暂停或提前释放资源。暂停发生在原本等待问题时，恢复后仍回到同一个等待，先恢复再回答。

### 8.3 目标修订到线上范围

复用阶段二/四的目标修订：version=2，groups=[线上]，只有 comparison_report，但保留局限章节。

分别在“修订已登记未确认”“用户确认事务前”“确认事务后”“新计划尚未获准”退出：

- 未确认重启后继续显示原旧值→新值预览；旧问题仍未被伪造回答。
- 确认事务全有或全无，不出现目标和检查器两版混合。
- 新目标报告总计为线上 1100→700，而非全渠道 2500→2400。
- 拒绝修订保留旧目标和问题，但已经停止的旧子任务不复活。
- PLANNED 模式仍先更新计划，planRevision 和预算不归零。

暂停/恢复不是另一种 revise；不能在恢复配置时顺带扩大资料目录或替换指标目标。

## 9. 预算、所有者和重复恢复

### 9.1 重启不清空额度

让根已消耗 39 次生成，最后一次请求已经提交发起意图但响应未保存。重启后该 attempt 仍计用；若总额已经达到 40，就不能“为了恢复”再发第 41 次。

未消耗的预留额度与已用额度分别保存。恢复已登记但未执行的工具调用不再扣一次初始调用；实际额外重试另扣，防止重复收费和漏收费两个方向的错误。

反复启动/停止恢复不会清空子任务尝试数、修正数、3 次恢复追加尝试上限或无进展计数。

### 9.2 主动时间与日历时间

用可控时钟测试一个已预扣 60 秒、实际跑 10 秒就崩溃的根许可段：恢复保守记 60 秒，不按离线 2 小时继续加时，也不猜测只用 10 秒退回。

正常无在途动作安全结算时，才退回该段未用部分。两个子任务同时运行 10 秒，正常结算根消耗 10 秒而不是 20 秒；各 Worker 累计耗时单独统计。

另让第三阶段的外部状态在等待/离线后超过 60 秒：必须重查。确认到期同理，主动预算不走不意味着业务时间停止。

### 9.3 两个进程不能同时接管

第二个应用指向同一 dataRoot 时，应因操作系统独占锁失败而拒绝接管；不删除锁文件、不发模型或工具。

在测试适配器中让旧 ownerEpoch 的回调迟到，即使内容合法，也不能推进新所有者状态。外部服务不受本地 epoch 直接约束，因此仍需业务核实，不能以 epoch 检查替代副作用处理。

数据库写失败时停止调度；不能依赖内存“暂时继续”并希望下一次恢复自动补齐所有事实。

## 10. 可选父子任务树恢复

只对启用第四阶段的实现适用。

### 10.1 委派登记后崩溃

父 delegateTasks 已持久登记两子身份和预留额度，但子 Worker 尚未全部启动。恢复使用原 subtaskId/childRunId 和原额度，不再执行一次新的 delegateTasks 创建第二组子任务。

### 10.2 一个子完成、一个仍在执行

数据子已持久完成并存有计算证据，资料子在读取期间崩溃：

- 数据子实际分析次数不增加。
- 资料子按自己检查点恢复，不继承兄弟的模型历史。
- 父仍等待原批次，汇聚后只有一次父 callId 响应。
- 根共享预算、来源范围、Skill/知识快照与 goalVersion 保持一致。

### 10.3 汇聚原子性

在父证据复制/登记与委派响应回填的各阶段注入失败。恢复后证据映射可以重新确认，但不能产生两次父工具响应，也不能把无映射的子 evidenceId 直接塞入报告。

孤儿内容不等于成功证据。目录存在但数据库没有接纳记录，不得自动视为完成。

### 10.4 屏障优先于检查点

根已取消或已登记修订时崩溃，恢复不能把旧非终态子记录当成可以直接启动的工作。已 STOPPED 的缺信息子任务也不 resume；父答复后需要补做时创建新尝试并计量。

没有实现多 Agent 的项目不需要为了通过本阶段额外实现一套调度平台。

## 11. 版本、撤回、备份与交付实验

### 11.1 冻结和不兼容

保存旧 Skill/提示/工具 Schema/检查器版本，发布新版本后：旧任务若仍具备兼容实现与快照，恢复使用旧清单；新任务使用新版。

删除旧可重建版本、换不兼容适配器、改变消息结构或工具执行策略时，恢复明确阻塞；不能把版本不一致只记 warning 后继续写。

MCP 重连重新初始化并核对批准目录；不同 JSON-RPC request id 不影响逻辑操作身份，但旧请求不直接重放。

### 11.2 撤回和记忆删除

旧任务暂停期间撤回已用知识来源、禁用工具或删除已加载偏好。恢复检查必须看到当前禁用信息并拒绝加载/继续；历史快照不能凌驾于禁用。

删除偏好时先取消受影响的可恢复任务，并按声明的清理范围处理可重建视图。测试不从旧摘要或检查点复活偏好，同时明确备份/历史产物/供应商记录不等于已被物理删除。

### 11.3 备份与恢复不是只复制数据库

在应用已停止并持有维护锁时，保存数据库、内容及快照清单到独立测试位置，验证摘要。正常续跑实验须确认原目录之后没有任何任务状态推进，并停用原执行副本，再从备份做只读检查与显式恢复；不能让原目录和备份副本同时接管同一任务。

另测过期备份：备份后原任务继续执行一次动作、消耗预算，或被取消/修订，再尝试从旧备份续跑。必须拒绝，备份只能只读查看；若无法确认备份后是否有执行，也不得续跑。不能用旧 PREPARED 状态覆盖后来已发生的动作或取消屏障。

缺一份被引用证据的备份应失败；不能仅因数据库能打开就宣称备份可用。迁移失败时保留原可用备份，只有满足正文的未继续执行条件才允许回退，不在损坏的新库上反复自动尝试执行任务。

测试目录总容量阈值和清理预览。活跃、暂停、可恢复任务引用的内容不能被默认清理；备份另有额度，不通过无限备份绕过磁盘边界。

## 12. 验收矩阵

### 12.1 确定性与集成测试规格

| 编号 | 情形 | 必须成立 |
|---|---|---|
| S5-01 | 正常任务持久保存后查询 | 目标、产物、消息、预算一致，无额外模型/工具执行 |
| S5-02 | 事务中途失败 | 关联状态全有或全无，不出现计数/消息/版本撕裂 |
| S5-03 | 状态已提交而JSONL未导出 | 以DB为准，补日志不重放业务 |
| S5-04 | 只有伪造成功日志 | 不登记真实成功或产物 |
| S5-05 | PREPARED后崩溃 | 恢复同一操作身份，按原计数继续 |
| S5-06 | IN_FLIGHT后无持久结果 | 保守UNKNOWN，不推断未执行 |
| S5-07 | 模型完整响应已提交 | 复用原生响应/callId，不重新生成 |
| S5-08 | 模型响应丢失/截断 | 无半参数执行，允许的重生成显式计费且有上限 |
| S5-09 | 模型适配器独立调用 | 无框架隐藏业务工具执行 |

| S5-12 | 控制工具处于恢复边界 | 恢复已存计划/问题/委派状态，不文本重放 |

| S5-14 | 只有暂存，之后取消/换目标 | 不继续发布为当前交付 |

| S5-17 | WAITING_INPUT跨重启 | 原问题和callId保留，恢复前无模型请求 |
| S5-18 | 答复事务成功而回执丢失 | 同commandId幂等，同ID不同内容拒绝 |

| S5-20 | COMPLETED/STOPPED/FAILED/CANCELLED恢复 | 拒绝续跑，允许只读查询 |
| S5-21 | 目标修订确认边界崩溃 | 新目标、问题处理、检查条件与计划失效原子一致 |
| S5-22 | 拒绝修订/原澄清未回答 | 保留旧关联，不复活被停止的子任务 |
| S5-23 | 动作确认过期/参数或目标改变 | 未发起者不执行；已发起者仍核实，不伪造未执行；answer不能批准 |
| S5-24 | 写动作已生效但响应丢失 | 查询原键核实，实际写入一次，原结果可恢复 |
| S5-25 | 写动作查询暂时无结果 | 保持未知，不换键、不盲重发 |
| S5-26 | 取消后的未知写动作 | 只读核实，终态不复活，不补做首次写入 |
| S5-27 | 超时/崩溃后用量不完整 | attempt仍计量，Token未知不记零 |
| S5-28 | 重启与子额度预留 | 已用/预留/未用明确，40/80及恢复上限不刷新 |
| S5-29 | 未结算主动时间许可段 | 崩溃保守扣段，离线不无界加时或返还额度 |
| S5-30 | 暂停后外部状态或确认过期 | 日历时效继续，不能导入时重新盖章 |
| S5-31 | 第二进程/旧epoch回调 | 不双重接管、不推进新状态，外部效果另核实 |
| S5-32 | DB不可提交/损坏 | 停止新调度，不用内存和日志伪造恢复 |
| S5-33 | Skill/模型适配/工具/检查器不兼容 | 不静默升级旧Run，给明确恢复阻塞原因 |
| S5-34 | 来源撤回/工具禁用/偏好删除 | 当前禁用优先，旧检查点不复活资料与记忆 |
| S5-35 | 压缩视图恢复 | 事实从账本恢复，原生消息协议与输入预算仍合法 |
| S5-36 | 备份缺内容/原任务后来推进/迁移失败 | 拒绝不安全续跑，不回退动作事实与预算，不破坏原备份 |
| S5-37 | 可选父子登记后崩溃 | 同子身份与预留，不重复委派 |
| S5-38 | 可选一子完成一子中断 | 已成子不重做，未完成按检查点恢复，预算共享 |
| S5-39 | 可选父导入/汇聚中途失败 | 引用与父响应不重复、不遗漏、不提升来源权威 |
| S5-40 | 可选取消/修订屏障后重启 | 旧子不复活，终态与新版本不被迟到结果覆盖 |
| S5-41 | 终态提交后展示前崩溃 | 原答案可查询，终态不重新执行 |
| S5-42 | 第一至四阶段回归 | 计算、引用、权限、callId、上下文和目标规则仍成立 |

S5-24 至 S5-26 的外部副作用验收要求独立服务端持久账本，不能只看客户端“调用一次”的计数。S5-37 至 S5-40 对未启用多 Agent 的实现明确记不适用。

### 12.2 真实模型回归

每类先做 3 次，保存全部成功和失败：

- 正常两日分析，无故障，确保持久化没有改变正确结果。
- 计算证据已保存后退出，恢复生成报告；不重复计算已确认结果。
- 等待口径澄清时退出，恢复同一个问题并完成任务。
- 报告已发布、结果未提交时退出，恢复同一文件及依据。
- 目标修订到线上范围后退出，恢复交付 v2 的正确范围。
- 产品调研暂停至状态过期，恢复必须重查而不引用陈旧可供应结论。
- 若启用多 Agent，一个子结果已保存时退出，恢复后正确汇聚。

真实模型可能选择不同工具路径。触发条件应绑定真实持久事件，不强迫固定轮次。若所选路径没有到达故障点，记录未触发，不能算故障恢复通过。

## 13. 衡量可靠性收益和持久化开销

对同一模型、任务、资料版本和预算，记录：

| 指标 | 说明 |
|---|---|
| 无故障交付正确率 | 检查数字、范围和引用，不仅RunStatus |
| 已触发故障的恢复结果 | 安全完成／正确阻塞／终态不可恢复／错误恢复，分开统计 |
| 重复副作用次数 | 以独立服务端或文件提交身份核实，安全边界用例不接受一次重复 |
| 重复读取/计算/生成 | 记录恢复成本，不把所有重复都等同于业务重复写 |
| 崩溃前后计量差异 | 已知用量、保守扣账和未知Token分别报告 |
| 存储开销 | 事务次数、检查点耗时、数据库/内容/暂存大小 |
| 恢复耗时 | 启动检查、人工等待、核实及继续执行分开 |
| 正确阻塞理由 | 版本不兼容、数据缺失、UNKNOWN未解、撤回、额度不足 |

对照可用“同一新版代码，无故障”与“同一新版代码，受控故障”比较恢复开销；也可另比前阶段内存版的正常性能，但不能把内存版不支持重启当作模型任务能力变差。

正确拒绝重复写入，比为了提高完成率冒险重试更重要。小样本仅作为回归，不能由此承诺生产年可用性、P99 或任意外部API exactly-once。

## 14. 最小交付与验收顺序

### 14.1 建议的小步

| 步骤 | 实现内容 | 首先证明 |
|---|---|---|
| 1 | 本地事务状态、快照版本、独占锁 | 能重开读取，状态全有或全无 |
| 2 | 模型/工具操作账本和原生消息 | 已提交结果不重复执行，未知可辨别 |
| 3 | 文件提交清单与核实 | 已发布报告可找回，冲突不覆盖 |
| 4 | 显式恢复、暂停、答复去重 | 安全继续同Run，不复活终态 |
| 5 | 持久取消与目标修订 | 旧意图不能跨重启绕过屏障 |
| 6 | 虚构外部动作确认与核实 | 已生效响应丢失不重复，查不到不盲重发 |
| 7 | 可选父子树恢复 | 不重复委派、汇聚或子成功动作 |
| 8 | 版本、备份、容量和评测打包 | 能在干净本地目录复现运行与恢复 |

### 14.2 实现完成后应具备的材料

- 一个可运行的 Java 打包物及明确的 JDK、依赖和构建版本。
- 无密钥示例配置，区分模型凭据引用、数据目录、预算、工具能力与恢复策略。
- 资料分析和知识调研的受控能力包、虚构输入和确定基线；多 Agent 配置可选。
- 启动、查询、回答、暂停、恢复、取消、未知动作核实的操作说明。
- 数据目录与备份/迁移/清理说明，以及单进程、本地磁盘等运行前提。
- 自动化测试与真实模型实验记录；未测、失败和不适用项明确标注。
- 已知限制：不支持的供应商会话、未验证的外部写API、无集群恢复、无企业身份系统等。

本轮没有为工程创建上述配置、脚本或README；这里只规定用户后续实现时应交付什么。不能因方案列了清单就把它勾为已完成。

## 15. 五阶段收束：得到主体，不急着做平台

五阶段方案走完，应形成从模型工具循环、长任务上下文、可复用能力、可选协作到可靠执行的一条完整学习路线。

进入真实场景前，先选择明确的数据范围与低风险动作，检查真实权限、数据外发、业务幂等和运行容量。需要多人使用再接身份权限，需要稳定服务再补部署保障；这些不能省，但不应反过来挤掉 Agent 主体。

最终判据不是“框架最多”或“每次都返回成功”，而是：**能完成时有真实产物和依据，不能继续时能说明原因，恢复时不丢目标、不越界、不盲目重复已经发生的动作。**
