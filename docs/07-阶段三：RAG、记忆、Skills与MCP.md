# 阶段三：RAG、记忆、Skills 与 MCP

版本：v0.1 · 第三阶段详细设计  
交付：方案，不编写或修改项目代码。  
配套：[08-阶段三：能力复用实验与验收](08-阶段三：能力复用实验与验收.md)

## 1. 这一阶段解决什么问题

阶段一让 Agent 会行动，阶段二让它能处理长任务。阶段三的目标是：

> 不重写 Runner，通过替换做事方法、资料范围和工具集合，让同一个 Agent 引擎完成不同类型的任务，并安全复用少量跨任务信息。

四种能力的分工必须先分清：

| 能力 | 回答的问题 | 不是 |
|---|---|---|
| RAG | 这次需要哪些外部资料，有没有来源支持？ | 把所有文件塞进 Prompt；相似度高就事实正确 |
| 长期记忆 | 下次值得继续采用哪些已经确认的信息？ | 无限聊天记录；把模型猜测存成事实 |
| Skills | 做这一类事情有哪些可复用方法、模板和约束？ | 又创建一个 Agent；通过说明文档自动获得权限 |
| MCP | 怎样用统一协议调用外部能力？ | Agent 循环本身；自动保证授权和业务幂等 |

仍然是单 Java 项目中的一个 Runner。首个 MCP Server 可以是独立本地进程，用来学习协议边界；其他部分不拆微服务，不建设插件市场和中心网关。

### 1.1 实施前提与非目标

方案可以先行，不能据此假定阶段一、二的代码已实现。真正接入前，需要已有工具循环、上下文预算、来源引用、用户补充和产物检查机制。

本阶段不做：多 Agent、A2A、自动下载并执行第三方插件、通用脚本工具、企业登录组织、多租户 SaaS、支付下单、自动审批、崩溃任务恢复。

长期记忆和知识索引可以跨进程保存，但这不代表旧 Run 能在重启后继续；活跃任务恢复仍属于第五阶段。

## 2. 四种能力怎样接到现有主体

```text
本地选择任务能力包与资料范围
          ↓
按能力包组装 AgentSpec
  ├─ Skill 的已审核方法与模板
  ├─ 当前 TaskBrief 与允许的工具
  ├─ 知识集合与索引版本
  └─ 当前本地档案的已确认偏好
          ↓
已有 Runner：模型 → 工具 → 观察 → 再次模型
  ├─ searchKnowledge / readKnowledge → 检索与原文
  ├─ 原有分析工具与工作区工具
  └─ MCP 适配工具 → 本地 MCP Server → 只读资料服务
          ↓
按当前能力包的检查规则验证产物
          ↓
用户可另外确认一条长期偏好，供下一次任务使用
```

知识查询和 MCP 调用都经过同一个受限工具目录、预算和事件链路。不能让 RAG Advisor 或 MCP 客户端在 Runner 不知情时再驱动一个工具循环。

Skill 激活、资料集合选择和工具批准在 Run 开始前完成；模型在当前 Run 内选择如何使用这些能力，不自行安装新能力。

## 3. 明确覆盖前两阶段哪些约束

| 原来的约束 | 本阶段演进 | 不变的底线 |
|---|---|---|
| 资料都来自本 Run 工作目录 | 增加已登记的跨 Run 知识集合 | 原文来源、版本和可见范围可核查 |
| 没有跨 Run 记忆 | 增加单用户本地确认型偏好 | 笔记、摘要和模型猜测不自动变为记忆 |
| Agent 方法写在配置/Prompt | 可从受控 Skill 目录加载 | Skill 不修改权限、目标或预算 |
| 工具是本地 Java 函数 | 增加 MCP 客户端适配工具 | 模型只提出调用，程序执行 |
| 报告至少引用一次分析结果 | 按任务类型分别检查证据 | 调研报告不被迫调用销售分析工具 |
| 工作项引用只属于本 Run | 全局资料可复用，但引用进入任务时重新绑定本 Run | 不直接把另一个 Run 的产物当本次已完成 |

第二阶段的目标版本、消息组压缩、有限修正和取消规则继续沿用。更换 Skill、知识集合或 MCP 服务属于更换任务环境，首版要求新建 Run，不通过 revise 偷偷扩大当前能力。

## 4. Skills：先做受控能力包，不做插件市场

### 4.1 区分开放格式与本项目装配配置

Agent Skills 规范以包含 YAML 元数据的 `SKILL.md` 为入口，name、description 是必需信息；可选 references、assets、scripts。渐进加载通常先看元数据，再读所选 Skill 正文，最后按需读附属资料。

本项目采用**无脚本、人工安装、单 Skill 激活的受限子集**，不宣称支持所有 Agent Skills 扩展。文件格式相似也不代表任意第三方 Skill 都兼容或可信。

建议布局：

```text
skills/
  data-analysis/
    SKILL.md
    references/metric-guide.md
    assets/report-template.md
  product-research/
    SKILL.md
    references/research-guide.md
    assets/comparison-template.md
```

这只是未来实现结构，本次不创建这些文件。

另由应用受控配置维护：skillId → 内容版本/摘要、允许工具、知识集合、TaskBrief Schema、CompletionCheck 标识。标准 SKILL.md 不承担应用的类加载或权限注册工作。

### 4.2 SKILL.md 写什么

- 适用任务和不适用任务。
- 推荐步骤，以及何时可以跳过步骤。
- 必须补充的信息、如何处理资料冲突。
- 输出结构与引用要求。
- references/assets 的相对引用。

不要把访问密钥、Java 类名、Shell 命令或运行时配置嵌进去让模型执行；不把工具的实现细节抄成几千行 Prompt。

### 4.3 装配与执行边界

1. CLI 列出受控目录中已登记的 name/description；用户选择一个 Skill。
2. 加载该 Skill 正文和已批准的配置，核对名称、路径、大小与内容摘要。
3. 构造 AgentSpec 和 TaskBrief；缺少必需工具或检查器就启动失败，不临时放宽限制。
4. 模型仅获得当前 Skill 的方法和允许工具。引用资料通过有界 readSkillReference 读取，不加载全部 Skill 目录。
5. 固定本 Run 使用的 Skill 版本。更新供新 Run 使用，不在运行中静默改说明。

`allowed-tools` 在开放规范中属于实验性字段。本项目如解析它，也仅把它作为“需求声明”，不能扩大本地批准工具集合；需求不被允许就拒绝激活。遇到 scripts 或不支持的执行要求，明确拒绝，不忽略后假称兼容。

首版禁止通过模型调用切换 Skill。以后需要自动推荐时，可以让模型推荐候选名称，但最终激活仍由可信装配层完成。

### 4.4 两个能力包足以验证通用性

- data-analysis：沿用 CSV 分析与报告检查。
- product-research：知识检索、原文回读、只读产品状态查询与调研报告检查。

如果为了后者在 Runner 里增加 `if product-research` 或修改销售计算逻辑，就说明边界没有做好。应更换配置、工具和检查器，而非通用执行循环。

## 5. RAG：建立能够回到原文的资料链路

### 5.1 本阶段选 Agentic RAG，但从简单检索开始

固定两步 RAG 是“先检索，再生成”；Agentic RAG 是模型在工具循环里决定何时查、怎样改写问题以及是否补查。本项目选择后者作为任务流程，复用 searchKnowledge/readKnowledge 工具，不再外加每轮自动查询的 Advisor。

本阶段实现顺序：先做可解释的关键词检索基线，再加入向量检索和一个简单混合排序实验。不要先做查询扩展 Agent、模型重排 Agent 或多知识库联邦。

Java 侧可复用 Spring AI 的 EmbeddingModel/VectorStore 等能力，但核心契约不绑定某个数据库和默认 Advisor。关键词检索选成熟库并明确中文分词；不要用仅按空格分词的英文方案来证明中文检索有效。

实验集合很小时，向量可保存在本地受控文件并加载内存检索；先证明召回有收益，再考虑独立向量数据库。

### 5.2 入库与查询是两个过程

**入库不在 Agent 自主循环里进行。** 本地操作员指定受控资料目录，执行一次导入：

1. 只接收初期支持的 UTF-8 TXT/Markdown，排除凭据、运行日志和未批准资料。
2. 为每份来源登记 sourceId、sourceVersion、内容摘要、标题、资料范围和适用日期。
3. 按标题/段落切块，保留原文行号或字符范围；长段落再按有界窗口切分。
4. 建立关键词索引；向量实验额外调用明确选定的 Embedding 模型。
5. 完整写入一个新 indexRevision，再发布可供新 Run 使用；失败时旧索引保持可用。

建议起步 300—500 Token 一块、最多约 50 Token 重叠，保留段落完整性优先。具体按中文资料评测调整，不是通用最优值。

索引需要保存 embedding 模型/版本、维度、切分版本和源摘要。更换模型或维度必须重建相应索引；向量不能直接跨模型比较。

外部 Embedding 服务也会接收原文；它不是“只传数字”。使用真实资料前明确数据能否出网，本实验只用虚构资料。

### 5.3 资料集合与版本

本地配置给每个 AgentSpec 明确 collectionIds；工具参数不能凭模型随意指定全盘集合。关键词、向量、缓存和原文回读都使用相同的范围限制。

资料原文保存不可变快照。Run 固定 indexRevision/sourceVersion，不受普通新版本发布影响；新 Run 再采用新索引。原目录源文件发生改变，不代表旧引用悄悄指向新文字。

“新版发布”和“资料撤回”要区分：

- 普通更新：旧 Run 保留原快照，显示资料版本与截至信息。
- 撤回/禁止使用：立即禁用该 sourceId 或版本，不能因为 Run 固定旧索引继续回读或交付。

本阶段撤回采用保守规则：凡当前 Run 已使用被撤回来源，下一执行/提交边界停止；新 Run 排除该来源。已发生的模型外发无法撤回，不能宣称撤回接口能消除供应商端内容。

旧快照不是生产权限实现。当前仅本地单用户、可信配置划定资料范围；多人使用前仍需补真正的身份和对象级授权。

### 5.4 两个核心工具

**searchKnowledge**

- 输入：query、可选 topK（默认 5、最大 8）。业务适用日期来自当前 TaskBrief，模型不能放宽批准集合。
- 输出：hitId、sourceId/sourceVersion、chunkId、标题、定位、短摘录、排序分数及检索方式。
- 必须有 returnedCount、是否被 topK 截断等信息。空结果表示“没有检索到”，不表示知识上已经证明“不存在”。
- 分数用于排序，不作为真实性概率或统一的跨模型置信度。

**readKnowledge**

- 输入：本 Run 已返回的 hitId，以及可选的邻近段落范围。
- 校验当前范围和撤回状态，读取命中的固定版本，返回有界原文、定位和程序生成的 evidenceId。
- 邻近回读仅限同一登记来源，不沿文中 URL、路径自动抓取任意外部内容。

搜索摘录只作候选导航，不直接作为最终主要结论证据；核心主张必须回读原文，再用 evidenceId 进入报告。这样同时练习“检索到”和“证据支持”的区别。

### 5.5 关键词、向量和混合排序

- 关键词：适合型号、字段名、明确术语；必须记录分词与匹配规则。
- 向量：适合同义表达，但可能找来主题相近、事实不适用的材料。
- 混合：先用相同的集合/版本过滤，再融合各自排名；可以采用 RRF，不直接把不可比较的原始分数相加。

RRF 实验可取 `score = Σ 1/(60 + rank)`，rank 从 1 开始。这个参数仅为可复现起点；去重按 sourceVersion＋chunk 范围，不让重叠切块占满所有候选。

不预设“加向量一定更好”。用配套同义问法、编号查询和无答案问题对比，记录各自优势与错误。

### 5.6 资料冲突与无答案

文档更新时间不等于业务生效时间。遇到旧版、草稿与正式资料冲突，应结合已登记适用范围、状态及原文判断；无法确定时提问或声明冲突，不让相似度裁决哪份政策生效。

searchKnowledge 无结果可有限改写查询；整个 Run 建议最多 6 次搜索，每个问题最多 2 次改写。空结果、重复片段和换一个新 hitId 不算新进展。

拿不到必要依据时不制造引用。知识问答可按预先约定输出“未找到依据”；必须完成的产品选型资料缺失时仍遵守阶段二的等待或 STOPPED 规则。

## 6. 长期记忆：先做好确认型偏好，不做自动学习人格

### 6.1 第一版只存什么

先限定在用户确认的展示偏好，例如默认语言、先结论后解释、报告是否简洁。稳定业务事实的跨任务沉淀留作后续评估，不把本阶段扩大成事实数据库。

销售额、产品状态、知识政策、密码、Token、模型推断的人物信息都不进这个记忆库。当前任务的“这次只看线上”也不是长期偏好。

长期记忆与第二阶段的笔记区别是：**跨 Run 复用需要单独授权，不能因它落在磁盘上就自动继承。**

### 6.2 最小结构和存储

MemoryItem 保存 memoryId、profileId、namespace、key、value、revision、confirmedAt、expiresAt（可选）、状态与确认事件引用。

profileId 和 namespace 由本地启动配置决定，不由模型输入决定。本阶段是单用户本地档案隔离，不把这个字段声称为已具备企业认证。

小规模用独立本地结构化存储即可：单进程串行写、校验完整文件后原子替换；写入失败保留旧有效记录且不给成功回执。可以选嵌入式存储，不必为几十条偏好部署远程数据库。

只有记忆条目需要跨进程保存，任务状态仍不恢复；重启后用新 runId 加载当前有效偏好。

### 6.3 怎样写、改、删

使用本地 CLI 的 memory list/add/update/delete 操作，而不是开放一个让模型直接持久写入的工具。

1. 用户明确提出长期偏好，或者模型提出候选；候选只是未保存的建议。
2. 在任务结束后展示精确 key/value、适用范围和替换关系，由用户确认。
3. 程序只接受白名单偏好字段；重复确认同内容不产生多条互相矛盾的记忆。
4. 更新/删除校验 expectedRevision，防止旧确认覆盖新值；修改后 revision 递增。
5. 拒绝、不确认或取消，记忆库没有变化，不能对用户说“已记住”。

首版任务结束后进行记忆操作，避免另造 WAITING_INPUT 分支与目标修订竞争。紧急删除/纠错如影响当前正在运行的任务，先取消该 Run，再更新记忆；不尝试从在途模型里“拔掉”已发送内容。

### 6.4 怎样读取与处理优先级

Run 开始时读取当前 profile/namespace 的有效记忆，最多 5 条，只投影成已知的展示默认值，记录所用 ID/版本。

优先级：程序安全边界不可改变；当前明确 TaskBrief 与本次用户要求优先于长期偏好；记忆只补默认值。偏好冲突或不适用时跳过并可解释，不扩大工具/目录范围，不让“偏好简短”删掉必需的证据附录。

首版使用结构化 key 查找，不必给偏好做 Embedding 检索。自由文本“经验总结”和自动反思记忆均不启用。

### 6.5 删除不能只改一个状态

删除后，从活跃存储、内存缓存和未来上下文中移除该偏好内容；如需去重/版本记录，仅保留不含正文的 tombstone。不要留下可被加载器重新读取的旧文件副本。

历史产物、备份、运行日志或已发送供应商的数据不一定因此消失；首版日志只记录记忆 ID/版本，避免复制正文。若已有历史内容需清除，应明确列出范围单独处理，不能把“以后不再用”宣传为所有位置的物理擦除。

已删除记忆不能从旧摘要、自动导入聊天记录或同一过期候选重新复活；再次保存必须有新的明确用户确认。

## 7. MCP：接一个服务，理解协议，不先造 Gateway

### 7.1 本阶段选择

采用一个用户控制的本地只读 MCP Server，通过 stdio 与 Java 客户端连接。Host 是当前 Agent 应用，Client 在应用内负责一个服务器连接，Server 提供能力。

作为教学协议基线，本方案明确参考 **MCP 2025-06-18** 的 lifecycle/tools 章节，不称其为最新版。实现时选支持该基线的 Java SDK，并做版本兼容验证；若实际 SDK 采用更新协议，应整体更新对应适配和测试，不能混抄不同版本字段。

本轮访问的 latest 页面出现了不同的发现和通知描述，因此不把其细节与固定版本混用。

### 7.2 为什么先 stdio

不用先处理公网服务和远程认证，但本地进程本身仍是代码执行边界：启动命令、参数、工作目录和环境变量来自人工批准配置，不能来自模型或 Skill 文本。

不自动运行来自市场的 npx/uvx 或下载脚本。服务端 stdout 只写协议内容，日志走 stderr；启动失败不给 Agent 假工具。

不继承与本工具无关的环境密钥，不允许 Server 随意读取整个工作站。协议连接不等于系统级沙箱，服务器代码必须是用户认可的。

### 7.3 初始化和发现

固定版本的顺序：Client 发 initialize，交换协议版本与 capabilities，兼容时发 notifications/initialized，再使用已协商能力。

- 不支持协商版本就断开并提示，不带着未知协议继续调用。
- tools/list 支持游标分页，必须读完批准范围内的目录后再核验；页面数量和工具数同样有上限。
- 发现结果只进入候选目录，不自动扩大 AgentSpec 的工具集合。
- 连接建立和新 Run 前主动核对目录与 Schema；Server 声明 tools.listChanged 时，客户端同时监听固定版 notifications/tools/list_changed。
- 收到变化通知，先标记连接不可继续，在下一调用/交付边界停止当前 Run；已发出请求的结果如实记录，但不能越过停用标记完成任务，不热加载新目录。
- Server 不支持通知时，只接入承诺“连接存活期间工具目录与 Schema 不变”的受控服务；升级先停连接。该模式不能检测违约服务的静默变化，验收与能力说明不得宣称具备这种保证。

本阶段只接 Tools；Resources 是可供读取的资源，Prompts 是模板，二者不自动转成获准工具，也不把 Server 的 Prompt 自动升为系统规则。

### 7.4 接到 ToolCatalog，而不是另造执行链路

应用为工具分配稳定本地别名，例如 catalog_get_product_status，映射到 serverId＋远端工具名＋批准的 Schema 摘要；避免依赖供应商不一定接受的冒号、斜线命名。

初始化后对 inputSchema、可选 outputSchema 和用途做批准记录。本地可信配置声明本阶段工具是只读且可用；服务器的 readOnlyHint 等 annotations 只是提示，不能据此授权高风险工具。

一次调用经过：Runner 的受限目录与预算 → 参数校验 → MCP Client tools/call → 结果校验 → ToolOutcome → 原模型 callId 的结果回填。

模型 callId 与 MCP 的 JSON-RPC request id 分开关联记录。后者由客户端产生，不能因为字符串相似就混用重试/去重逻辑。

只接受首期明确支持的文本或结构化结果；不支持的图像、音频或资源链接返回 UNSUPPORTED_CONTENT，不默默抓取链接或丢弃重要块。结构化输出存在时按 outputSchema 校验；没有时按批准的工具契约处理文本，不假定所有 Server 返回 JSON。

### 7.5 错误、变化和取消

| 情况 | 本阶段行为 |
|---|---|
| tools/call 返回 isError=true | 作为工具执行失败，不能当成功证据；可修正参数错误可反馈模型 |
| JSON-RPC 协议错误 | 与业务错误分开记录；名称/契约不匹配时停止该连接并要求处理 |
| 超时、断线、Server 退出 | 不伪造结果，不自动重放；必要能力不可用时停止或等待用户决定 |
| 调用参数/返回不符合批准 Schema | 拒绝采纳；不能让模型依据不合格结果完成任务 |
| 工具列表或 Schema 发生变化 | 当前 Run 不热更新、不扩大目录；标记连接不可继续，停止后重新批准并新建 Run |
| 用户取消或目标修订后旧响应返回 | 按第二阶段边界处理，不继续旧工具链或把旧结果当新目标已完成 |

本地只读工具也可能有耗时和日志副作用；只读不等于可以无限重试。首版不自动重连重放，重连后应重新协商与校验，不继承旧工具目录。

协议取消通知只表示取消请求，不保证远端已经停止；观察时间和结果状态必须如实记录。

### 7.6 外部状态证据和资料证据不同

产品状态查询结果记录 serverId、toolName、参数摘要、返回内容摘要、observedAt、来源返回的版本/有效期（若有）。只证明当次观察，不宣称永远最新。

TaskBrief 需要“当前可购买”之类时效性条件时，检查器必须验证观察时效。样例可设 60 秒观察有效期，失效后重新查询；若工具不可用，不能用模型记忆补成实时事实。

重新查询仍消耗工具和时间预算，重复结果也不能无限刷新无进展计数。普通状态变化是新的观察，不等于工具 Schema 变化；两者要区分。

## 8. 统一证据、上下文和完成检查

证据类型最少区分：CALCULATION、KNOWLEDGE_EXCERPT、EXTERNAL_OBSERVATION。每种带各自来源/版本/时间，登记到当前 Run 的证据表。

MEMORY、SKILL、NOTE、SUMMARY 不作为报告业务事实的直接证明：偏好不是产品政策，做事方法不是产品能力，笔记也不是原文。

完成检查按能力包装配：

- data-analysis：沿用目标范围、计算口径及产物版本检查。
- product-research：要求知识主张有回读证据、当前状态有合格的 MCP 观察，检查目标中的候选与交付项。

通用 writeReport 仅负责正文、deliverableKey、evidenceIds、目标版本和真实文件产物；领域证据要求移动到各自检查器/工具配置，不能继续写死“没有 analyzeDataset 就拒绝所有报告”。本阶段明确替代此前样例专属限制。

要点引用可以用 claimId→evidenceIds 的结构方便检查，但“引用存在”与“引用支持这句话”不同；后一项仍需专项评测或人工抽查，不宣称能通用自动证明。

所有新增内容进入第二阶段同一个 ContextComposer：保持资料/记忆/方法来源标记，按需加载，超过预算走受控压缩或停止，不能绕开消息组完整性。

撤回资料、停用工具或纠错记忆时，优先于冻结版本；冻结用于可追踪，不是允许继续使用已禁止内容。

## 9. 预算、保存和错误规则

保留第二阶段每 Run 40 次生成模型请求、80 次工具请求、900 秒主动时间的实验起点，不因为装了新能力就悄悄翻倍。

额外明确：

- Query Embedding 每次实际调用单独计量，初期每 Run 最多 6 次；不把其成本混成生成模型的 0 Token。
- 入库 Embedding 是独立导入作业，记录源字符/Token、文档/块数、时间和失败数，不记到某个对话任务里，也不能隐藏其成本。
- 每条记忆值最多 512 字符，最多注入 5 条；Skill 正文建议不超过 5,000 Token，参考资料按需读取。
- 每次搜索返回最多 8 个候选，知识回读、Skill 资料和 MCP 内联结果沿用 4 KiB 限制；可受控保存的大结果沿用工作项上限。
- MCP 建连/发现也有超时和总主动时间约束，工具目录最多 20 项；超出不截成“全部发现成功”，明确拒绝本阶段配置。

未变化的知识片段、偏好与 Skill 文本不反复算“新证据”；命中相同 sourceVersion＋片段或同一外部查询内容仍按第二阶段无进展规则判断。

导入、索引、记忆和技能版本的磁盘持久化只是各自数据生命周期，不提供 Run 的崩溃一致性或自动重放保证。

## 10. Java 项目如何演进

以下仅为建议职责，不声称项目已经有这些实现：

| 职责 | 本阶段扩展 |
|---|---|
| agent / bootstrap | Skill 配置装配为 AgentSpec，创建本地档案与能力快照 |
| model | 保持单次生成和原生消息；复用第二阶段上下文管理 |
| knowledge | 导入、版本快照、关键词/向量检索、原文回读与引用 |
| memory | 确认型偏好的单机存储、版本与 CLI 管理 |
| skill | 受控目录、元数据/正文/参考文件的分级读取 |
| tool / mcp | MCP 连接、发现与已批准工具适配，统一 ToolOutcome |
| workspace / trace | 新证据类型、来源定位、查询耗时与能力版本事件 |
| sample | 数据分析、产品调研两个检查器与夹具 |

不要同时把 Spring AI 自动 RAG Advisor、MCP 自动工具执行器和自己的 Runner 都打开。能力库可以复用，执行所有权只能有一套。

## 11. 推荐实现顺序

1. 先把已有资料分析 Agent 整理成一个受控 Skill，验证功能不回退。
2. 实现关键词检索＋原文回读＋引用，跑通知识调研，不先接外部服务。
3. 加 Embedding 与混合检索实验，对比是否改善同义问题。
4. 接一个已批准的只读 MCP Server，让调研结合当次业务观察。
5. 补展示偏好的确认、跨 Run 读取、覆盖和删除。
6. 用两个能力包和同一个 Runner 验证复用，再做配套异常与对照实验。

不要求每一步都马上成企业平台。第三阶段的里程碑是“能力可组合、来源可核查、循环不重写”，不是工具和框架数量最多。
