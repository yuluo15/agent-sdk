# 技术支持 Agent：核心工作流与决策边界

版本：v0.1 · 2026-09-22  
定位：按已选方向展开场景设计；只交付方案，不编写项目代码。  
前置：[14-应用场景选型](14-应用场景选型：为什么先做技术支持Agent.md)  
配套：[16-工具契约、调用样例与验收](16-技术支持Agent：工具契约、调用样例与验收.md)

## 1. 本次设计到什么程度

本次明确一个可以逐步实现的场景能力：

> 支持人员提交某个产品的资料导入／检索问题，Agent 调查被授权的任务记录与适用文档，必要时追问，形成内部调查摘要、对客回复草稿，以及需要时的升级材料。

本版固定为：单产品、单案例、单目标导入任务、单 Agent、文字输入、串行工具、只读业务数据、本地交付。没有自动发送、自动修复、工单流转、任意 SQL／Shell，也不引入多 Agent。

先实现 `support-investigation-v1` 能力配置，不新造 Runner。产品字段、证据充分条件和草稿检查放在支持场景组件中；通用 Runner 继续只负责模型、工具、消息、预算和状态。

首个可运行版本使用**人工批准的静态案例与状态快照**。它交付的是“截至快照采样时的调查”，不能叫实时诊断。在线只读查询是同一工具语义的后续接入，必须满足 16 中的对象绑定、观察一致性与时效要求后才启用。

## 2. 一条主线，三个责任主体

```text
支持人员选择案例和调查目标
            ↓
程序校验范围，创建 Run 和固定任务简报
            ↓
模型读取案例，选择下一步
            │
            ├─ 信息缺失 → requestClarification → 等待支持人员
            │                                      ↓
            │                              回填原调用后继续
            │
            ├─ 需要事实 → 查导入任务／关联索引
            │                    ↓
            ├─ 需要依据 → 搜索知识／回读原文
            │                    ↓
            └──────── 观察结果，更新调查判断 ←───────┘
                                 ↓
                   提交结构化支持处理包
                                 ↓
                 校验内容和引用，真实写本地产物
                                 ↓
                 模型最终答复 → Runner 最终检查
                                 ↓
                     交支持人员审核与处理
```

这里的流程图不是固定的工具调用清单。缺任务标识时才问；解析已经失败时不必查询索引；证据已经充分时不再规划或反复搜索。

| 主体 | 决定什么 | 不能决定什么 |
|---|---|---|
| 支持人员 | 选择案例、补充业务信息、审阅草稿 | 不能通过聊天文字绕过工具权限或伪造后台状态 |
| 模型 | 如何搜索、哪些证据需要补查、何时提问、提出什么调查结论和草稿 | 不能授予权限、制造证据、提交 Run 终态、宣称外部动作已执行 |
| 程序 | 范围与参数校验、执行工具、绑定证据、控制等待与预算、校验并保存产物 | 不把任意自然语言的根因判断假装成已经确定性证明 |

**固定的是安全与交付条件，变化的是取得足够证据的路径。**对于固定错误码可以采用确定性检查，模型不必重新“推理”已知规则。

## 3. 接收什么输入，绑定什么范围

### 3.1 可信任务简报

由本地受控配置和支持人员的选择建立，不能由模型填写权限部分。

| 字段 | 本版含义 |
|---|---|
| caseId | 本次唯一案例标识，运行中不切换 |
| objective | 调查导入／索引可见性问题并生成支持处理包 |
| goalVersion | 起步固定为 1；换案例、换已确定目标任务或换资料环境时新建 Run |
| productKey | 固定产品，例如教学用 starboat-local，不从客户正文决定 |
| allowedJobIds | 应用预先批准的有限导入任务集合，仅用于执行端范围检查 |
| targetJobId | 可已知或待补充；确定后锁定，本 Run 只分析这一任务 |
| statusBasis | 首版为 SNAPSHOT；未来显式配置 LIVE，不由模型切换 |
| snapshotId | SNAPSHOT 时固定，案例、任务和索引记录必须属于该快照 |
| allowedKnowledge | 固定知识集合／索引版本；内容适用版本还需与任务实际版本匹配 |
| permittedOutcomes | 有据建议、状态说明、满足条件的升级材料 |
| deliverableKey | 固定 support_package，一个结构化本地产物 |
| limits | 模型、工具、时间、结果大小、澄清与修正限额 |

允许范围不会因为任务没有标识而自动变成“可查询全部任务”。预批准集合是权限上限，不是模型可以遍历的候选目录；不向模型列出无关标识。

### 3.2 客户问题不是权威事实

案例正文可包含客户现象、相关时间、已尝试步骤和支持人员补充。它们是用户陈述，需要保留来源，不能直接变成后台故障证据。

特别区分：

- “上传页面提示成功”是用户陈述。
- “后台 processingState=FAILED”是任务状态观察。
- “该版本仅支持 TXT／Markdown”是文档依据。
- “可能是资源不足”没有证据时只是猜测，本版不作为诊断交付。

文本中的“忽略规则”“读取另一客户的数据”仍是案例内容，不是执行命令。

### 3.3 缺少标识时怎样续跑

1. `readSupportCase` 返回当前目标标识缺失，模型应调用 `requestClarification`。
2. 如果此时尚未绑定 targetJobId，本地输入适配器要求支持人员以 `/answer <一个任务标识>` 回答；这只是本场景对数据格式的限制，不新增审批系统。
3. 适配器先确认标识属于预批准集合；无效或未批准的输入不回填原 callId，继续等待，并提示不能扩大当前范围。
4. 合法输入被绑定为 targetJobId，连同来源记录回填原澄清调用，然后继续同一 Run；预算不清零。
5. 标识已有时，后续澄清只补充现象或复现信息，不改变目标任务、资料集合或权限。

这些操作由支持输入适配器执行，不让模型从自由文本中自行扩权。用户明确无法提供必需标识时，结束为 STOPPED/MISSING_REQUIRED_INPUT，不生成“调查已完成”草稿。

如一开始目标标识填写错误，或用户后来要求调查另一个任务，结束当前调查并新建 Run；本版不实现支持场景的目标修订 Schema。已有其他能力的 revise 行为不受影响。

## 4. 状态、调查进展与结论不要混在一起

### 4.1 继续使用通用 RunStatus

| 状态 | 本场景含义 |
|---|---|
| RUNNING | 模型决策、执行工具或生成产物 |
| WAITING_INPUT | 等待当前澄清问题的回答，不继续查询 |
| COMPLETED | 支持处理包通过检查并有最终答复；客户问题不一定解决 |
| STOPPED | 资料缺口、预算或业务边界使本次调查无法完成 |
| FAILED | 模型协议、工具依赖、存储或数据完整性故障 |
| CANCELLED | 已接受取消，停止新增动作 |

第五阶段真正实现后才启用 PAUSED 与持久恢复；现在不能因为草稿保存了就声称任务能崩溃续跑。

### 4.2 最小调查上下文

在本 Run 中记录：targetJobId、已解析产品版本、当前有效任务／索引证据、已回读知识、用户补充、待解决缺口和已有产物。

证据引用与用户补充是执行事实；模型的“初步判断”“还想查什么”是推导内容。可以放在工作笔记或简短上下文中，不要求创建第二套可调度的状态机。

对外展示的“读取案例／等待补充／调查状态／核对知识／准备草稿”只是进度标签，不控制权限和终态，也不要求每个标签都走一遍。

### 4.3 支持处理包的三种交付结果

| disposition | 表示什么 | 不能表示什么 |
|---|---|---|
| GUIDANCE | 有证据支持的处理建议 | 已经替客户执行或保证修复 |
| STATUS_EXPLANATION | 能解释快照／观察时的处理进度 | 保证某个时间后完成，或保证客户实际能检索到 |
| ESCALATION | 达到最低调查条件后，整理可供人工继续处理的材料 | 已创建远端工单、已转人工、已确认一个未知根因 |

这些结果从 Run 开始即允许，完成 ESCALATION 不属于模型临时降低要求。但必须满足第 6 节条件，不能用一句“请联系技术人员”跳过调查。

## 5. 核心工作流逐步展开

### 步骤 A：初始化与读取案例

程序先锁定能力、范围和资料快照，建立 Run。模型第一次读取 `readSupportCase`，获得问题正文和已知目标；未读案例就查询业务对象，由工具前置条件拒绝。

首版不把完整案例直接藏进系统 Prompt 后再伪造一次读取成功。可信规则和范围摘要是规则区，真实案例内容是工具观察。

### 步骤 B：绑定目标，读取任务事实

targetJobId 已知则调用 `getImportJob`；未知则提问。查询成功后，程序根据可信结果锁定该任务的产品版本，用于后续知识适用范围过滤。

不机械询问客户已经能从记录核实的版本。若案例里自报版本与任务记录不同，保留差异并说明当前调查针对哪个版本，不能悄悄改写记录。

### 步骤 C：按观察选择调查分支

模型综合状态和问题选择必要工具。具体条件见下一节：解析失败时核对格式；处理成功但不可检索时才核实本任务关联的索引；无法解释时补查或提出合理问题。

工具失败与业务失败必须区分：查询成功且任务状态 FAILED，是可用观察；查询自身超时，不是“已证明导入失败”。

### 步骤 D：核对文档与冲突

`searchKnowledge` 找候选，`readKnowledge` 回读原文后才获得主要结论引用。支持场景按任务产品版本过滤适用资料，不按文档发布日期或相似度自行裁决。

同一适用范围的正式资料仍可能冲突。先有限补查；不能解决时保留两侧依据，按条件生成冲突升级材料，不任选一份假装确定。

### 步骤 E：生成支持处理包

模型调用 `writeSupportPackage`，提交结构化结论、事实／建议与引用、对客草稿和可选升级信息。它不是任意文件写入工具，不能指定路径或对外收件人。

采用一个本地结构化包，而不是分别写三份文件后假定三者天然同版本。程序将内部材料和对客草稿分字段；包整体标为内部使用。对客只能取草稿字段并经人工审核，不能把包含内部引用的完整包直接发送。

### 步骤 F：检查、有限修正、结束

写入前做结构和领域条件检查；不通过则不产出交付物，给具体缺项。写入成功后，模型仍需给出无工具调用的有效文本表示准备结束，Runner 再用相同检查器核验产物、引用及控制边界。

首版只有首次交付尝试与最多一次修正尝试。一次符合输入 Schema 的完整包进入内容校验即计一次，无论校验成功还是失败；首次成功后主动改内容或换证据也计为修正。已存在且当前校验有效的相同内容幂等重提不重复计交付尝试，但仍计工具请求；更换 artifactId、刷新证据或最终检查失败均不增加额度。取消、预算、数据撤回或完整性错误不能靠修正继续。

支持场景的输出适配器根据本次通过最终检查的产物，生成真实位置、辅助交付类型和“尚需人工审核”的固定回执；不直接透传模型最终文本、路径或动作声明。原生模型文本仍保存在受控执行记录中，只表示停止意向，不作为已核实的结果。

因此，即使模型最后写了“已发送／已修复”或引用旧产物，用户也不会收到该未经验证的终结声明。对客候选内容只来自同一通过检查的包中的 customerDraft，仍需人工审核，不能绕过写包检查。

## 6. 决策表：什么证据支持什么结论

下表是本版有限领域条件，由工具与支持检查器落实；不是写进通用 Runner 的业务分支。自然语言表达是否忠实仍需模型评测与人工复核。

| 观察与最低依据 | diagnosisCode／交付类型 | 合理行动与限制 |
|---|---|---|
| 任务 FAILED，错误码 UNSUPPORTED_FORMAT，输入格式和同版本格式说明相符 | FORMAT_UNSUPPORTED／GUIDANCE | 说明上传不等于解析成功，给文档允许的准备方式；不执行转换、重传或删除 |
| 任务 RECEIVED 或 PROCESSING，回读同版本生命周期说明 | IMPORT_IN_PROGRESS／STATUS_EXPLANATION | 说明截至观察时尚未完成；不查询一个尚不存在的索引，不承诺完成时点 |
| 任务 SUCCEEDED，关联目标批次处于 QUEUED／BUILDING／AWAITING_PUBLICATION，且尚未服务该批次；有生命周期依据 | INDEX_NOT_PUBLISHED／STATUS_EXPLANATION | 解释处理完成不等于目标内容已可检索，不自动持续轮询 |
| 任务或关联目标批次明确 FAILED，但没有可核实的更深原因；已搜索对应错误并回读适用支持边界说明 | FAILURE_UNEXPLAINED／ESCALATION | 明确失败位置和未知原因，提交已查内容；不猜内存、磁盘或数据库故障 |
| 目标批次 PUBLISHED 且被服务，用户仍陈述无法检索；已询问必要复现信息，回读排查边界说明 | VISIBILITY_UNEXPLAINED／ESCALATION | 说明可见性元数据不能证明实际检索一定正确；本版没有检索复现工具，不扩展到任意查询 |
| 至少两份已回读、同产品版本适用的正式资料发生未解决冲突，相关状态已查询 | DOCUMENT_CONFLICT／ESCALATION | 引用两侧材料并说明矛盾；冲突语义不能仅由“有两个引用”证明 |
| 缺任务标识，或缺可由支持人员补充的复现信息 | 暂不交付 | requestClarification；无法补充必需信息则 STOPPED |
| 无法获得必需知识、任务不存在于可读记录、关键状态 UNKNOWN，或查询不可用 | 暂不交付 | 分别按缺口或工具故障停止；不自动包装成合格升级 |

两个关键限制：

1. **索引整体 READY 不证明当前导入批次已发布。**工具必须针对该导入的版本／批次返回关联状态，不能拿旧索引的可用性支持新内容已可检索。
2. **搜索过不证明排查充分。**搜索记录用于审计，检查器只验证结构化最低条件；查询是否相关、遗漏了哪些现成方案，要由案例答案和人工检查发现。

如果证据既满足明确建议又被模型选成“原因未知”，已知结构化条件应拒绝不必要升级；不能为提高安全表象把所有任务退给人工。

## 7. 工具调用的依赖与批次规则

最小工具目录为 7 个，完整契约见 16：

| 工具 | 主要职责 | 必要前提 |
|---|---|---|
| readSupportCase | 读取当前案例 | Run 已绑定案例范围 |
| getImportJob | 读取目标导入任务 | 案例已读，targetJobId 已锁定 |
| getIndexStatus | 读取该任务对应批次的索引状态 | 本 Run 成功任务证据，任务已 SUCCEEDED，关联信息完整 |
| searchKnowledge | 搜索批准且适用的知识 | 已从成功任务观察锁定产品版本 |
| readKnowledge | 回读搜索命中的原文 | 本 Run 有效 hitId |
| requestClarification | 向支持人员补充询问 | 没有另一个待答问题，尚有澄清额度 |
| writeSupportPackage | 校验并保存处理包 | 对应结论的最低证据成立，且无控制屏障 |

工具目录在 Run 中固定。缺前提就返回结构化错误，不依赖“把某工具从列表藏起来”作为安全措施。

业务查询都串行执行。相互独立且参数已有依据的只读调用可以在同一模型响应中提出，例如任务成功后查询索引与搜索生命周期说明；执行器仍按顺序执行，再完整回填。

不能在同一批里先搜索再猜新的 hitId，或先查询任务再猜 evidenceId。模型没有看见前一步结果时，程序不代填参数。

`requestClarification` 独占批次，沿用 MIXED_CONTROL_BATCH。支持包写入也独占批次，以避免“用旧证据写完，再查到新事实”；混批整批不执行，返回 MIXED_EFFECT_BATCH。该规则来自工具执行策略，不在 Runner 中硬编码工具名称。

callId 仅用于原生消息配对，evidenceId 用于证据引用，artifactId 用于产物定位；三者不能互相代替。

## 8. 证据、时效与最低可交付性

- 案例快照与用户补充只证明“谁陈述了什么”，不能替代任务观察。
- 任务和索引观察绑定同一目标、产品和对应导入批次，SNAPSHOT 下还必须属于相同快照。
- 知识证据绑定集合、来源版本、片段位置和适用产品版本；撤回优先于快照冻结。
- 报告实际使用的证据必须满足条件；Run 中另有正确证据但包未引用，不能补算通过。
- 模型笔记、摘要、Skill 和长期偏好不是故障依据。

当前快照模式允许重现历史时间的样例，因此不使用“距离现在超过 60 秒就作废”的在线规则；产物明确保留 snapshotId 和采样时间。重新读取旧快照不能把时间刷新成现在。

将来在线模式在写前和最终提交前检查有效期，且避免把来自不同任务修订的状态拼成一个瞬时事实。证据变旧时有限重查；变化后重新判断并重写草稿，不能只替换引用编号。具体规则在 16 中定义。

## 9. 预算、错误和取消

本场景先采用小于或等于通用阶段上限的配置，不因为增加领域工具扩大总预算。

| 项目 | 起步限制 |
|---|---:|
| 模型请求 | 16 次，含最终回答和修正 |
| 工具请求 | 30 次，含错误、控制工具、搜索和写入 |
| 单次模型请求 | 60 秒，且不得超过剩余主动时间 |
| 单次外部只读请求 | 10 秒，且不得超过剩余主动时间；本地读取也检查截止时间 |
| 主动处理时间 | 300 秒，等待人工不计入 |
| 澄清 | 最多 2 次成功发起的问题，未批准的本地输入不触发模型继续 |
| 知识搜索 | 最多 6 次，同一问题最多 2 次改写 |
| 同一对象的有效状态查询 | 最多 2 次，含必要重查，不做后台轮询 |
| 交付内容修正 | 最多 1 轮，写前与最终检查共享 |
| 单个模型可见工具结果 | 最多 4 KiB，有界结构而非截断 JSON |

保留第三次连续同工具同参数停止、第三次连续可修正错误停止。若已有第二阶段实现，还保留连续六轮无有效进展规则；引用换 ID 或重复读同一版本不能清零。工具批次先预检总预算，不执行半批后才发现额度不足。

没有隐藏网络重试，也不自动重连或持续等待后台任务完成。超时、拒绝访问、格式错误、业务状态 FAILED 和完整性损坏分别处理，见 16 的错误表。

取消在模型前后、每个工具前和产物发布前检查。在途查询可能已发生，但迟到结果不得启动新动作；跨过文件发布边界的产物如实记账，不声称回滚。后续真正实现第五阶段时，再接操作账本和显式恢复，不从普通 JSONL 日志重放。

## 10. 实现时按什么顺序落地

1. **先做领域工具和夹具，不接模型。**单独验证对象范围、状态含义、索引批次绑定、知识版本和错误分类。
2. **再接原 Runner。**用脚本模型验证原生消息配对、缺参数、错误反馈和唯一执行入口。
3. **跑通一条明确建议链。**案例→任务失败→适用文档→支持处理包，产物与引用可核验。
4. **补信息与可见性分支。**验证澄清原位续跑、处理成功但未发布、失败原因未知、全部状态成功但问题未复现。
5. **补写前检查、最终检查与有限修正。**让伪造证据、不必要升级和对客泄漏样例不能当成功交付。
6. **再跑真实模型和基线对照。**沿用 14 的 RAG／固定流程／Agent 比较，记录成功、失败与人工成本。

初期知识集合很小，searchKnowledge 可用本地关键词实现；不需要先建向量库。第三阶段再把方法提取成受控 Skill，把状态适配接到 MCP；这是更换能力装配和连接方式，不重写工作流。

如果尚未实现通用 writeReport 的解耦，本场景的 writeSupportPackage 使用同一个底层受控产物存储，自己的输入 Schema 和检查器；不修改原销售工具的业务行为，不把支持包改成假销售报告。

**本次完成的是工作流与调用契约设计。下一步实现入口是配套 16 的工具与虚构案例，不是新增客服管理系统。**
