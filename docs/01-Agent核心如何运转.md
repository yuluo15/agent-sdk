# Agent 核心如何运转

本文只讲引擎，不讲企业外围平台，也不绑定某个框架的具体 API。

## 1. 先理解六个概念

| 概念 | 在这个系统里是什么意思 |
|---|---|
| Tool Calling | 模型输出“调用哪个工具、传什么参数”；实际执行由程序负责 |
| Agent Loop | 工具结果回到模型，模型据此选择下一步，循环推进任务 |
| Context Engineering | 每一轮选择、组织、裁剪模型需要的信息，而不是把所有历史全部塞进去 |
| Planning | 对复杂目标维护可调整的计划；计划是工作假设，不是必然正确的流程 |
| Memory | 跨轮或跨任务保留必要信息；当前任务状态与长期记忆不是同一件事 |
| Agent Harness / Runtime | 围绕模型的执行环境：工具、上下文、状态、限制、恢复与观测 |

类似 ReAct 的“决策—行动—观察”循环很适合作为学习入口。我们记录工具选择、输入输出与状态，不要求模型公开隐藏推理，也不把思维链文本当作正确性的证据。

## 2. 谁控制什么

**模型负责选择：**是否还缺信息、该用哪个工具、如何生成参数、是否应该补查、如何组织回答。

**程序负责约束：**工具是否存在、参数是否合法、目录是否越界、是否超预算、结果怎样回填、是否允许继续。

**用户负责目标与关键授权：**说明想得到什么，必要时补充信息或确认有影响的动作。

模型提出的“我已经完成了”不是事实证明；Runner 仍应检查最低交付条件，例如报告是否确实生成、统计结果是否存在。

## 3. 一轮循环做什么

```text
接收目标
  ↓
准备当前上下文和可用工具
  ↓
调用模型
  ├─ 最终回答 → 检查交付条件 → 返回结果
  ├─ 信息不足 → 向用户提问 → 等补充后继续
  └─ 工具请求
       ↓
     校验与执行
       ↓
     记录结果、错误和用量
       ↓
     把结果按对应调用标识加入上下文
       ↓
     检查步数、时间和停止信号
       └─ 未触发停止 → 进入下一轮
```

同一条链路可以完成一轮，也可以完成多轮。第一次实现时可让工具串行执行，看清因果；之后再对无依赖、无冲突的调用做并行优化。

需要避免一个常见错误：**框架已经自动驱动工具循环，你的 Runner 又驱动一次。**必须明确谁是唯一的循环控制者。

## 4. 工具不只是一个函数名

一个工具至少需要：

- 名称：稳定、易区分。
- 描述：做什么、何时用、有哪些限制。
- 输入定义：字段、类型、必填和取值约束。
- 执行函数与返回结构：返回可供下一轮使用的真实结果或可理解错误。

描述和 Schema 会直接影响模型能否正确选工具、填参数，是 Agent 设计的一部分，不是接入完成后的装饰。

以资料分析为例：

| 工具 | 目的 | 设计注意点 |
|---|---|---|
| listWorkspaceFiles | 发现可用文件 | 限定工作目录，不暴露整个磁盘 |
| inspectDataset | 查看列、类型及样例 | 控制返回大小，不一次返回整份 CSV |
| analyzeDataset | 做筛选、分组和统计 | 先提供受限操作，不让模型随意执行代码 |
| readReference | 阅读指标口径或业务说明 | 文件内容是资料，不是可以覆盖系统约束的指令 |
| writeReport | 生成产物 | 只写指定输出目录，默认不覆盖已有文件 |

初期不需要 MCP 才能调用工具。以后可把 MCP 服务提供的工具适配进同一个执行入口，核心循环保持不变。

## 5. 用一个任务看“自主性”在哪里

用户要求：“找出本月销售变化最大的渠道，说明原因，生成报告。”

| 过程 | 得到的观察 | 下一步为什么会改变 |
|---|---|---|
| 列文件、查看字段 | 找到两个月数据，但一个字段叫退款额，一个叫退货额 | 先读口径说明，不能直接相减 |
| 阅读说明 | 两个字段口径一致，但总销售额包含退款 | 确定净销售额计算方式 |
| 分渠道统计 | 某渠道净销售额下降明显 | 再检查订单数、客单价和退款变化 |
| 补充统计 | 发现下降主要来自订单数减少 | 报告可以描述贡献，不能凭空断言“广告效果差” |
| 检查样本 | 本月只有半个月，上月是整月 | 改用可比较区间；没有对应日期数据则询问用户或明确局限 |
| 生成报告 | 保存成功，返回产物标识 | 返回结果与依据，不只说“报告已生成” |

Agent 的价值不是固定执行了六个工具，而是能根据观察调整路线；同样的初始问题，输入情况不同，下一步也可以不同。

程序可以规定“必须有证据、不能改原数据”，但不必写死每一次补查的顺序。

## 6. 上下文怎么组织

第一版只区分三类：

1. **稳定说明**：角色、目标边界、工具使用规则。
2. **当前任务信息**：用户目标、补充条件、近期消息、当前进展。
3. **观察与证据**：工具结果、错误、计算结论和产物引用。

任务变长后再增加：计划摘要、阶段结论和按需读取的工作文件。大结果保存在工作区，模型读取必要片段，而不是每一轮重复发送全部原文。

这里需要区分：

- RAG：从外部资料检索当前需要的知识。
- 任务记忆：当前任务已经确定什么、完成到哪里。
- 长期记忆：跨任务保留的偏好、经验或事实，需要来源和更新规则。

向量库不是 Agent 的必备组件，也不能代替执行状态。第一版没有向量数据库，依然可以是完整的工具型 Agent。

## 7. 第一版怎么避免停留在“碰巧成功一次”

只做与循环直接相关的控制：

- 设置轮数、时间与工具调用预算；重复无进展时停止，而不是继续烧 Token。
- 工具参数错误可反馈给模型修正，但限制修正次数。
- 资料缺失时追问或说明局限，不把缺失补成事实。
- 记录轮次、工具、参数摘要、结果摘要、耗时、错误、模型与任务配置。
- 同一任务重复运行，对比工具选择、产物和失败原因，而不是只看回答是否流畅。
- 用户指定输出目录意味着允许正常生成报告；删除原文件、外发资料等超范围动作默认不开放。

现阶段不开放支付、下单、删库等高风险工具。未来接入真实副作用时，再增加确认、幂等和结果核实，而不是现在先建庞大的审批系统。

## 8. Java 怎么落地最合适

建议 **Java＋Spring AI 做模型和工具接入，主体先采用一个可观察、可控的薄 Runner**。

为了学习，先亲自理解并控制一次“请求模型—执行工具—回填结果”的循环；模型 SDK、协议解析和基础工具适配复用成熟库，不重造全套框架。

后续复杂到需要持久恢复或图编排时，再比较框架提供的运行时与当前薄 Runner，选定一个执行核心，不把两个循环嵌套在一起。

LangChain/LangGraph、Deep Agents 可以作为学习参照，不意味着项目必须改用 Python，也不要求同时引入多套框架。具体版本与 API 在动手实现当阶段再核验和锁定。

这一阶段的成果应该是：**你能清楚解释 Agent 每一轮获得了什么信息、调用了什么工具、为何继续或停止，并且换工具就能处理另一类任务。**
