# Agent SDK 演进建议

日期：2026-10-07。分析基线：当前仓库 `1.1.0-SNAPSHOT` 源码。

> [!NOTE]
> 2026-10-18 更新：具体执行顺序、阶段门与技术选型以 [企业化演进 ADR](18-Agent-SDK企业化演进决策记录-ADR.md) 为准；本文保留 P0~P3 的原则、边界与风险判断，不再作为执行排期依据。

本文固化本轮讨论形成的演进方向，不代表文中的后续能力已经实现，也不构成生产就绪认证。本轮只做源码核对和文档整理，没有重新运行测试、构建或真实模型验证。

配套阅读：[使用场景手册](使用场景手册.md)。本文调整了旧 [17 号路线规划](17-Agent-SDK架构体系与演进路线规划.md)中阶段 3.5、4.0 的定位；旧文档保留作历史方案，不应将其中所有规划和能力宣传直接当作当前承诺。

## 1. 核心结论与产品定位

**把 SDK 做成可靠、受控、易接入、容易被组合调用的单 Agent 执行组件，而不是包办业务编排、任务调度和运维管理的 Agent 平台。**

“单 Agent”不等于只有聊天能力，也不等于只能调用一个工具。一个 Agent 可以完成检索、分析、多轮澄清、工具操作、人工审批和交付物检查。应用还可以创建多个独立 Agent，并自行组织它们的协作。

后续演进遵守三个判断：

1. **每个 Agent 都需要的执行机制，优先沉淀在 SDK。** 例如工具协议、预算、状态、隔离、审批挂起和结果契约。
2. **随业务变化的协作政策，交给应用。** 例如谁分配任务、何时转交专家、失败后是否补偿、哪个人有审批权。
3. **只有部分部署需要的基础设施能力，按需提供接口或独立适配。** 不因为一个应用需要数据库、工作流或监控系统，就让所有使用者承担这些依赖。

不以功能数量衡量成熟度，而以四个问题衡量：新应用是否容易接入、失败是否能解释、危险动作是否受控、版本是否能安全升级。

## 2. 阶段 3.5：移出完整编排，保留可组合能力

原阶段 3.5 将主从委派、隔离和调用链关联放在同一组，实际应拆开。

| 能力 | 推荐归属 | 处理建议 |
| --- | --- | --- |
| Supervisor/Worker、任务拆解、Agent 路由 | 应用或独立编排组件 | 移出 SDK 必经主线 |
| 工作流顺序、分支、并行、补偿和人工节点路由 | 应用或工作流引擎 | 不在 core 内重建通用流程平台 |
| 单个 Agent 的上下文、工具集和运行预算隔离 | SDK | 保留并加固，组合时也需要这些基础 |
| 结果、状态、取消、澄清与审批接口 | SDK | 稳定契约，使外部编排不必读取私有实现 |
| 跨调用关联标识、事件扩展 | SDK 接口与应用协作 | 可支持追踪，但不因此引入调度器 |
| 父子任务关系、总预算和失败传播规则 | 应用 | 根据业务语义制定，不能只靠子 Agent 自己控制 |

### 为什么由应用编排是合理的

例如一个业务流程可以是：

```text
应用编排服务
  → 诊断 Agent 分析问题
  → 应用依据诊断结果及业务规则选择下一步
  → 方案 Agent 生成建议
  → 可信审批服务确认权限与操作范围
  → 业务服务执行并记录回执
```

每个 Agent 的内部模型—工具循环仍由 SDK 管理；外层只协调任务，并未重复实现内核。应用可以使用普通 Java 服务，也可以按自身需要接入已有工作流系统。

当前 SDK 已提供创建独立 Runner 及执行、查询、取消、澄清、批准、拒绝等入口，具备被上层组合的基础，但并不等于已提供完整跨 Agent 执行语义。

### 不要将组合简化为几个同步方法调用

子 Agent 可能返回 WAITING_INPUT 或 WAITING_APPROVAL，这不是任务完成。应用还需要决定父任务如何等待、回答和审批如何路由、总预算如何累计、取消如何传播、权限如何收窄。

因此，不能通用地把“调用子 Agent”包装成一个普通同步工具，再把其等待状态当作工具成功。先在实际应用中验证组合方式；只有多个应用出现稳定共性，再考虑独立、可选的编排组件。

**SDK 可以支持被编排，但不必拥有编排决策。**

## 3. 阶段 4.0：按层拆分，不整体删除

### 3.1 四种不同的保存与恢复

| 能力 | 解决的问题 | 推荐归属 |
| --- | --- | --- |
| 对话记忆持久化 | 新一轮对话能读到历史文本和偏好 | SDK 记忆接口＋可选存储实现 |
| 任务历史归档 | 以后可以查询结果、状态、产物和审计记录 | 应用归档服务／存储适配层 |
| 单 Agent 检查点与恢复 | 重启后继续同一个未完成 Run | SDK 定义执行语义，适配层负责存储 |
| 多节点任务接管 | 哪个节点领取、执行和接管任务 | 应用运行平台／调度系统 |

当前已有文件对话记忆实现，不等于已有运行级检查点。`RunSnapshot` 是公开观察视图，不是全部内部状态；Runner 仍明确不支持进程重启恢复。

例如，磁盘里保留“用户希望退款”的聊天记录，不能证明某笔退款是否已批准、是否已提交、是否只丢失了回执。重新发送对话让模型再做一遍，不叫安全续跑。

### 3.2 真正的检查点为什么需要 SDK 参与

内核掌握待处理工具 callId、待审批批次及位置、错误与重复调用计数、累计预算、模型会话和工作区索引等状态。要求应用自行推断并恢复这些信息，会迫使应用复制私有状态机，破坏 SDK 的复用和升级价值。

合理分工是：

> SDK 规定什么时机、什么状态可以安全保存和恢复；应用决定保存在哪里、由哪个节点恢复、何时恢复。

以后若需要该能力，先明确以下契约，再决定是否增加存储模块：

- 允许保存的安全边界，例如没有外部动作正在提交时的受控等待点，而非任意一行代码。
- 检查点版本、场景及工具版本、模型会话格式和必要元数据。
- 未完成工具调用、审批绑定、预算与事件序号的一致性。
- 外溢文件、证据和产物是否仍可访问；临时资源保留与恢复策略。
- 恢复时如何重新验证权限、取消状态、审批有效性及过期条件。
- 不支持恢复的模型或资源适配器如何明确拒绝，而不是假装成功。

不应直接序列化活动 Java 对象、线程、网络连接或业务服务实例。仅增加 `RunRepository` 保存 `RunSnapshot`，不足以实现断点续跑。

### 3.3 高可用与业务一致性仍属于更上层

租约、任务所有权、防止旧执行者继续提交的机制、故障接管、队列和调度，属于运行平台。分布式锁不自动提供排队、公平性、权限隔离或业务幂等。

外部写操作必须另有业务幂等键、提交回执和查询对账。进程可能在业务系统已提交、SDK 尚未记录结果时退出；此时不能根据本地缺少完成记录就重放操作，也不能承诺任意外部动作 exactly-once。

监控同样需要分层：SDK 提供事件和指标接入能力，可选模块对接观测系统；收集器、告警、大盘、审计检索和运维账号不属于 core。

## 4. 是否需要持久续跑，由业务承诺决定

| 实际业务 | 建议 |
| --- | --- |
| 短时、只读问答，用户可以重新提问 | 可以暂不做 Run 恢复，但要明确失败与重试入口 |
| 需要跨轮次记住聊天内容 | 对话持久化可能足够，不必立即建设检查点 |
| 审批等待数小时或跨部署窗口 | 若承诺重启后仍继续原审批，需提前建设相关持久状态与恢复机制 |
| 长任务且重做成本高 | 评估检查点收益，限定先支持的恢复边界 |
| 涉及订单、退款或其他写入 | 首先落实幂等、回执及不确定结果处理；检查点不能替代它们 |
| 多实例需要接管在途任务 | 检查点与上层任务所有权机制共同设计，不能只增加副本数 |

**服务恢复接收新请求，不等于原有任务无损恢复。**

不具备持久续跑的版本仍可用于边界明确的商用场景，但必须明确重启行为和人工处置；不能在合同、文档或界面上承诺不存在的连续性。已有真实需求时，恢复可以提前，不必机械等待路线末尾。

## 5. 当前最值得优先核对的问题

以下是源码静态核对事实及验证建议，不是本轮已经修复的清单。

| 项目 | 已见事实 | 优先行动 |
| --- | --- | --- |
| 文档与版本 | 根 POM 为 1.1.0-SNAPSHOT；根使用手册仍标 0.0.1-SNAPSHOT，部分能力描述滞后 | 建立一致的版本、支持范围与能力矩阵 |
| 流式声明 | 内置 Spring AI 适配器先获得完整响应，再回调整段文本 | 区分事件回调与真实增量生成；按需求实现或收窄声明 |
| 拒批与批次闭合 | 拒批后的剩余调用只记跳过事件，适配器却要求全部 pending 调用有结果才能继续 | 编写定向测试，确定协议闭合与后续执行规则 |
| 回调故障 | 监听器直接进入执行路径，首次状态通知位于 drive 的 try 之前 | 明确观察回调异常、断连与执行生命周期的关系 |
| 文件记忆可靠性 | 文件记忆读写异常存在忽略路径 | 明确记忆是尽力保存还是可靠保存，让调用方能识别失败 |
| 等待期清理 | 有 prune 和等待超时机制，不等于宿主已配置后台清理调度 | 明确触发方式、上层调度和容量测试 |
| 会话隔离 | Factory 返回独立 Runner，但默认共享可配置模型、工具、事件和记忆依赖 | 验证身份命名空间、共享对象线程安全和请求路由 |

不应因列出了这些核对点就全面重写内核。先建立失败用例，再做最小修复；没有证据的扩展不进入本轮范围。

## 6. 建议的新演进主线

### P0：能力真实性与版本基线

**目标：让开发者明确知道这个版本能做什么。**

- 统一使用手册、变更日志、示例和实际接口，明确已实现、受限实现、应用提供和未实现能力。
- 清理无法证明的“金融级”“永不遗忘”“精确预算”“全协议兼容”等绝对性承诺。
- 明确 Java、Spring、模型供应商及 MCP 协议/传输支持范围。
- 固定消费者视角测试，从发布制品接入，而不只在源码 reactor 内验证。
- 定义不可变发布版本、兼容性与迁移规则；开发快照不能替代可追溯交付。

**验收：** 对外承诺都有源码、测试或受控验证依据；示例与支持版本一致；升级影响可说明。

### P1：单 Agent 可靠性与安全加固

**目标：已有功能在失败、取消、审批和边界输入下仍然可信。**

- 优先复现并修复第 5 节的协议和生命周期问题。
- 验证批准/拒绝/取消/目标修订之间的竞争及过期审批；权限依然由服务端判断。
- 验证压缩后的上下文不会把失败误表述为成功，不丢失待处理工具关系和关键证据约束。
- 验证等待过期、历史清理、工具超时、回调异常和资源释放。
- 验证共享记忆、工作区和 MCP 工具的租户边界；明确写操作幂等与真实回执责任。
- 建立正常路径、故障注入和有限容量测试，按场景定义质量与成本门槛。

**验收：** 失败路径可预测；不串会话、不伪造成功；取消不被误解为回滚；关键业务动作不会因 SDK 的恢复或重试策略被盲目重放。

### P2：快速接入与可组合性

**目标：第二个应用不需要复制 SDK 内核，也不必接受 SDK 的业务流程模型。**

- 稳定结果、状态、错误和事件契约，说明等待、终态、背压及取消语义。
- 完善声明式工具与场景构建示例，尤其明确完成检查不能默认代表业务成功。
- 按真实需要实现增量模型输出，或继续明确标注整段输出；不要把 SSE 包装当作模型流式已经实现。
- 在应用层验证两个独立 Runner 的顺序调用、等待路由和失败处理，形成可参考接法，不新增通用编排引擎。
- 检查适配器不支持的扩展能力是否明确报错，避免公共接口无声忽略调用方意图。

**验收：** 新场景主要新增业务工具、配置和完成检查；上层能正确识别结果与等待状态；不依赖 Runner 的私有字段。

### P3：商用运维与交付

**目标：能定位故障、评估容量与成本、支持客户升级。**

- 按需求提供可选指标和追踪适配；控制标签数量，避免把用户问题、密钥、runId 当作无限增长的指标标签。
- 分开度量模型执行、工具执行、排队和等待用户的时间；usage 缺失保持未知。
- 使用授权数据验证真实模型和实际 MCP Server，记录协议与能力边界，不以本地 mock 代替生产接入证据。
- 补充漏洞、许可证、依赖物料清单、发布和迁移流程。
- 为目标部署做容量、长期资源稳定性与优雅关闭验证，并明确未支持的恢复场景。

**验收：** 出现常见故障能用脱敏信息定位；版本和依赖可追溯；承诺的部署规模、业务质量与费用有测试依据。

### 按需分支：单 Agent 持久续跑

启动条件是明确的客户需求和恢复承诺，而不是“路线图必须有下一阶段”。

先限定可恢复状态和模型/资源范围，再定义检查点格式，之后才实现存储适配和恢复入口。验收覆盖恢复后预算累计、审批有效性、工具结果完整性、版本不兼容拒绝、缺失资源，以及外部提交结果不确定时的人工或自动对账。

跨节点调度、工作流和高可用接管作为上层项目独立推进，不成为所有 SDK 用户的必选依赖。

## 7. 每次迭代如何落地

每次只选择一组目标，在实施前说明：

1. 当前哪个应用遇到了什么真实问题。
2. 问题属于 SDK 机制、适配器还是业务政策。
3. 最小改动及影响的公开契约。
4. 正常和失败路径的验收方法。
5. 升级、回退及必要的数据兼容处理。

先做 P0、P1，再根据接入反馈推进 P2、P3。业务评测从少量高价值案例开始，持续加入实际失败样本，不追求一次搭建庞大评测平台。验证发现的问题优先修复，不用新增特性掩盖已有契约缺口。

## 9. 一句话总结

**移出完整多 Agent 编排和高可用平台，保留可靠的单 Agent 内核；先兑现现有能力，再按真实需求提供可组合接口和可选的持久执行能力。**
