# Agent SDK 企业化演进决策记录（ADR-018）

- 状态：已接受（Accepted）
- 决策日期：2026-10-18
- 适用范围：Agent SDK `1.2.0` ~ `2.0.0`
- 决策者：用户（业务目标与最终拍板）
- 实现负责人：编码 AI（按本 ADR 与后续子 ADR 实施）
- 替代：此前“P4–P7 功能优先”讨论稿（未采纳）
- 配套文档：[Phase 0 评测设计](19-Phase-0-评测设计.md)

> 本文是执行决策，不是能力宣传。文中“已有”指当前源码可验证；“计划”指尚未实现；“应用负责”指 SDK 不承诺内置。

---

## 1. 背景与问题

当前 SDK 已具备扎实的单 Agent 执行内核：

- 确定性 ReAct 循环、状态机、运行预算、澄清与 HITL 审批；
- 工具 JSON Schema 校验、超大结果工作区外溢；
- 记忆、目标修订、完成检查、流式事件、运行指标；
- MCP 工具桥接与 Skills；
- Spring Boot 自动装配与样例应用。

但对照企业试点门槛，仍有四个结构性缺口：

1. **没有真实场景证据**：现有测试主要验证机制，不证明真实业务任务正确。
2. **没有信任边界**：`RunRequest` / `ToolContext` 缺少租户、主体、权限、trace 等可信上下文；审批未绑定审批人和参数版本。
3. **协议代际落后**：MCP 仍为 `2024-11-05`，仅有 stdio/in-memory；没有 A2A/AG-UI 适配。
4. **可运营能力不足**：没有 OTel GenAI 链路、成本预算、稳定错误分类、会话配额与检查点恢复。

此前存在两条路线争论：

- **功能优先**：先做持久化、Handoffs、Workflow、Guardrails、Tool RAG、OTel；
- **企业门禁优先**：先做真实试点与评测，再补信任边界与可观测，最后做持久化与生态互操作。

本 ADR 选择后者，并明确：**先证据、后能力；先信任、后自治；先标准、后厂商；先单 Agent、后编排。**

---

## 2. 决策摘要

1. **定位不变**：SDK 是单 Agent 确定性执行引擎，不是多 Agent 编排平台、工作流引擎或 Agent 平台。
2. **当前目标**：企业内部试点（Enterprise Pilot Ready），首个场景为 IT 技术支持只读排障。
3. **执行顺序**：Phase 0 试点与评测 → Phase 1 信任边界 → Phase 2 可运营 → Phase 3 协议与互操作 → Phase 4 持久化与规模化（按需）。
4. **内核纯净**：`agent-core` 只增加必要 SPI/契约；存储、遥测、策略引擎、协议适配、评测实现进入可选模块。
5. **先只读、后写入**：Phase 0 不开放写工具；身份、策略、审批绑定、审计完成前，不接真实写操作。
6. **协议策略**：MCP 以 `2025-11-25` 稳定版为目标；`2026-07-28` 单独评估；A2A/AG-UI 以可选适配器提供；不自造前端/工具协议。
7. **可观测标准**：采用 OpenTelemetry GenAI 语义约定，锁定 semconv 版本；内容采集默认关闭，开启时必须脱敏。
8. **持久化审慎**：检查点放在 Phase 4；不做“分布式事务”承诺，不以 Redis TTL 作为审批真相源；外部写操作必须有幂等键、回执和对账。
9. **多 Agent/工作流不进 core**：Handoffs、Workflow、Tool RAG、输入/输出护栏分类器按真实需求做成独立模块或产品。
10. **阶段门**：每个阶段有验收证据和退出条件；没有证据不进入下一阶段。

## 3. 选项对比

| 选项 | 内容 | 优点 | 致命问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. 功能优先 | 先做 P4 持久化、P5 Handoffs/Workflow、P6 Guardrails/Tool RAG、P7 OTel | 功能亮眼，贴近业界热词 | 没有真实证据；多 Agent 侵入 core；检查点设计不足；OTel 太晚 | 拒绝 |
| B. 平台优先 | SDK 内置运行时、网关、身份、记忆、调度、沙箱 | 一站式 | 与“轻量 SDK”定位冲突；依赖重；维护成本高 | 拒绝 |
| C. 企业门禁优先 | 试点/评测 → 信任边界 → 可运营 → 协议 → 持久化 | 证据驱动；边界清楚；可回退 | 前期功能感不强 | **采用** |
| D. 只整理文档 | 只对齐文档，不做试点 | 成本最低 | 无法证明任何企业能力 | 拒绝 |

## 4. 边界：SDK、宿主与可选模块

| 能力 | SDK 负责 | 宿主/平台负责 | 可选模块 |
| --- | --- | --- | --- |
| 执行循环 | ReAct、状态机、预算、取消、澄清 | 任务调度、队列、优先级 | — |
| 身份 | 接收并传递可信上下文；禁止模型提供身份 | IdP、登录、租户、权限来源 | `agent-policy` |
| 工具授权 | 工具契约、策略 SPI、审批绑定 | 业务授权规则、审批人组织关系 | OPA/Cedar 适配 |
| 工具接入 | MCP 客户端、工具适配、结果防护 | MCP Server 运维、网络与凭据 | 远程传输/网关适配 |
| 记忆 | 记忆 SPI、会话内历史 | 长期存储、向量库、知识库 | JDBC/Redis/Vector 适配 |
| 可观测 | 事件契约、OTel instrumentation | Collector、Jaeger/Tempo、告警 | `agent-otel` |
| 评测 | 评测 SPI、轨迹断言契约 | 评测数据授权、业务验收 | `agent-eval` |
| 持久化 | 检查点契约、恢复语义 | 数据库/对象存储运维 | JDBC/Redis 存储适配 |
| 多 Agent | 单 Agent 可被调用 | 路由、交接、补偿、人工节点 | `agent-a2a-adapter`、独立编排模块 |
| 前端 | 流式事件契约 | 页面、会话、交互 | `agent-agui-adapter` |

**红线**：模型输出、工具返回、检索内容都不能成为身份或权限依据；授权必须在服务端和工具执行前完成。

## 5. 阶段路线与阶段门

### Phase 0：试点与评测证据（2–3 周）

**目标**：用真实只读数据证明 SDK 能完成任务，并建立可复现的评测基线。

交付：

- IT 技术支持只读场景（`lookupTicket`、`searchKnowledgeBase`、`analyzeSystemLogs`）；
- 30–50 条评测用例，覆盖正常、缺参、无证据、权限不足、工具失败、长上下文、Prompt 注入等；
- `agent-eval` 评测骨架：确定性回放 + 真实模型、轨迹断言、证据/产物断言、成本/时延统计；
- 安全负向测试与基线报告；
- 文档/版本/能力矩阵对齐。

退出条件：

- 评测可复现，模型/Prompt/工具 schema/数据集版本齐全；
- 禁止工具被实际执行 0 次；未处置的 P0 安全失败为 0（越权、敏感数据泄露、审批绕过等）；已处置的失败保留在报告；
- 失败案例可分类、可复现；
- 输出 go/no-go 结论。

**不通过则**：缩小场景、修复数据接入或评测设计，重跑；不得进入 Phase 1。

### Phase 1：信任边界（3–5 周）

**目标**：让 SDK 能安全接入真实只读系统，并为未来写操作打基础。

交付：

- `TrustedContext`：tenant、user principal、agent identity、scopes、traceId、requestId、delegation；
- `ToolPolicy` SPI：ALLOW / DENY / REQUIRE_APPROVAL / REDACT，before/after，策略版本与审计；
- 工具语义：readOnly / destructive / idempotent / openWorld、outputSchema、timeout、idempotencyKey；
- 审批绑定：审批人身份/角色、参数规范化 Hash、策略版本、TTL、单次使用、执行前复核、批量语义；
- 审计 sink：谁在何时基于什么策略批准/拒绝了什么；
- MCP 安全基线：工具定义 pin/diff、描述清洗、禁止 token passthrough、凭据隔离；
- 写操作结果语义：`UNKNOWN_OUTCOME` 的兼容设计与对账契约（本阶段只定义，不开放写工具）。

退出条件：

- 跨租户、越权工具、审批重放、参数篡改、过期审批测试通过；
- 审计记录可回答“谁批准了什么、基于什么参数”；
- 旧消费者兼容测试通过。

### Phase 2：可运营（3–4 周）

**目标**：能定位故障、评估成本、做质量回归。

交付：

- OTel GenAI：`invoke_agent` / `chat` / `execute_tool` span，W3C traceparent，内容采集默认关闭；
- 事件 schema v1：版本号、traceId、tenant 哈希、事件回放（仅诊断）；
- 成本与用量：价格表版本化、usage 归一、单 Run/会话/租户预算；
- 错误分类与重试边界：配置、模型、工具、策略、上下文、存储、取消、预算；
- 评测进入 CI：确定性套件阻断、真实模型套件定期、负载与故障注入。

退出条件：

- 每次 Run 有完整 trace；
- 成本报告可对账；
- CI 能区分引擎回归、模型变化、业务工具问题。

### Phase 3：协议与互操作（4–6 周）

**目标**：从“能接自己的工具”到“能被企业生态接入”。

交付：

- MCP `2025-11-25` 稳定版：Streamable HTTP、OAuth 2.1/PKCE、tasks（实验）、elicitation、resources/prompts、JSON Schema 2020-12；
- 为 `2026-07-28` 预留无状态核心、`Mcp-Method/Mcp-Name`、CIMD/RFC 9207、MRTR 的传输抽象；
- A2A v1.0 适配：Agent Card、签名身份、任务生命周期、多租户；
- AG-UI 适配：`RunStreamChunk` 映射为标准前端事件；
- 模型适配：Anthropic/Gemini/Azure/Bedrock/Ollama；能力矩阵、结构化输出、多模态、prompt caching；
- 并行只读工具调用。

退出条件：

- MCP 互操作/一致性测试通过；
- 两个独立 Agent 通过 A2A 完成一次跨进程协作；
- 一个前端通过 AG-UI 正常展示流式与等待状态；
- 供应商能力矩阵有测试证据。

### Phase 4：持久化与规模化（按需，4–6 周）

**触发条件**：真实试点出现“审批等待跨部署窗口”“长任务重启恢复”“多租户配额/排队”需求。

交付：

- Checkpoint/resume：完整内部状态、安全保存点、版本校验、权限复核、身份快照、未完成审批批次、预算累计；
- `CheckpointStore` SPI：JDBC 优先；Redis 仅缓存；乐观并发/版本栅栏；
- 外部写操作：幂等键 + 回执 + 对账，明确“结果未知”，不自动重放；
- 会话治理可选 Starter：租户/用户/会话映射、队列、配额、等待 TTL、保留期、优雅关闭；
- 沙箱 SPI：代码执行/浏览器工具的 microVM/容器适配；
- 发布：BOM、消费者兼容测试、Javadoc、SBOM、迁移说明。

退出条件：

- 重启恢复测试通过；
- 超额/排队行为可预测；
- 多租户隔离测试通过；
- 沙箱基础测试通过。

### Phase 5（可选，独立产品，不进 core）

只有当两个以上真实应用证明“单 Agent + 应用层组合”不足时，才考虑：

- Handoffs / 多 Agent 编排；
- 轻量 Workflow；
- Tool RAG；
- 输入/输出护栏分类器。

优先通过 A2A 或宿主应用编排实现；不得在 `agent-core` 内重建 Swarm/工作流平台。

## 6. 关键设计决策

### 6.1 可信上下文

- `TrustedContext` 由宿主注入，不可由模型/用户文本生成；
- 区分 `agentIdentity`（工作负载身份）与 `userPrincipal`（委托用户）；
- 支持 on-behalf-of / token exchange 的语义，但 **不把 raw token 放进 ToolContext**；
- tenant 命名空间贯穿 memory、workspace、tool catalog、事件与日志。

### 6.2 工具策略与审批

- 策略在工具执行前判定，默认拒绝未授权工具；
- 审批绑定：审批人、角色、参数规范化 Hash、策略版本、有效期、单次使用；
- 执行前重新校验参数与权限；参数变化后旧审批失效；
- 批量审批需明确“逐调用”还是“整批”语义；
- 审计事件 append-only，包含决策理由与策略版本。

### 6.3 结果未知

- `ToolOutcome` 保持向后兼容；新增“不确定结果”通过独立类型/默认处理实现，避免破坏 sealed interface 的消费者；
- 写工具必须返回业务回执；超时/断连时先查询/对账，不盲目重试；
- 明确“取消不撤销已提交动作”。

### 6.4 检查点

- 不把 `RunSnapshot` 当内部状态；定义独立 `RunCheckpoint`；
- 保存点至少覆盖：模型响应后、工具结果后、等待态；
- 保存内容至少包括：待处理 callId/审批批次、预算计数、模型会话原生消息、计划/目标版本、工作区引用、场景/工具/策略版本、身份快照、事件序号；
- 恢复前校验版本、权限、审批有效性；
- 不支持恢复的适配器必须明确拒绝，不能“假装成功”；
- 不做分布式事务承诺；使用乐观并发与 fencing。

### 6.5 可观测与评测

- 锁定 OTel GenAI semconv 版本；span 以 `invoke_agent` / `chat` / `execute_tool` 为骨架；
- trace context 从宿主传入，跨异步/工具/MCP 传播；
- 内容采集默认关闭；开启时脱敏并控制保留期；
- 评测分两层：确定性回放（CI 阻断）+ 真实模型（定期/人工）；
- 回放只用于同版本回归；Prompt、模型或工具 schema 变化时旧录像失效，必须重跑真实模型，不能用旧录像代替新结果；
- 证据断言使用结构化 Evidence ID，并交叉校验 `RunSnapshot.observations` / workspace artifacts，不能只做文本包含；
- 安全关键断言使用确定性规则，LLM-as-judge 只能辅助。

### 6.6 协议策略

- MCP：先稳定版 `2025-11-25`，再评估 `2026-07-28`；传输层抽象，避免协议变更侵入 core；
- A2A：只做“可被编排”，不做编排器；
- AG-UI：只做事件映射，不做前端框架；
- 所有协议适配必须有 conformance/互操作测试。

### 6.7 兼容与发布

- core 新契约优先使用默认方法、重载构造、可选字段；
- 建立消费者视角测试，从制品仓库解析 SDK；
- 固定版本、BOM、迁移说明、SBOM、弃用策略；
- 不兼容变更必须升级主/次版本并给出迁移步骤。

## 7. 技术雷达

| 档位 | 技术 | 说明 |
| --- | --- | --- |
| **Adopt** | 单 Agent 确定性循环、JSON Schema 校验、HITL 审批、工作区外溢、OTel GenAI（锁定版本）、W3C traceparent | 已在用或 Phase 1–2 落地 |
| **Trial** | MCP `2025-11-25`、A2A v1.0、AG-UI、OPA/Cedar、Tool Selector | 有明确场景后试点 |
| **Assess** | MCP `2026-07-28`、microVM/容器沙箱、持久执行框架、多 Agent Handoffs | 观察规范与生态成熟度 |
| **Hold** | 把 Workflow/Swarm 放进 core、Redis 作为审批真相源、隐藏自动重试、自造前端/工具协议、无证据的“金融级”承诺 | 不作为默认方案 |

技术雷达每季度复核一次；跨档需要新的 ADR。

## 8. 风险登记册

| 风险 | 触发信号 | 影响 | 缓解 | 负责人 |
| --- | --- | --- | --- | --- |
| 真实数据接入延迟 | 接口授权/脱敏未完成 | Phase 0 无法证明真实价值 | 合成数据先搭框架；并行推进授权；退出前至少接一个真实只读端口 | 用户 |
| 密钥/凭据泄露 | 配置含默认密钥、日志出现敏感串 | 安全事件 | 立即轮换；移除默认值；secret scanning；最小权限 | 用户 + 编码 AI |
| 范围蔓延 | 又回到 Handoffs/Workflow/平台化 | 周期失控 | 以本 ADR 的 non-goals 阻断；新需求先写 ADR | 我 |
| 评测过拟合 | 只针对 30 个 case 调 Prompt | 真实场景退化 | 留出 hold-out；多轮真实模型；版本化数据集 | 我 |
| 协议追赶 | MCP/A2A 规范快速变化 | 返工 | 传输/协议抽象；稳定版优先；conformance 测试 | 我 + 编码 AI |
| 检查点假安全 | 只存快照、不校验外部写 | 重复提交/丢单 | 幂等键、回执、对账；恢复测试；明确 unknown | 我 |
| 单人维护容量 | 阶段过多、并行推进 | 质量下降 | 一次只做一个阶段；阶段门；砍功能 | 用户 |
| 成本黑盒 | usage 缺失、价格表过期 | 预算失控 | usage 归一；价格版本；单 Run/租户预算 | 我 |

## 9. 明确不做

- 不在 `agent-core` 内置多 Agent Supervisor、Swarm、Workflow 引擎；
- 不在 core 内置向量数据库、MCP 网关、IdP、UI、调度平台；
- 不把 `RiskLevel` 扩成完整策略引擎；
- 不对写操作做隐藏自动重试；
- 不用测试数量或演示成功替代业务评测；
- 不在没有真实需求时提前做 checkpoint/分布式/多模态；
- 不对外承诺“金融级/永不遗忘/精确预算”等无法证明的能力。

## 10. 复盘与变更

- 每两周一次方案复盘：目标、证据、风险、下一步；
- 每个 Phase 结束提交一页 go/no-go 备忘；
- 架构变更必须先改 ADR，再改代码；
- 文档以本 ADR、Phase 0 评测设计、使用场景手册、使用手册为准；历史文档不作为当前承诺。
