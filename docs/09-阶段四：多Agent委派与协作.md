# 阶段四：多 Agent 委派与协作

版本：v0.1 · 第四阶段详细设计  
交付：仅方案，不编写或修改项目代码，不假定前三阶段已实现。  
配套：[10-阶段四：协作实验、对照与验收](10-阶段四：协作实验、对照与验收.md)

## 1. 先回答：为什么要增加 Agent

前三阶段已经有工具、计划、工作区、知识、Skills 和 MCP。第四阶段不是把这些组件各改名为一个 Agent，而是研究一个问题：

> 当任务可以分成相对独立、需要不同上下文的子问题时，让几个有自己执行循环的 Agent 分工，是否比一个 Agent 更有效？

可能的收益是隔离冗长研究过程、并行获取独立依据、减少主模型同时处理的无关信息。代价是委派说明、重复读取、结果汇总、通信损失和更多模型调用；拆分不当会让原本简单的任务更难。

| 情况 | 优先选择 |
|---|---|
| 单个确定查询、计算或格式转换 | 普通工具，不创建子 Agent |
| 同一目标、短上下文、步骤强依赖 | 单 Agent＋计划 |
| 两块可独立研究、结果可明确交接 | 可以试验子 Agent |
| 多人共同写同一可变文件、紧密共享中间状态 | 本阶段不并行拆分 |
| 仅仅希望“多一个模型更可信” | 先改善工具和检查，不以投票代替证据 |

**多 Agent 是可选进阶，不是进入第五阶段的资格证明。** 如果对照实验没有收益，可以保留委派实验，正式运行仍使用单 Agent。

## 2. 首版只采用一种协作结构

```text
用户目标 / TaskBrief
          ↓
主 Agent（Supervisor）
  自己理解目标、计划、决定是否委派
          │
          └─ delegateTasks：一次提交 1—2 个独立子任务
                    │
          ┌─────────┴──────────┐
          ↓                    ↓
数据分析子 Agent          资料研究子 Agent
独立模型会话              独立模型会话
受限工具＋自己的循环       受限工具＋自己的循环
          │                    │
          └──── 结构化结果＋证据 ┘
                       ↓
              主 Agent 核查、补查、汇总
                       ↓
           主任务 CompletionCheck → 用户产物
```

- 一个本地 Java 进程，一次只运行一个用户根任务。
- 同时最多两个子任务；委派深度最多一层，子 Agent 不能再委派。
- 子 Agent 不互相发消息、不直接读对方工作目录、不直接与用户对话。
- 主 Agent 在等待这一批结果时不另开模型请求；首版不实现边运行边收消息的后台助手。
- 只有主 Agent 生成用户交付报告；子 Agent 只写自己的受控工作项。
- 不引入 A2A、消息队列、分布式锁、企业身份系统或崩溃恢复。

三个角色可以使用同一个模型。角色差异首先来自任务、上下文、工具和结果契约，不要求三套模型供应商，也不要求三份业务实现。

## 3. 谁拥有执行循环

“Runner 是唯一循环控制者”在这里指：**每个 Agent 实例的模型—工具循环，都只能由同一套 Runner 实现控制。** 不再限制整个进程只能存在一个运行实例。

主 Agent 和子 Agent 各有自己的运行状态、ModelSession、原生消息和 callId 空间。子 Agent 是真正可以连续观察、补查的 Agent，不是固定调用一次模型的函数；但一个确定统计仍由 analyzeDataset 工具完成。

增加一个小型本地协调组件，负责创建子任务、预算预留、取消传播和汇聚。它不替模型决定分析步骤，也不另写第二套模型循环。

建议执行所有权：

- 根任务 Coordinator 串行处理委派登记、子任务结果、用户取消、目标修订和最终提交。
- 每个 Runner 实例串行处理自己的模型响应、工具批次和状态。
- 不同子任务可以并行；一个子任务内部仍按已有规则串行执行工具。
- 子任务通过事件/完成信号交回结果，不直接修改父状态。
- 等待子任务不能占住执行子任务所需的唯一线程；用有界执行器和完成回调，不在同一单线程池里提交后阻塞等待。

Java 21 的并发能力足以承载该结构，但虚拟线程不等于无限并发，也不自动解决共享状态、取消或模型限流。本阶段不强制引入图框架或预览 API。

## 4. 对前三阶段契约的显式调整

| 原约束 | 本阶段改变 | 仍不改变 |
|---|---|---|
| 一个活跃 Run | 一个根 Run，最多两个活跃子 Run | 一次一个用户任务，不是多租户调度平台 |
| 每 Run 单个 Skill | 每个实例各固定一个受控 Skill/角色配置 | 模型不能动态安装、切换或授予工具 |
| 证据只在当前 Run 有效 | 增加父子间受控导入并重新绑定的通道 | 不接受任意其他 Run 的引用 |
| 每 Run 独享调用额度 | 根任务树共享总额，子任务有子额度 | 创建子任务不产生免费预算 |
| 一个 Worker 推进所有状态 | 每实例串行，根协调器串行处理跨实例边界 | 不允许多个线程直接改同一状态 |
| 等待用户再继续原 Run | 只有主 Agent 可等待用户；子任务缺信息就交回 | 本阶段不保存可重启的子任务检查点 |

已有输入变化、来源撤回、工具目录停用、原生消息配对、报告目标版本和有限修正规则继续有效。下面的父子通道是新增契约，不能简单关闭旧的跨 Run 校验来实现共享。

## 5. 委派前先明确共同前提

父目标中的日期、指标口径、允许资料和交付要求，不能让两个子 Agent 各自猜一套。

以销售样例为例：先由主 Agent 查清适用窗口、净额单次扣减规则和退款字段映射；再并行委派：

1. 数据分支：按已确认口径计算渠道变化。
2. 资料分支：确认结论适用范围、背景说法与缺少的因果依据。

如果计算必须等资料分支确认口径，这两个步骤就是有依赖，不应为了展示并行而同时开始。可先派资料任务、拿到依据后再派计算任务，也可由主 Agent 自己完成前置核查。

主 Agent 可以通过计划描述依赖，不需要本阶段再设计通用 DAG 调度器。模型决定是否委派及任务内容，程序只允许在明确边界内执行。

## 6. 最小委派契约

### 6.1 delegateTasks 是一个根任务控制工具

只在主 Agent 中注册，输入为当前 expectedGoalVersion 和 tasks 数组，数组长度 1—2。每项允许：

| 输入 | 含义 |
|---|---|
| taskKey | 根任务内的逻辑事项，如 channel_comparison、limitations_review |
| agentType | 从预先批准的角色模板中选择，不是类名或远端地址 |
| objective | 清楚、简短的子目标 |
| scope | 当前任务 Schema 允许的日期、分组、资料子集等结构化范围 |
| inputRefs | 父任务已登记且允许下发的资料/证据/用户确认引用 |
| expectedFindings | 要返回的结果种类和待回答问题，不得修改根交付要求 |
| previousSubtaskId | 可选；明确补做时指向之前的子任务，并附补做理由 |

程序填写 rootRunId、parentRunId、childRunId、subtaskId、父 goalVersion、委派契约摘要、能力快照和预算。模型不能传工作根目录、模型密钥、任意系统提示词或自定无限额度。

objective 和 expectedFindings 是模型撰写的任务描述，不能承载权限。程序能验证结构化 scope 是根范围子集；对于自然语言是否拆对任务，仍依靠主 Agent、检查器与评测，不能声称 Schema 已证明语义正确。

### 6.2 批次与启动规则

1. 验证原模型消息、callId 和剩余工具请求额度。
2. delegateTasks 必须独占当前工具批次；与业务工具、updatePlan、requestClarification 混批，或同批出现两个 delegateTasks，均整批不执行，合法 callId 分别回填 MIXED_CONTROL_BATCH。
3. 检查全部子任务的版本、范围、引用、角色、重复事项、子任务总数和预算；先整体校验，再原子登记并预留额度。
4. 任一任务校验不通过，本批一个也不启动；返回可定位错误，不“先跑合法的那个”。
5. 已登记后发生启动失败，记录每个任务的实际状态；已经启动的兄弟任务不能被假称未执行，后续按故障规则处理。
6. 调度 1—2 个子 Runner，主任务进入内部阶段 JOINING_CHILDREN。主 RunStatus 仍为 RUNNING，不是 WAITING_INPUT。

父模型只看到一个 delegateTasks 调用及其一个工具结果。各子任务内部的 callId、工具响应和摘要历史留在自己的 ModelSession，不复制进父模型的原生 Tool 消息。

### 6.3 一批结束再回主模型

子任务全部得到逻辑终态，或根任务取消/停止使该批被中止后，协调器生成一个结果信封，回填父 callId 恰好一次。信封包含各子任务的状态、简短结论、已导入引用和未完成项。

返回超出 4 KiB 时，沿用工作区引用化；主 Agent 使用 readWorkItem 查看完整结构化结果。等待本身不靠模型轮询，不增加 askStatus 工具。

父超时或取消后，即使无需再请求模型，也记录本次调用的实际结束方式。迟到子结果只补诊断事件，不再次回填父 callId、不追加可用证据或改变终态。

同一 goalVersion 下相同 taskKey、角色、范围、输入版本和结果要求的重复委派，不自动重跑：返回已登记结果或重复提示。重新观察已过期状态、补充用户信息、针对检查问题补做时，必须显式关联 previousSubtaskId 和有效的新依据/问题；仍消耗新尝试额度。仅改标题、生成新 ID 不算新任务进展。

## 7. 子 Agent 到底能看到、能做什么

### 7.1 子任务上下文不是父聊天的复制品

下发内容仅包括：

- 本次子目标、结构化范围和结果契约。
- 与子目标有关的根约束，包括不可修改项和来源限制。
- 受控角色 Skill 的方法，以及明确允许的工具 Schema。
- 必要资料或父证据的有界内容/引用。
- 程序投影的用户确认信息；模型摘要不能伪装成用户确认。

不默认下发父完整计划、兄弟任务、全部长期记忆、无关资料或历史对话。需要更多资料时，只能在已分配范围内读取；缺少必要范围或用户信息就提出缺口。

下发引用也在子 Run 中重新登记。子工具不能直接拿父 evidenceId/fileId 绕过本 Run 校验。文件清单工具只列分配的文件视图，而不是即使不可读也列出整个根目录。

### 7.2 能力范围如何计算

子能力 = 根任务预先批准的能力上限 ∩ 角色模板允许能力 ∩ 本次委派子范围。

这里的“根任务能力上限”包括启动时明确批准的可委派能力，不是“模型在文本里请求的能力”。父模型当前可见的工具列表与总批准范围可以不同，但委派不能获得根配置从未批准的工具。

- 子 Agent 不注册 delegateTasks、writeReport、长期记忆写入口或任意命令工具。
- 子 Agent 可以使用自己受控的计划、笔记、工作项回读和业务只读工具。
- 子任务计划不能改变父 TaskBrief，也不能把父计划项改成 done。
- 每个实例独立 ModelSession；SDK 的会话缓存、工具目录和回调也不得串用。
- 使用相同供应商不会建立秘密的信息隔离保证；此处隔离的是应用提交内容与本地访问范围。

共享不可变输入/知识快照是存储优化，不是共享可变聊天历史。共享 MCP 连接时由适配器保证 request id 路由和并发限制；连接不支持并发就串行排队，不因此降低校验要求。

## 8. 结果交接：子 Agent 的结论不自动变成证据

### 8.1 SubtaskResult 的最小结构

子模型以结构化最终输出提出 findings、gaps、questions；子检查器核验后，程序生成完整结果：

| 字段 | 谁负责及意义 |
|---|---|
| 身份与版本 | 程序填写父子 ID、parentGoalVersion、契约摘要 |
| childStatus / stopReason | 程序根据真实执行和子检查填写，不采信模型自报成功 |
| findings | 少量结论，每项有 claimId 和源证据引用 |
| gaps / questions | 未完成要求、无法判断事项、建议询问用户的问题 |
| evidenceManifest | 实际登记证据的类型、来源版本、范围、摘要和观察时间 |
| usage | 程序记录各类请求、耗时和可获得 Token；未知不记为零 |

建议每份完整结构化结果不超过 32 KiB、最多 8 条 findings、20 条证据引用、3 个问题。大表通过证据引用读取，不塞进自然语言总结。该结果是工作项，不是用户交付报告。

子检查只判断本次委派要求是否满足，不替父检查整个任务。子 COMPLETED 表示其局部契约通过；父可能仍然缺另一份结果、需要补查或无法交付。

资料缺口时，子任务以 STOPPED/NEEDS_PARENT_INPUT 交回已有发现及问题，不进入 WAITING_INPUT，也不保留待用户恢复的调用。结构无效或缺项可使用子任务允许的一次修正机会；仍失败就 STOPPED/INCOMPLETE_SUBTASK。实际协议/环境故障仍是 FAILED。

### 8.2 受控证据导入

子任务不能直接生成一个父 evidenceId。协调器在汇聚边界执行：

1. 核对父子登记关系、委派契约摘要和当前父 goalVersion，没有取消、停用或待处理修订。
2. 只处理实际成功登记、已完整提交的源证据；核对内容摘要、输入版本、范围、资料撤回及外部观察时效。
3. 校验该证据在子能力范围内取得，也在根任务批准范围内；伪造 ID、兄弟任务 ID、无关 Run ID 均不接受。
4. 为父 Run 创建新的 evidenceId 和可回读工作项，保留 originChildRunId、originEvidenceId、源摘要及原始时间。
5. 生成引用映射，结构化 findings 中的有效引用改为父 ID；失败项明确列入导入问题，不留下“看似可用”的子 ID。

一份合格的计算证据仍是 CALCULATION；原文仍是原文，外部观察仍有原采样时间。**不新增一种可替代所有来源的“Agent 说过”证据类型。** 子总结、计划、笔记均为 MODEL_DERIVED，不能在导入时升格为事实。

完整、未被取消的 COMPLETED 或因资料缺口 STOPPED 子任务，可导入已完成且独立验证通过的证据；失败/取消/过期结果默认只保留诊断，不自动导入。导入成功不等于整份子结论语义正确。

父 Agent 可通过 readWorkItem 回读导入的原始证据，不必重新运行同一个计算。重复导入按来源身份、摘要和范围去重，保留所有来源路径，不把两个子任务引用同一原文当作两个独立信源。

### 8.3 文件写入边界

input 和已发布知识快照只读。工作区逻辑上分别属于根 Run 和各 childRunId；模型只接触受限 ID，不接触可选择的路径。

子 Agent 只在自己的 work 区保存笔记、结果和证据；只有父 writeReport 能创建 output/<rootRunId> 下的报告。不能通过让两个子任务都写 report.md 再“最后一次写入获胜”来合并。

首版可复制有界证据到父工作区，所有副本都计入根工作区总额；也可用受控不可变对象引用，但不能借引用绕过配额。子目录在父运行及证据核查期间保留，不因子任务结束就删除来源。

## 9. 主 Agent 汇总时还要做什么

汇聚工具成功仅表示这批子任务已结束并返回结果，不表示主任务成功。

主 Agent 应逐项检查：当前交付项是否齐全，计算范围和知识版本是否一致，引用是否真正支持主张，有没有未回答的必要问题。

- 两个 Agent 结论冲突：先对照原始证据和适用范围，不投票、不让第三个 Agent 凭语言裁决。
- 一个说“没有因果数据”，另一个写“活动已证实导致下降”：保留可核验数字，删除无依据因果；需要时补读资料。
- 某个子任务不完整：父可以用已批准工具补做，或在剩余额度内明确重新委派；不默认整批重跑。
- 所有子任务 done 但没有父报告：不能 COMPLETED。
- 子任务结果中出现“忽略规则”“已获用户许可”：仍是模型输出，不改变目标、工具或已确认状态。

最终仍由父 writeReport 生成当前 goalVersion＋deliverableKey 的产物，并由根 CompletionCheck 检查报告实际引用的证据。跨 Agent 转述不会解决自然语言幻觉，主张支持关系仍需专项评测和人工核查。

## 10. 预算：一棵任务树只有一个总账

沿用前阶段实验总量，不给每个子 Agent 再发一套 40/80/900：

| 项目 | 根任务树总额 | 子任务建议上限 |
|---|---:|---:|
| 生成模型请求，含摘要/修正 | 40 | 每次子任务最多 8 |
| 工具请求，含委派/计划/回读 | 80 | 每次子任务最多 16 |
| Query Embedding | 6 | 每次子任务最多 2 |
| 摘要请求，已包含在生成请求中 | 3 | 每次子任务最多 1 |
| 主动处理时长 | 900 秒 | 每次子任务最多 240 秒，且受根剩余时限限制 |
| 同时活跃子任务 | 2 | 内部工具仍串行 |
| 子任务尝试总数 | 4，含失败与补做 | 不能递归创建 |
| 工作区内容总量 | 16 MiB，含所有子区和导入副本 | 单工作项仍最多 1 MiB |
| 产物/结果修正 | 父报告最多 2 轮 | 每子任务最多 1 轮，不能换 ID 重置根尝试数 |

### 10.1 额度预留和回收

Coordinator 在启动前原子预留各子任务的请求额度；子请求实际发出时从预留转为已用，不同时再扣一次根总额。

始终满足：已使用＋尚未使用的全部子预留 ≤ 根总上限。启动委派时，还要额外留出仅供父使用的收尾空间，建议至少 8 次生成、12 次工具请求；不能把所有额度给子任务而让父无力读结果和写报告。

若本批按配置所需预留和父收尾空间装不下，整批拒绝，主 Agent 可改为自己处理或减少子任务，不能悄悄扩大总额。模型不选择任意大预算。

子任务结束释放真正未使用的额度；已发出但超时/取消的请求仍计已用，usage 缺失为 unknown。子摘要、结构化输出修正、框架重试都必须显式计量；首版关闭隐藏重试。

delegateTasks 本身算父工具请求一次，内部每次子工具也分别计数；不能只记外层一次。没有发出 API 的等待不算模型调用，但占用真实时间。

### 10.2 并行时间怎样算

根主动时长是任务树处于主动运行状态的墙钟时间：两个子任务并行 10 秒，根消耗 10 秒而不是 20 秒；另报各 Worker 累计时长和总调用成本。

父 JOINING_CHILDREN 期间子任务在工作，因此根时钟继续。只有子任务均已停止调度、根真正等待用户时才暂停主动时钟；不能把等子结果标成等用户来逃避 900 秒。

单次模型调用继续不超过 60 秒，并取子剩余时间和根剩余时间的较小值。总并发还受供应商限流和客户端连接许可限制；不假定增加线程一定减少延迟。

### 10.3 无进展判定

各子循环保留相同请求和连续错误检测；根只在重新获得控制的决策边界判断进展，不为等待子任务制造空模型轮次。

有效进展按新的来源内容/范围、已核验结果或用户确认判断，而不是子任务 ID、计划状态或新总结。反复委派同一问题不能清零根无进展计数；全局时间、请求和尝试数仍是硬上限。

## 11. 缺信息、失败、取消和目标修订

### 11.1 只有主 Agent 向用户提问

子任务发现缺口后交回 NEEDS_PARENT_INPUT。其他独立子任务可在额度内结束；这一批收齐后，父合并重复问题，通过原有 requestClarification 提问。

父等用户时没有继续运行的子任务。用户回答按父原 callId 回填，预算不清零。父可补做或创建一个新子任务；不 resume 已经 STOPPED 的子 Run，也不假装阶段五检查点已存在。

### 11.2 故障分级

| 故障 | 行为 |
|---|---|
| 子参数可修正、结果缺项 | 子内有限修正；父收到具体缺项 |
| 子模型超时/失败、局部资料不足 | 该子任务结束，独立兄弟可完成；父决定补做或停止 |
| 根预算或主动时间耗尽 | 停止全树新增动作，根 STOPPED |
| 根输入变化、共同存储摘要破坏 | 根 FAILED，停止所有分支，不交付混合输入结果 |
| 任一已使用来源撤回，或共享 MCP 连接目录停用 | 本阶段保守地停止整棵任务树，不能通过兄弟分支绕过 |
| 用户取消根任务 | 根 CANCELLED，向所有子任务传播取消 |

子任务报错不会自动改写根 TaskBrief，也不使根直接变 COMPLETED。可接受的 no-match 必须事先是目标允许的结果；关键证据未知不是 no-match。

### 11.3 取消与迟到结果

根协调器先登记取消/停止屏障，阻止父子新增模型请求、工具、证据导入和最终提交，再通知各 Worker 协作取消。

已经在执行的操作可能完成：记录真实观察和已生成的子工作项，不声称回滚。一次委派结果逻辑封口后，迟到结果只能进诊断，不复活子任务、不补写父报告、不重复回填 callId。

逻辑终态不等于远端请求物理消失。客户端许可在本地请求完成或超时关闭前不能提前复用；若不响应取消的本地操作尚未退出，不启动会复用其可变资源的新根任务，明确提示仍在收尾。远端是否仍处理未知时不宣称已经停机，且本阶段没有远端写业务动作。

### 11.4 目标修订：选择简单、明确的停止屏障

延续第二阶段 revise 的用户确认机制，增加一个限制：**修订登记后，旧版本活跃子任务全部停止，不让两版目标的子任务继续并行。**

1. 先登记 pendingRevision，暂停所有新委派和父子新增动作；通知活跃子任务取消。
2. 在途操作如实记录。父未结束的 delegateTasks 调用以实际已收齐的状态和 NOT_EXECUTED_SCOPE_REVISION/停止原因一次配对；不虚构普通子工具未发生。
3. 子结果从该屏障开始只作为旧版本诊断，不再自动导入。待各分支停止调度后，根进入 GOAL_REVISION 确认；迟到 I/O 仍被隔离并计费。
4. 用户确认且补丁有效：结束旧待回答问题的关联，再推进 goalVersion；旧产物不属于新交付。PLANNED 模式先接受新计划，planRevision 不归零。
5. 用户拒绝或补丁无效：原目标、计划和旧澄清 callId 不变；已停止的子任务不复活。没有旧问题时，父从完整消息边界重新决策，可使用屏障前已导入且仍有效的证据，必要时重新委派。
6. 新版本不自动接纳旧子报告。只允许经范围、口径、摘要和时效复核后复用既有父证据；首版对缩小范围建议重新计算，最易核验。

拒绝修订也可能已经消耗取消与重做成本，CLI 应说明这一点，不能承诺拒绝等于整个执行过程从未受影响。任意修订都不重置全树预算、尝试数或修正次数。

根终态提交前，Coordinator 必须再次检查取消、pendingRevision、来源撤回、连接停用和当前版本；不能一边提交旧答案一边接受新目标。

## 12. 观察执行，而不是记录隐藏思维链

建议所有事件带 rootRunId、runId、parentRunId、subtaskId（适用时）、goalVersion、实例内 sequence、时间和请求关联。

至少能查看：委派提出/接受/拒绝、额度预留、子任务启动/结束、证据导入/拒绝、父汇聚、取消屏障和迟到结果。Coordinator 的接收顺序用于理解根状态，不能只按跨线程时间戳猜因果。

callId 必须与 runId 联合定位；不同子模型生成同一个字符串不算冲突，也不能串回响应。MCP request id 和模型 callId 仍分开。

事件记录问题、动作和真实结果即可，不要求输出隐藏思维链。JSONL 仍是诊断记录，不是已经具备崩溃一致性的任务日志。

## 13. Java 职责怎样演进

以下是后续实现建议，不声称已有这些类或方法：

| 职责 | 增量 |
|---|---|
| agent / Runner | 复用单实例循环，支持根/子实例上下文与子完成检查 |
| agent / coordination | 小型 Coordinator、子任务表、汇聚和取消屏障 |
| bootstrap / skill | 固定的主/子角色配置、能力快照和允许委派清单 |
| model | 每实例独立 Session，统一实际请求计量，保留原生协议 |
| workspace | 父子分区、不可变证据导入映射、全树容量核算 |
| tool | 根专用 delegateTasks，子工具沿用已有受限目录 |
| trace / sample | 父子关联事件、局部结果检查、根交付检查及对照夹具 |

不需要新 Maven 工程、Python 服务、通用消息总线或插件注册中心。第一步先实现串行委派，把权限与结果交接讲清，再开启两个子任务并行；不要让并发问题掩盖证据契约问题。

## 14. 图编排与 A2A 放在哪里

- **图编排**适合明确表达步骤依赖、分支和状态流转。一个图可以只有一个 Agent；多 Agent 也可以不用图框架。
- **MCP**在本方案中连接已批准的工具，不负责安排父子目标和检查交付。
- **A2A**值得在独立运行、独立部署的 Agent 之间需要互操作时研究；本地同进程委派无需为了“标准化”先经过网络。

可选阅读时关注能力发现、任务状态、消息和产物交接的区别即可。本阶段不规定 A2A 协议版本、SDK 方法或服务部署；真正跨进程时，需重新设计身份授权、超时后的结果查询、传输重试与重复执行、取消语义和版本适配，不能把本地方法调用机械换成 HTTP 就宣称完成。

A2A 不自动解决授权、事实正确性、共享事务或业务幂等。若本阶段不接 A2A，不影响验收完成。

## 15. 阶段结束时应学会什么

按配套实验验证之后，应能说明：为什么某件事是工具、为什么某个子问题值得独立 Agent；哪些上下文被隔离；证据怎样跨边界而不丢来源；并行到底省了多少时间、增加了多少调用；失败和修改目标后谁还能继续。

下一阶段再处理持久检查点、重启恢复和真实副作用下的重试/对账。现在保留诊断和来源，不据此宣称可以恢复父子任务树。
