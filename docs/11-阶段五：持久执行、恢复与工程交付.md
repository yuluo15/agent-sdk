# 阶段五：持久执行、恢复与工程交付

版本：v0.1 · 第五阶段详细设计  
交付：仅方案，不编写或修改项目代码，不声称前四阶段已经实现。  
配套：[12-阶段五：故障实验、评测与交付验收](12-阶段五：故障实验、评测与交付验收.md)

## 1. 工程化仍然围绕 Agent 主体

前几阶段让 Agent 会执行、会管理上下文、会接能力，也可选择委派。本阶段解决：

> 程序在任意一次模型调用、工具执行或等待用户时中断，重新启动后，能否明确知道哪些工作已经完成、哪些尚未执行、哪些结果未知，并在不重复副作用的前提下继续？

不是继续堆功能，而是让已有能力可以长期使用、复现问题、受控升级和交付。

首个目标仍是本地 Java 引擎：单进程、一次一个活跃根任务，可选择单 Agent 或第四阶段的一根两子。不做集群、高可用调度、多租户、登录组织、企业审批平台、MCP Gateway 或 A2A 网络。

如果没有实现多 Agent，先完成本章单 Agent 路径即可；多 Agent 的持久恢复是对应能力启用后的附加验收，不是所有实现者都必须先拆 Agent。

## 2. 本阶段新增什么、承诺到哪里

| 以前 | 本阶段 | 不作出的承诺 |
|---|---|---|
| 内存状态，JSONL 仅供诊断 | 事务性运行记录与恢复检查点 | 不是从任意日志文字推断任务状态 |
| 进程存活时等待和继续 | 问题、答复、计划、控制请求跨重启保存 | 不是把线程或网络连接存到磁盘 |
| 结束后新开 Run | 非终态任务可经检查显式恢复原 Run | FAILED/STOPPED/CANCELLED 不因此复活 |
| 不覆盖报告，但有崩溃窗口 | 持久操作标识、文件提交记录与核实 | 数据库事务不能同时提交文件和远端系统 |
| 调用超时后停止 | 区分未执行、已成功、已失败和结果未知 | 超时不等于失败，更不等于已回滚 |
| 配置主要用于启动 | 保存可重建的版本清单并检查恢复兼容性 | 模型别名不保证供应商权重永远不变 |
| 少量临时实验 | 固定评测集、故障注入与最小交付清单 | 几次通过不代表生产 SLA 或全场景安全 |

**持久执行不是 exactly-once 魔法。** 本项目可以保证事务内部状态一致、对已确认结果不盲目重做；跨进程、跨文件和外部系统的动作，需要各自的核实与幂等契约。

## 3. 最小架构：保留 Runner，给关键边界加可靠记录

```text
CLI / 嵌入式调用入口
          ↓
RunService：提交、查询、答复、暂停、取消、显式恢复
          ↓
原 Runner / 可选根协调器
  ├─ 持久状态与操作记录 → 本地 SQLite
  ├─ 模型适配器        → 单次模型请求
  ├─ 工具执行器        → 受控本地工具 / 已批准 MCP
  └─ 受控内容存储      → 证据、工作项、报告
          ↓
检查与终态提交 → 真实结果
          ↓
诊断事件 / 评测记录
```

建议从 SQLite＋JDBC 的本地事务存储起步。数据库在本地受控磁盘，不放网络共享目录；单个应用实例持有数据目录的操作系统级独占锁，第二实例启动失败，不抢占旧锁、不依靠删除一个普通 lock 文件接管。

应用内部由一个持久状态写入口串行提交；模型和工具 I/O 在事务外执行，不能持有数据库事务等待一分钟网络请求。启用并验证 SQLite 的外键、事务和同步配置，不能为了性能关闭持久化保证；首版可使用 DELETE journal＋FULL synchronous，WAL 并非必需，采用其他组合时整体测试其备份与恢复语义。

这是一项本地设计选择，不要求现在修改 pom 或既有 Spring Boot 版本。原工程依赖保持用户选择，实现时再锁定兼容的 JDBC、模型适配和测试依赖。

## 4. 保存什么：足够恢复，而不是持久化所有 Java 对象

使用有版本的结构化数据和受控字节内容，不直接反序列化任意 Java 对象或第三方类名。

以下是逻辑记录，可用少量表和 JSON 列实现，不要求照表格逐项建立独立服务或大型关系模型。

| 记录 | 最少需要保存 |
|---|---|
| Run 快照 | 根/父子身份、RunStatus、执行阶段、stateRevision、goalVersion、TaskBrief、PlanState |
| 控制状态 | 暂停/取消请求、pendingRevision、待答问题、待确认动作及其关联版本 |
| 消息记录 | 原生 Assistant/Tool/User 消息、协议必需元数据、批次与 callId、是否已配对 |
| 操作账本 | operationId、类别、参数/请求摘要、目标版本、执行策略、每次 attempt、结果和未知原因 |
| 预算 | 已计请求、子额度预留、摘要/Embedding、修正/无进展计数、主动时间、工作区容量 |
| 来源和产物 | 已登记文件/知识版本、内容摘要、范围、证据映射、观察时间、产物提交状态 |
| 配置清单 | 模型/适配器、Schema、Skill、检查器、协议与内容快照版本 |
| 事件 | 已提交状态变化的序号与必要诊断载荷，不含密钥 |

一份 Run 检查点包括当前快照、已提交消息位置、操作记录和内容清单的关联版本。检查点不是聊天摘要；摘要仍是可丢弃的派生视图，不能恢复已确认目标、权限或工具成功记录。

### 4.1 事务一致性和唯一约束

关键逻辑要在同一个数据库事务里完成：

- 创建任务＋配置清单引用＋初始预算。
- 接受模型响应＋保存原生 Assistant 消息＋登记整批调用及其计数。
- 确认工具结果＋证据/产物元数据＋对应 Tool 消息＋状态推进。
- 接受用户答复＋记录来源＋回填原 callId＋结束等待。
- 确认目标修订＋旧问题处理＋新 TaskBrief/goalVersion＋计划失效。
- 根产物检查通过＋最终答案＋COMPLETED＋完成事件。

建议唯一约束包括 runId＋callId 的响应绑定、operationId＋attemptNo、父子委派项身份、产物提交标识和命令去重键。数据库拒绝重复提交比“进程内判断一次”可靠。

每次修改检查 expectedStateRevision 和当前执行所有者 epoch；冲突就重新读取状态，不覆盖更新后的取消或修订。epoch 是应用层隔离旧回调的标识，不是能阻止外部系统写入的万能锁。

### 4.2 日志和数据库谁是事实源

运行事实来自已提交数据库状态和通过摘要验证的内容对象。JSONL 是可重新导出的诊断视图，不从它自动执行工具，也不因它缺少最后一行就认定动作没发生。

事件与对应状态在同一事务提交，再向 CLI/日志投影。投影失败可按序号补发；界面重复显示不是业务工具应再次执行的理由。

存储提交失败时停止新动作。不能一边数据库写不进去，一边继续请求模型并把成功只打印在终端。

## 5. 操作账本：先把“不知道”作为正式情况

### 5.1 不同标识不要混用

- runId：任务身份，恢复不变。
- callId：模型消息关联，由供应商产生，限定在本实例协议中。
- operationId：程序生成的稳定逻辑操作身份，用于恢复同一件事。
- attemptId：该操作的一次实际尝试；重试产生新 attempt，不更换逻辑 operationId。
- actionFingerprint：工具、规范化参数、目标版本、资源范围及关键业务前提的摘要，用于防止确认错用。
- 外部幂等键：只有工具契约明确支持时才由程序从操作身份映射产生，不让模型自由填写。

参数相同不一定代表同一个业务意图。operationId 不能简单等于“工具名＋参数”；跨 Run 的两次合法动作也不能被错误地永久合并。

### 5.2 最小状态

| 操作状态 | 含义 |
|---|---|
| PREPARED | 请求与参数已经持久保存，执行入口尚未被获准调用 |
| IN_FLIGHT | 已提交发起意图及本次计量，接下来可能已调用外部能力 |
| SUCCEEDED | 合格结果已经持久提交，可以重建原 Tool 响应 |
| FAILED_KNOWN | 明确失败结果已保存；有副作用时还须明确实际效果，效果仍不明则归 UNKNOWN |
| NOT_EXECUTED | 因取消、拒绝或版本变化等明确没有启动 |
| UNKNOWN | 发起意图存在，但没有足以证明最终结果的持久记录 |

先把 IN_FLIGHT 与 attempt 计量提交，再发起 I/O。这会产生一个保守窗口：数据库写了发起，但实际请求还没发就崩溃。恢复时仍按 UNKNOWN，而不是猜测“一定未执行”。

保存结果后再向模型交付。若结果已持久提交但进程在展示前崩溃，恢复只重建消息/展示，不再次调用原工具。

## 6. 模型与工具各自怎样恢复

### 6.1 模型调用

模型请求也有操作记录，保存本次合法模型视图的版本/摘要、工具目录、输出上限和请求元数据。

- 完整合格响应已提交：复用原 Assistant 消息，不再请求模型来“生成一样的答案”。
- 响应只存在于崩溃进程内：按丢失处理，不从片段日志重建 tool calls。
- 没有持久响应：在恢复获准、预算允许且旧执行者不可再驱动工具后，可以重新生成；记为新的 attempt，计入模型总请求，结果可能不同。
- 新生成只使用最后合法完整消息边界，不伪造丢失响应里的 callId。

此规则依赖已有前提：模型适配器不自动执行工具。否则模型请求重发可能同时重放隐藏工具，本阶段不接纳这种调用链。

若供应商依赖不可重建的服务端会话/不透明协议状态，适配器必须有恢复集成测试；无法重建就标为不支持该 Run 恢复，不能仅存一串文本假称等价。

### 6.2 工具分三类处理

执行策略由可信 ToolDefinition 配置，不采信模型说明或 MCP annotations 自动推导。

| 工具类型 | UNKNOWN 时的恢复方式 |
|---|---|
| 受控只读/确定计算 | 先查是否已有可验证结果；没有时可在预算内重新执行，但必须保持输入版本与范围 |
| 本地持久写入，如报告/工作项 | 依据稳定提交标识核实文件与元数据；能重建结果就重建，不直接再写新文件 |
| 外部有业务副作用 | 先按原 operationId/外部键只读核实；无可靠核实/幂等保证则阻塞，不自动重发 |

重新读取固定 CSV 是重复计算成本，不是重复业务扣款；但查询实时状态会得到新的观察。若旧观察已经保存，保留旧时间；若查询本身重新执行，则登记本次新观察，不伪装成原调用时间的数据。

首版不做通用自动重试器。允许恢复时重试的模型/只读操作，每个逻辑操作最多追加一次，全 Run 最多三次恢复追加尝试；它们同时受原有 40/80 等总量限制。参数错误由模型发出的新调用仍按已有循环限制处理，不混成恢复重试。

这里恢复的是进程中断时尚未提交终态的任务。正常运行已按原错误规则提交 FAILED/MODEL_TIMEOUT 等终态的 Run，不因账本存在而获得额外重试；未知业务效果可以另做只读核实，但不能据此复活终态。

### 6.3 多工具批次只补缺失部分

例如 Assistant 请求 A、B、C，A 已成功提交、B 为 UNKNOWN、C 仍 PREPARED：

1. 保留 A 的原结果，不重做。
2. 按 B 的执行策略核实或阻塞；B 未解决时不越过它执行有序批次的 C。
3. C 只有在目标、预算、取消与授权检查仍允许时才启动；已在原批次计过的请求不重复收费。
4. 所有 callId 合法配对后才进入下一模型请求。

控制工具也要进入持久记录，但恢复策略是“查询/恢复已提交控制状态”，不是再次执行文本指令。updatePlan、requestClarification、delegateTasks 不能当普通只读工具重跑。

终态 Run 不为补齐消息而执行剩余工具；诊断记录可以保留哪些调用未执行。

## 7. 报告写到一半崩溃：数据库和文件如何对账

文件系统不在 SQLite 事务里。建议给每次内容写入建立稳定提交清单，流程为：

1. 在事务中预留 artifactId/itemId、相对最终位置、operationId、goalVersion、证据引用、完整预期字节摘要及容量。报告最终字节由模型正文与程序附录确定后冻结，不恢复时重新让模型生成。
2. 将有界待写正文保存到受控暂存区，验证摘要并按平台能力同步；这是执行存储的一部分，不能凭日志还原。
3. 以不覆盖目标的方式发布到预留最终位置。采用同卷原子移动时需验证实际文件系统/Java实现语义；不支持就明确报错，不声称普通覆盖复制具有同样保证。
4. 在事务中登记已提交文件、证据/产物和 Tool 结果，随后才向模型返回成功。

内容暂存本身也可能失败，因此清单中的“预期存在”不是成功。恢复逐一核实：

| 发现 | 行为 |
|---|---|
| 最终文件存在且摘要/操作身份匹配，DB 尚未确认 | 在当前控制边界允许的范围内重建真实结果元数据，不重新写第二份 |
| 只有完整合格暂存文件，最终未发布 | 只有非终态、目标仍适用、没有取消/修订屏障时才可继续发布 |
| 暂存与最终都缺失 | 不返回成功；可从已保存的完整字节重新暂存，否则明确存储缺口 |
| 最终位置内容不匹配 | 视为存储冲突/破坏，停止并提示；不覆盖或自动删除 |
| DB 记成功，但文件缺失/摘要错误 | 不交付成功，标记完整性问题，不能用模型重新编一份顶替 |

恢复核实已有文件，不等于授予取消后的新写入许可。取消或旧目标下已经存在的真实文件可记入历史产物；只有暂存内容时不得继续发布来“补完”被取消动作。

临时副本、待提交字节和导入副本都计入受控容量；预留＋实际占用原子核算，避免并行超额。清理只处理已核实属于本次存储协议的遗留临时对象；首版提供预览和人工执行，不自动删除不熟悉文件。

本地进程崩溃恢复是首要验收；突然断电、硬件缓存不兑现同步或介质损坏的保证必须额外测试。数据库事务与原子重命名都不等于任意硬件故障后绝无数据丢失。

## 8. 启动后怎样恢复，而不是自动把全部任务跑起来

### 8.1 RunStatus 与恢复门槛分开

新增非终态 `PAUSED`，用于明确的运行中暂停。保留 RUNNING、WAITING_INPUT 和四种终态。

另设运行时恢复门槛 recoveryState，可为 NEEDS_CHECK、READY、BLOCKED；这不是业务是否成功的结论。进程重启发现上次活跃 Run 时，先 NEEDS_CHECK，禁止任何模型/业务工具调度，不自动将其标 FAILED，也不立即开跑。

恢复需要用户显式选择根 runId。已提交 COMPLETED、STOPPED、FAILED、CANCELLED 只能查看或按规则核实未知动作，不得 resume；希望再做任务则新建 Run，并保留原任务引用。

### 8.2 恢复检查顺序

1. 获得本地数据目录独占锁，确认旧本地执行者不再持有资源；创建新 ownerEpoch。
2. 检查数据库结构版本、完整性、快照和内容引用；不将损坏记录默认置零或空列表。
3. 重建配置清单、原生消息和工具执行策略，验证已登记输入及知识/Skill快照。
4. 读取当前取消/撤回/工具停用/记忆删除信息；禁止项优先于历史冻结版本。
5. 重建全树预算、预留、操作状态和消息配对；将未确认的 IN_FLIGHT 分类为 UNKNOWN。
6. 对需要的本地文件/远端操作做受控核实；有未解决业务副作用就 BLOCKED，不先交给模型猜。
7. 展示原目标、检查点、已有产物、缺口、预计重新执行项及剩余额度；用户确认后才 READY 并继续。

已在 WAITING_INPUT 的任务恢复后仍展示原问题，不重新问一个语义相似但关联不同的问题。PAUSED 任务只有显式 resume 后继续；用户拒绝恢复则不发新调用。

恢复预览不是权限升级。换模型/Skill、扩大工作区、换资料集合或无法兼容的工具升级应另开 Run，不能通过“修复恢复”偷偷改变环境。

### 8.3 暂停、取消与退出

- pause：先持久登记暂停请求，停止发起新动作；让正在进行的有界请求结束并保存真实结果，在全树安全边界转 PAUSED。未执行调用保留待执行身份，不丢弃后重新让模型猜。
- cancel：持久登记取消屏障，禁止后续业务动作；按已知事实收尾，进入 CANCELLED。恢复后也不能继续剩余写入。
- exit：活跃任务默认先请求暂停并等待明确安全边界；若用户选择强制退出，提示下次需要恢复检查，不承诺立即安全暂停。

CLI 明确区分“暂停请求已接受”和“已经 PAUSED”。超过合理收尾期限时显示未结束操作，不能把 Future.cancel 当作外部执行已经撤销。

如果暂停期间已是 WAITING_INPUT，保留原问题和恢复前状态；先 resume 返回原等待，再接受答案，避免同时设计另一条暂停中答复路径。

## 9. 用户答复、目标修订和必要动作确认

### 9.1 命令持久去重

命令由可信入口产生 commandId，绑定 rootRunId、expectedStateRevision 以及 questionId/revisionId/actionId。重复投递同一命令返回已有回执；同一 commandId 内容不同则拒绝。

CLI/调用方要保留已提交的 commandId 并支持查询回执。用户重新手输相同文字未必是同一命令，不用自然语言相似度去重。

问题状态与答复回填同事务提交。答复已保存、但 CLI 回执丢失时，重发原 commandId 不再次推动模型、不重复生成 Tool 响应。

### 9.2 目标修订沿用第二、四阶段规则

pendingRevision、旧值→新值、用户确认和被替代的澄清 callId 都持久化。确认前不结束旧问题；拒绝后保留原目标和问题。确认时一次提交新目标、goalVersion、完成条件和计划失效状态。

修订时已有子任务停止屏障也持久保存。重启不会取消 pendingRevision，更不会把因修订停掉的旧子任务当作“崩溃任务”复活。planRevision、预算与修正次数不归零。

### 9.3 写业务前的最小确认，不做企业审批平台

普通受控报告写入可沿用任务启动时批准的范围。本阶段若学习真实业务写工具，只先用配套的虚构回执工具验证机制，不接支付、下单或生产系统。

对需要确认的工具调用，在执行前展示：具体动作、目标对象、关键参数、影响和有效期。确认绑定 operationId＋actionFingerprint＋goalVersion；参数、目标、关键前提改变后必须重新确认。

此类写动作要求独占模型工具批次，混批返回 MIXED_EFFECT_BATCH，整批不执行。原工具 callId 保持待完成；运行时以 WAITING_INPUT/ACTION_CONFIRMATION 等待可信 `approve/reject` 入口，而不是让模型再调用一个伪“用户同意”工具。

- `/answer` 只回答澄清，不能批准动作。
- 拒绝或确认到期：仅当操作尚未获准发起时，才记 NOT_EXECUTED 并给原 callId 回填未执行原因；预算允许时模型再决定下一步。
- 操作已进入 IN_FLIGHT/UNKNOWN 后，拒绝或确认到期只能禁止新的写尝试，不能改记未执行；保留真实状态，按原操作身份核实，不能提前回填一个虚假的最终结果。
- 崩溃后不能仅因之前“确认过类似动作”重新取得许可；需核对确认与原操作完全一致、未过期、当前前提仍有效。
- 已发出但结果未知时，确认有效也不意味着允许再次发出。

当前仍是本地单用户可信控制台，不声称实现企业身份认证、多人授权或审批审计。将来真实业务确认应接真实身份与权限，但不在本阶段造一套组织系统。

## 10. 外部副作用：先核实，不能以重试代替判断

外部写工具接入前至少声明：动作效果、是否支持稳定幂等键、怎样只读查结果、失败是否可能已生效、键有效期及参数冲突行为。MCP 只是调用协议，不自动提供这些业务保证。

UNKNOWN 时的决策：

1. 查询原操作的最终状态，查询工具必须是真正只读。
2. 已应用且参数/版本匹配：登记原真实结果，不再次写入。
3. 已确定未应用且原执行不可能稍后生效：只有当前用户意图仍有效、确认未过期、工具契约允许时，才可考虑同键重发；首版仍要求明确人工决定。
4. 处理中、查询失败或无法判断：保持 BLOCKED/需要核实，不当作失败、成功或“可以安全重试”。

普通“查不到”不等于第 3 项的确定未应用；旧请求可能仍在队列里。幂等键过期、服务端不保存最终状态、相同键参数不同，均不能靠换一个键绕过不确定性。

取消后仅允许核实已经发生的动作，不能通过重新调用同键写接口“查结果”，因为该接口可能第一次真正执行。需要撤销是新的补偿动作，需另外的授权与业务规则，不假装通用回滚。

根尚非终态时，核实调用计入原任务预算；已终态或预算耗尽后，操作员可显式启动独立的只读核实维护操作，建议最多 3 次/30 秒，并单独记录成本。它不能调用模型继续任务、不能写业务、不能把 CANCELLED 改成 COMPLETED。

核实得到新事实可补充操作账本和诊断，但终态任务的已交付答案保持历史身份；需要新交付则新建 Run。

## 11. 预算与时间不能靠重启刷新

沿用单根任务或全树 40 次生成、80 次工具、6 次 Query Embedding、3 次摘要、900 秒主动时长、16 MiB 工作区等实验起点；对应功能未启用时没有额外开销，也不能因此自动扩大其他限额。

- 模型发起意图提交时计一次 attempt，崩溃窗口中不确定是否实际发送也保守计用。
- 模型接受的工具批次仍整批预检并计入请求数，包括非法参数和混批；恢复未执行的同一调用不重复计一次初始请求。
- 因恢复而额外实际执行的工具 attempt 另消耗一次工具额度。分别记录原始调用数与重试数，总收费额度是二者之和，不能仅数 callId。
- 所有恢复重试、核实、摘要、子模型和子工具计入所属预算；缺失 usage 记 unknown。
- 子额度由持久预留记录恢复，不能用“新进程没有 Worker”作为全部释放理由；已用不退回，未用仅在对应状态明确结束/取消后释放。
- 产物修正、子尝试数、恢复尝试、重复请求与无进展计数均持久保存。

### 主动时间的保守恢复

内存 monotonic 时钟不能跨进程复用。建议根任务采用“先持久预扣一段主动时间许可，再运行”的小机制：每段最多 60 秒且不超过总剩余时间，父子共享同一段墙钟许可，实际请求截止时间不得超出已许可边界。

正常运行用 monotonic 时钟计时；全树到达无在途动作的安全边界时，可事务结算实际已用并退回该段未用部分。若进程崩溃，未结算段全额算已用，不猜实际死亡时刻，也不因时钟回拨返还预算。后续需要更多时间先提交下一段许可。

暂停、等待用户和离线时长不持续消耗主动许可；恢复检查/继续工作的耗时计入新的许可。某次崩溃可能多扣至一个许可段，这是明确的保守代价；可缩小段长，但不能为了精确而允许无限重启获得免费执行。

状态证据的 60 秒有效期、动作确认期限属于真实日历时间，不因 PAUSED、离线或主动预算停表而冻结。恢复时过期的“当前可供应”观察仍需重查。

## 12. 可选多 Agent：恢复任务树，而不是重放委派工具

若启用了第四阶段能力，根、子、委派合同、额度预留、汇聚状态和证据导入映射在同一个本地数据库内保存。

- delegateTasks 接受时，父控制操作、子任务身份和全部额度预留原子提交；崩溃后读取原记录，不重新生成 childRunId 再派一次。
- 子已 COMPLETED 且结果持久完整：直接参与汇聚，不重新请求该子模型。
- 子非终态：按其最后检查点和操作策略恢复；仍受同一根 goalVersion、能力子集和原预算约束。
- 子已因取消、修订或缺信息 STOPPED：保持终态。父根据现有契约决定是否创建新尝试，不能因持久化而改变第四阶段的终态规则。
- 汇聚结果、父证据映射和父 Tool 响应绑定原子提交；内容对象先提交并核验，未引用孤儿内容不是成功导入。
- 崩溃在“子结果已保存、父尚未汇聚”：恢复导入，不重做子业务工具，也不重复给父 callId 回填。
- 根取消/修订屏障持久存在时，旧子操作结果仅按原控制边界记录，不推进新目标。

根可以显式 pause 整棵树，子实例各到安全边界后保存 PAUSED；只有根统一 resume，不提供独立恢复旧子绕过父版本的入口。

一根两子、深度一层、一次一个活跃根任务仍不变。数据库不是增加任意数量后台 Agent 的理由。

## 13. 版本冻结、更新与数据保留

### 13.1 一次任务的配置清单

至少记录模型供应商/模型 ID与可得版本、参数、适配器版本、消息格式版本、提示/Skill 内容快照、工具 Schema 和执行策略版本、检查器版本、知识索引/来源版本、MCP 服务器身份与批准目录摘要、应用构建版本和状态结构版本。

版本号只是一条标签；Skill、规则等需有可校验内容快照，工具实现需能定位兼容构建。凭据只存受控凭据引用，不把 API Key、完整环境变量或访问令牌写入数据库和检查点。

模型供应商只提供浮动别名时如实标记可复现性限制。固定模型 ID 与 temperature 不等于逐字重现；确定性程序恢复测试用脚本模型，真实模型结果按行为与证据评价。

### 13.2 恢复时不偷偷升级

普通新资料、Skill 和配置供新 Run 使用。恢复旧 Run 时要么有原兼容快照/实现，要么明确阻塞并让用户新开任务；不能静默用当前最新配置重解释历史操作。

MCP 重启连接要重新协商和核验批准目录；协议与工具契约一致才能继续，旧 JSON-RPC request id 不直接重放。普通状态变化生成新观察，工具目录/Schema变化仍按第三阶段停用边界处理。

撤回来源、禁用工具或删除记忆优先于冻结版本。恢复前检查最新禁用状态；涉及已删除记忆的旧视图不得加载。首版保守取消受影响的非终态 Run，再按清理范围移除其可重建上下文中的相关内容；历史产物、备份和已发送供应商的数据不能承诺自动物理消失。

这扩展第三阶段“删除当前使用记忆前先取消”的规则到暂停/可恢复任务，不能让旧检查点复活已删除偏好。

### 13.3 备份、升级和存储限额

首版在应用完全停止或维护模式取得独占锁后备份：数据库及所用 journal 文件、内容存储、配置/技能快照一起形成清单并校验。不能复制一个活跃 db 文件就假称包含所有证据和提交状态。

备份完整不等于允许从任意历史点重新执行。只有明确确认原 Run 自该备份后没有状态推进、原执行目录已停止并不再使用，才允许把备份作为续跑来源；恢复时仍检查当前禁用信息和未知外部效果。若原任务后来执行、取消、修订过，或无法确认这一事实，该备份仅供只读检查，不用于续跑，否则可能回退预算和屏障、重复旧动作。

备份清单记录各 Run 的 stateRevision 和最后提交序号，用于核对，不把清单本身当作“后来没有执行”的证明。停用原副本与避免两份数据目录同时运行是本地受控运维前提；每目录独占锁不具备跨副本互斥能力。本阶段不设计任意历史回滚后的跨系统对账恢复。

迁移前备份并验证回读，记录 schemaVersion，拒绝未知版本；本阶段不要求任意跨版本向后恢复。迁移失败时原任务没有继续执行才可采用上述备份回退；回滚应用也要匹配状态结构，不能把新库直接给旧程序试着读。

除每 Run 上限，还需数据根目录总容量阈值，实验可从 256 MiB 起步，覆盖数据库、消息、事件、暂存与内容；备份位置另配额度。达到限额拒绝新任务并提供诊断，不静默删活跃/可恢复内容。保留少量用于记录停止原因的余量；数据库已无法提交时关闭调度并在终端明示，绝不伪报持久停止成功。

保留/清理按整个任务及其来源关联处理，默认先预览，不删除仍被恢复任务引用的证据。单用户本地 ACL、凭据管理与是否允许数据外发是部署前提；持久化更多信息意味着更需要明确敏感内容和保留范围。

## 14. 评测、调试和最小 Java 交付

### 14.1 三类测试分开

1. 确定性机制：脚本模型、可控时钟和故障点验证状态、预算、调用次数和恢复边界。
2. 适配集成：实际 Spring AI 消息链、SQLite 事务、文件提交、MCP 客户端与本地受控服务，不能 mock 掉被测边界。
3. 真实模型任务：固定资料、目标与配置，检查产物、来源支持、成本和缺口处理，不只看“COMPLETED”。

调试先定位模型输入、操作账本、工具观察、检查器和恢复阶段，不把任何恢复失败都归因于 Prompt 不够好。用 root/run/operation/attempt/callId 联合定位，不要求输出隐藏思维链。

### 14.2 入口和职责

保留一个 Maven 项目，明确逻辑边界即可：

| 部分 | 责任 |
|---|---|
| RunService / CLI | start、status、answer、pause、resume、cancel、inspectRecovery 及命令回执 |
| Runner / Coordinator | 原循环、父子协调与状态推进，仍是唯一执行所有者 |
| persistence | 状态事务、操作账本、版本迁移和恢复扫描 |
| model / tool | 单次调用、可恢复消息、执行策略与核实能力 |
| workspace | 内容提交、证据清单、文件核实与容量 |
| trace / evaluation | 诊断导出、固定夹具、实验结果汇总 |

入口接收明确的任务和命令对象，不要求同步等待整个任务。仍可只做本地 CLI，不需要为了“API稳定”先开放公网 HTTP 或建设前端。

实现完成后交付：可运行打包物、依赖/构建版本、无密钥的示例配置、虚构样例资料、启动/状态/暂停/恢复操作说明、回归测试与已知限制。这是将来项目交付应包含的内容，本轮只创建方案文档，不替你生成这些项目文件。

## 15. 完成标准与主体之后的路

推荐顺序：单 Agent 状态落盘 → 原生消息恢复 → 已完成工具不重做 → 文件提交核实 → 等待/暂停/修订 → 未知副作用练习 → 可选父子树恢复 → 版本、备份和评测交付。

真正实现并验收后，你应得到一个可以解释、可重复运行、能明确恢复或拒绝恢复、能控制成本和保留依据的 Agent 引擎。五阶段方案齐备不代表工程已经实现，更不代表任何真实企业场景都可直接上线。

之后不必机械进入“第六阶段全平台”：选一个真实但可控场景，补它确实需要的身份授权、数据合规、容量、部署和业务连接。主体保持稳定，行业变化优先落到工具、资料、能力包和检查器；对外部真实副作用逐项验证，不把学习夹具的通过当作生产授权。

## 16. 本轮官方参考与采用边界

- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：检查点与任务状态保存的概念；本项目的操作账本和预算仍需自己定义。
- [LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)：检查点、已完成节点写入与恢复/历史重放的区别，不代表所有外部动作只执行一次。
- [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)：中断恢复可能重新进入节点，中断前副作用需要幂等设计；不能理解为保存任意 Java 指令位置。
- [SQLite Atomic Commit](https://www.sqlite.org/atomiccommit.html)：回滚日志模式下的事务原子性及底层锁、同步和存储假设；独立文件和远端动作不在此事务保证内。

以上资料已在本轮核验，用于理解持久执行，不要求引入 Python/LangGraph，也不是本项目 Java 适配器、SQLite驱动或模型协议已经通过兼容测试的证明。本文选择的本地事务、显式恢复与操作核实仍须按配套实验实现和验证。
