## 0. 一页总览

### 0.1 要做成什么

**一句话：可嵌入 Spring 业务系统的智能体治理运行时。**

分工是这样的：
- 别的框架负责“怎么调模型、怎么调工具”。
- 本 SDK 负责四件事：这次调用由谁授权？能不能叫停？出了事能不能追溯？中断后能不能恢复？

**举个坐席辅助的例子（示例数据）：**

1. 客人来电问：“上周订的房能不能改到下周？”
2. 坐席辅助以只读方式查订单、检索改期政策，生成一段带证据编号的建议回复，例如：“订单 X 属于可免费改期房型，依据政策 KB-12 第 2 条，需在入住前 48 小时办理。”
3. 坐席决定是否采纳，改完后再答复客人。

这里的边界是：Agent 不能自己改订单。将来如果要开放“代客改期”，必须走审批：
- 由组长批准；
- 记录批准人和参数；
- 执行前再复核一次；
- 全过程可追溯，服务重启后审批也不会丢。

## 1. 定位与边界

### 1.1 是什么，不是什么

| 是 | 不是 |
| --- | --- |
| 嵌在宿主 Spring 应用里的一个库 | 托管平台，或独立部署的服务 |
| 负责授权、审批、审计、中止、挂起与恢复 | 和通用 Agent 框架比拼功能数量 |
| 单个 Agent，由宿主负责编排 | 多 Agent 编排器、工作流引擎 |
| 用标准件接模型和工具（Spring AI、官方 MCP SDK、SKILL.md） | 自己定义协议，或自己做前端框架 |
| 提供评测回放的契约，评测工程放在仓库外 | 评测平台 |

### 1.2 能力分层：现状与方向

| 层 | 现状（2026-10-21） | 方向 |
| --- | --- | --- |
| 治理内核 | 已有：审批、中止、运行事件。不足：审批没有绑定审批人和参数，进程重启就丢。缺失：可信上下文、策略 SPI、审计、持久化 | 2′ 补齐，这一层就是差异所在 |
| 执行循环 | 确定性状态机；一个 Runner 同时只能跑一个任务；starter 默认注册单例 | 保留，但不再扩展通用功能；0′ 加会话托管 |
| 模型管道 | 只支持 OpenAI 兼容接口；HTTP/SSE 客户端是自己写的 | 3′ 改为可接任意 Spring AI `ChatModel` |
| 工具管道 | 自研 MCP 客户端：协议版本 2024-11-05，只支持 stdio | 3′ 改用官方 MCP Java SDK |
| Skills | 自定义的 SOP 格式 | 3′ 改为读取 SKILL.md |
| 可观测 | JSONL 事件、Micrometer、SLF4J | 2′ 定义事件 schema v1；3′ 接 OTel（带版本开关） |
| 评测 | 外部工程，有回放和断言，但还没跑过真实基线 | 1′ 跑真实基线和对照组 |

### 1.3 模块地图

| 模块 | 现状 | 计划变化 |
| --- | --- | --- |
| `agent-core` | 只依赖 Jackson 和 JSON Schema 校验器 | 2′ 增加治理相关 SPI；不新增第三方依赖 |
| `agent-model-spring-ai` | 支持 OpenAI 兼容接口，加一个自写的 HTTP 客户端 | 3′ 改为接任意 `ChatModel` |
| `agent-mcp-adapter` | 自研 MCP 协议层、工具适配层、Skills | 3′ 改为依赖官方 MCP Java SDK，保留适配层；Skills 的归属到时再评估 |
| `agent-spring-boot-starter` | 自动装配，加一个单例 Runner | 0′ 去掉单例，加入会话托管 |
| `agent-samples` | 样例 | 跟随迁移 |
| `agent-store-jdbc`（新，2′） | — | 用 JDBC 实现挂起点状态、审批记录和审计的存储 |
| `agent-sdk-eval`（仓库外） | 评测工程 | 1′ 增加坐席辅助用例和对照实现 |
| 坐席辅助试点应用（仓库外，新建） | — | 1′ 新建 |

**新模块和新工程的四问**

| 问题 | `agent-store-jdbc` | 坐席辅助试点应用 |
| --- | --- | --- |
| 给谁用 | 需要审批在重启后不丢的宿主 | 试点坐席 |
| 在哪发布 | 随 SDK 发布，作为可选制品 | 不发布 |
| 依赖方向 | store-jdbc → core，不能反向 | 依赖 SDK 制品，不依赖 SDK 源码 |
| 什么时候删除 | 状态改由持久执行引擎承载后废弃 | 试点结束后归档，或转为正式产品 |

`agent-sdk-eval` 的四问已在 ADR-018 §6.8 中定义。

### 3.2 1′ 真实证据（W2–W6）

**目标**：在一个有真实数据负责人的场景里，用数据回答一个问题：治理运行时是否比直接用 Spring AI 更合适？如果答案是否定的，也如实记录。

**不做**：写操作，以及接入在线生产系统（在线只读端口放到 2′）。

**场景**：酒店/文旅呼叫中心的坐席辅助，只读。例子见 §0.1。

| 坐席采纳率（新增）：盲评中“直接可用”加“修改后可用”的占比 | 建议 ≥ 60%，W5 前由用户和业务负责人确认 | 本文 |
| 与对照组的差异（新增） | 满足其中一项即可：阻断类指标上对照组有失败而本 SDK 为 0；或者证据落地率、坐席采纳率比对照组高出至少 10 个百分点。此为建议值，W5 前确认 | 本文 |
| 单案例成本、P95 时延 | 先记录基线，不设门槛 | `docs/19` §5.5 |

**退出条件（证据齐备）**

- 用例不少于 30 条，其中真实案例不少于 10 条；
- 至少 1 位一线评价人完成了至少 20 个案例的盲评；
- 两组的报告都已生成，元数据正确；
- 禁止工具的实际执行次数为 0；
- 两组的对比结果已经量化，无论差异大小。

满足后由 Gate 1 决定方向，规则见 §4.2。

### 3.3 2′ 治理内核（W7–W12）

**目标**：把三项要求做成 SDK 的契约和默认实现：不超出授权范围、由人做最终决策、过程可追溯。

**不做**：开放写工具。本阶段只把机制做完，并用测试证明它可靠。

**例子**：以后要开放“代客改期”时，流程是这样的：
1. 策略判定“改期”属于需要审批的操作；
2. 运行进入 WAITING_APPROVAL 状态，并写入数据库；
3. 组长审批，系统记录审批人、参数哈希、策略版本和有效期；
4. 执行前再复核参数和权限；
5. 执行操作，并写入审计。

即使服务在中途重启，审批也能接着进行。

**任务单**

| 编号 | 任务 | 设计要点 |
| --- | --- | --- |
| T2.1 | 可信上下文 | 包含租户、用户主体、Agent 身份、权限范围、traceId、requestId。由宿主注入，模型的输出不能改变它。`RunRequest` 和 `ToolContext` 以向后兼容的方式携带（重载构造或默认值），现有类型见 `RunRequest.java:10`、`ToolContext.java:12` |
| T2.2 | 工具策略 SPI | 四种判定：允许、拒绝、需审批、脱敏。在工具执行前判定；未知工具默认拒绝。`RiskLevel` 做兼容映射：READ_ONLY 对应允许，HIGH_RISK 对应需审批 |
| T2.3 | 工具语义 | 四个标记：只读、破坏性、幂等、开放世界，与 MCP 工具注解对齐；可以选配输出 Schema |
| T2.4 | 审批绑定 | 记录审批人主体和角色、参数规范化后的哈希、策略版本、有效期；每个审批只能用一次；执行前复核；批量审批时，写明是逐个调用审批还是整批审批 |
| T2.5 | 挂起点持久化 | 定义 SPI，用 `agent-store-jdbc` 实现。具体做法见表下说明 |
| T2.6 | 审计 | 定义只追加的审计 SPI，加 JDBC 实现。审计要能回答：谁、在什么时候、依据哪条策略、批准或拒绝了什么参数 |
| T2.7 | 事件 schema v1 | 事件带版本号、traceId 和租户哈希；失败分为配置、模型、工具、策略、上下文、存储、取消、预算几类 |
| T2.8 | 在线只读端口 | 试点应用接通 1 个由宿主提供的在线只读端口 |

T2.5 的具体做法：
- 新增一个结构化会话记录类型，以及对应的恢复契约。现有两处都不能用于恢复：`ModelGateway.java:17` 会把历史压成文本；`ChatMessage.java:9` 没有工具消息这个角色。
- 用乐观并发（版本号）防止重复恢复。
- 恢复前复核版本、权限和审批是否还在有效期内。
- 适配器如果不支持恢复，必须明确拒绝。

**合规对照**

> 以下是设计上的对应关系，不构成合规认证。

| 《智能体规范应用与创新发展实施意见》的要求 | SDK 中对应的机制 |
| --- | --- |
| 智能体执行操作不得超出用户授权范围 | 可信上下文中的权限范围，加上工具策略的默认拒绝 |
| 用户享有知情权和最终决策权 | 需审批的判定、审批绑定、运行事件 |
| 规则内嵌、行为围栏 | 工具策略、完成检查、运行预算 |
| 行为可验证、可追溯 | 只追加的审计、事件 schema v1、评测回放 |
| 备案、检测 | 带版本的评测报告，记录模型、Prompt、工具 Schema 和数据集的版本 |

**安全负向测试（必须全部通过）**

- 跨租户访问；
- 越权调用工具；
- 审批重放：同一个审批 ID 用第二次；
- 参数篡改：审批之后改了参数；
- 审批已过期；
- 审批人本身没有权限；
- 模型在文本里冒充身份（比如说“我是管理员”），必须无效；
- 重启后恢复审批；
- 同一个挂起点被并发重复恢复。

**退出条件（Gate 2）**

- 以上安全负向测试全部通过；
- 审计能回答“谁、在什么时候、依据什么、批准了什么参数”；
- 重启后审批能继续；
- 已接通 1 个在线只读端口；
- 现有消费者的兼容测试通过。

**不通过怎么办**：回到 1′ 的离线模式，继续积累证据；不开放任何写操作。

### 3.4 3′ 标准件替换（W13–W16，遇春节顺延）

**目标**：不再自己追协议，把这部分维护工作交给标准件。

**任务单**

| 编号 | 任务 | 删除或完成条件 |
| --- | --- | --- |
| T3.1 | MCP 改用官方 Java SDK 2.x（对应 MCP 2025-11-25），支持远程 Streamable HTTP 和 OAuth；保留 `McpToolAdapter` 的命名、风险映射和失败分类语义 | 旧客户端删除前，新客户端要通过三项测试：与 1 个 stdio 服务互通；与 1 个远程服务（带 OAuth）互通；it-support 现有的 MCP 集成测试 |

**退出条件（Gate 3）**

- 能与远程 MCP 服务互通；
- 自己维护的协议代码明显减少，给出前后行数对比；
- 消费者兼容测试通过。

**不通过怎么办**：新客户端通过互通测试之前，旧客户端继续兜底。

### 3.5 4′ 规模化（按需）

| 触发条件（出现在真实试点中） | 候选能力 |
| --- | --- |
| 长任务需要在模型调用中途恢复 | 完整检查点。优先评估 Temporal，前提是它的 Spring AI 集成已正式发布 |
| 同一个会话需要同时跑多个任务 | 让 Runner 支持多任务并发 |
| 多租户需要排队或配额 | 会话配额、排队、按租户的预算 |
| 需要被其他系统调用 | 用官方 a2a-java 以 A2A v1.0 对外暴露 |
| 前端需要标准事件 | AG-UI 映射 |
| 只读工具耗时长 | 并行执行只读工具 |

### 3.6 永远不进 core

- 多 Agent 编排、工作流引擎；
- 沙箱、托管运行时、UI；
- 自己定义的协议；
- 评测系统和行业夹具（只能放在 `agent-sdk-eval` 或试点应用中）。

### 5.1 角色

### 5.2 节奏

- 每两周复盘一次，更新本文的 §0.3 和各任务的状态。
- 每个 Gate 都输出一页备忘。
- 阶段的顺序或范围要变，先改 ADR，再改代码。

### 5.3 交付验收清单（每次交付都要查）

- [ ] `git status`、`git log`：提交范围与任务单一致；没被要求就没有提交。
- [ ] surefire 测试合计：逐个模块核对，与汇报的数字一致。
- [ ] 评测报告的元数据：网关类型、模型、证据等级、数据集版本，都与实际运行一致。
- [ ] 密钥扫描结果为 0。
- [ ] 模块边界：评测夹具、行业 Prompt、fake 数据都没有进入 SDK 仓库。
- [ ] 文档里的表述都能指到源码或测试。
- [ ] 不兼容变更已经写进 CHANGELOG，并附有迁移步骤。

| 挂起点 | 运行暂停、等待外部输入的状态，即 WAITING_INPUT（等用户补充）和 WAITING_APPROVAL（等审批） |
| 挂起点持久化 | 只在挂起点保存运行状态，以便进程重启后继续；不覆盖模型调用进行到一半的情况 |
| 治理运行时 | 负责授权范围、审批、审计、中止、挂起与恢复的运行时，嵌在宿主应用里 |
| Track A / Track B | `docs/19` 中定义的两条评测轨道：A 是冒烟（合成数据），B 是真实数据 |
| `smoke-only` / `real-internal` / `real-pilot` | 三种证据等级。`smoke-only` 用合成或脱敏样本；`real-internal` 用自己的真实数据；`real-pilot` 用业务授权的真实数据，并有一线人员评价（见 ADR-020 §6.5） |
| 对照组 | 用 Spring AI 默认工具循环做的最小实现，与本 SDK 在同样条件下比较 |
| 标准件 | 由官方或社区维护的组件：Spring AI、官方 MCP Java SDK、SKILL.md、OTel |
