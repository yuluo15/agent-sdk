# 阶段二：复杂任务与上下文工程

日期：2026-09-16  
性质：详细设计，不修改项目代码。  
配套：[06-阶段二：长任务实验与验收](06-阶段二：长任务实验与验收.md)

## 1. 这一阶段的主角仍然是单 Agent

阶段一解决“能不能正确地调用工具并完成任务”。阶段二解决：

> 任务变长、资料变多、口径相互冲突、用户中途调整要求时，Agent 能否不忘目标、不反复做无用功，并交付经过检查的结果？

围绕这个问题增加五种能力：**显式计划、运行内工作区、上下文压缩、受控目标调整、依据检查结果修正产物。**

它们是同一个 Agent 的运行机制，不是五个 Agent，也不是五个微服务。

### 1.1 先说明实施前提

现在可以提前完成第二阶段方案，但不把已创建的 Java 骨架当成阶段一功能已经完成。真正实现本阶段前，应先跑通阶段一的模型—工具—观察循环、callId 配对、工具边界和报告生成。

用户已接手代码，本次仅交付方案；类名和方法能力是建议的演进方向，不声称它们已存在于当前实现。

### 1.2 本阶段不扩张到哪里

| 做 | 不做 |
|---|---|
| 当前任务的计划和进度 | Supervisor、多 Agent、A2A |
| 工作区文件与按需回读 | RAG、向量库、跨任务长期记忆 |
| 当前进程中的暂停、调整后继续 | 数据库任务恢复、崩溃自动续跑 |
| 目标、证据、产物的简单版本关联 | 企业审批、租户、组织权限 |
| 确定性检查与有限修正 | 每一步都增加“反思 Agent” |
| 当前模型适配器的上下文控制 | 更换全部技术栈、引入第二套循环框架 |

基本文件边界、取消、超时和预算继续有效。学习 Deep Agents 的方法，不等于必须引入其整套实现。

## 2. 与阶段一相比，真正改变什么

| 阶段一 | 阶段二 | 保持不变 |
|---|---|---|
| 直接进入工具循环 | 简单任务直接执行；复杂任务维护可修改计划 | Runner 仍是唯一循环控制者 |
| 全部近期历史累计发送 | 完整历史与本轮模型视图分离 | 原生工具调用与结果仍须配对 |
| 返回超限即停止 | 有界完整结果可落盘，向模型返回引用并按需回读 | 不允许无限读取或写入 |
| 目标约束在样例配置中固定 | 从明确结构化约束开始，支持用户确认的有限变更 | 模型不能自行改变验收条件 |
| 有报告和证据即可基本检查 | 按当前目标版本验证范围、引用和产物用途 | 数字由工具计算，不能靠模型担保 |
| 一次缺项反馈 | 有限次、有具体缺项的修正循环 | 不清零预算，不无限自我反思 |

对阶段一文档的覆盖只限本表。未明确更改的行为继续沿用，例如输入文件运行中变化仍终止当前 Run，不能借“长任务”混用新旧资料。

## 3. 新执行链路

```text
明确目标 TaskBrief
        ↓
简单任务直接执行 / 复杂任务生成可更新计划
        ↓
┌──────────── 同一个 Runner 循环 ──────────────┐
│ 取当前目标、计划与证据索引                    │
│         ↓                                   │
│ 组装本轮上下文，必要时卸载旧内容或压缩         │
│         ↓                                   │
│ 单次模型决策                                │
│         ↓                                   │
│ 工具执行 / 计划更新 / 请求用户补充            │
│         ↓                                   │
│ 保存真实结果、工作文件和进展，再决定下一轮     │
└─────────────────────────────────────────────┘
        ↓ 模型提出最终交付
确定性检查 → 通过则完成
        └─ 未通过：具体问题反馈 → 有限修正 → 再检查
```

不要把“先计划”实现成必须按计划顺序机械执行。计划是供 Agent 调整的工作清单，实际行动仍根据工具观察决定。

## 4. TaskBrief：把目标从聊天文字里单独拿出来

长任务容易失败，并不总是模型忘了某条历史，也可能是系统从未明确“现在究竟要交付什么”。

建议为本次 Run 保存一个很小的任务简报：

| 信息 | 用途 | 谁可确定 |
|---|---|---|
| goalVersion | 当前目标版本，从 1 开始 | 程序 |
| objective | 用户目标与当前修订后的描述 | 用户输入，经程序保存 |
| constraints | 比较期间、允许资料、指标口径、渠道范围等 | 用户或预先认可的样例配置 |
| deliverables | 必須交付的报告类型及范围 | 用户或样例配置 |
| unresolved | 尚未确认、影响分析的问题 | 模型可提出，用户或证据解决 |

TaskBrief 不是一个新平台对象，也不要求设计数据库表；可以先是 RunState 中的结构化数据。

本阶段继续采用资料分析样例，constraints 的 Schema 是确定的。自然语言可帮助提出建议，但不能直接覆盖程序保存的约束。CLI 首先展示当前简报；出现冲突先确认，不带着互相矛盾的目标开始执行。

主模型上下文一直包含当前 goalVersion 和约束。原始请求保留用于追溯，但已替代的旧要求不能与新要求以相同权重并列。

## 5. 显式计划：用于定位进展，而不是制造思维链

### 5.1 怎样启用

每次任务在启动配置中选择 `DIRECT` 或 `PLANNED`：

- DIRECT：阶段一方式；不注册计划工具，不要求先写计划。
- PLANNED：适合多资料、多产物、存在待确认条件的任务。

先用人为选择做对照实验，不开发一套“自动判断复杂度”的额外模型路由，也不把这个实验选项做成复杂功能开关系统。

### 5.2 计划的最小形式

建议 3—6 项，最多 8 项。每项记录 stepId、简短目标、完成依据、状态、证据/产物引用。

示例：

1. 确认资料覆盖区间和指标口径。
2. 对齐字段，计算各渠道变化。
3. 对照背景资料，区分数据事实与假设。
4. 生成指定报告并检查证据。

不用输出内部思维链，不要求解释每个 Token 的推理过程。计划描述可执行事项即可。

状态采用 pending、active、done、blocked、dropped；串行运行最多一个 active。blocked 不等于失败，可先完成其他独立事项；dropped 需要理由且不能删除用户仍要求的交付。

### 5.3 一个 updatePlan 工具就够

模型通过控制工具 `updatePlan` 提交：expectedRevision、当前 goalVersion、reason、完整的计划项列表。首次 revision 为 0；成功后由程序递增版本。

程序必须验证：

- 目标版本和计划版本仍是当前值。
- stepId 唯一；修改项保留原 ID，新项生成新 ID；步骤数有上限。
- 状态值合法，active 不超过一个。
- 声称完成的步骤必须引用真实存在的本 Run 证据、产物或已记录的用户答复；纯准备步骤可引用受控状态事件。
- 不能通过计划文本修改 TaskBrief、工具目录、输入文件或预算。

**done 只表示工作清单中声明完成，并不证明对应业务结论正确。**引用存在性检查不是语义验证，最终仍以交付检查和评测为准。

updatePlan 独占一个工具响应批次；若和业务工具或 requestClarification 混用，整批返回 MIXED_CONTROL_BATCH，不实际执行其中任何一项。这样避免同轮既改计划又使用旧计划上下文写报告。

计划更新纳入工具调用预算。不允许用反复改标题或切状态刷新“取得进展”的计数。

## 6. 工作区：让模型可以忘细节，但不能丢证据

### 6.1 四类内容分开

```text
input/                         用户提供的只读资料
work/<runId>/                  工具结果、阶段笔记、上下文摘要
output/<runId>/                 面向用户的报告
traces/<runId>.jsonl            执行事件
```

新增 workRoot，和 input/output/traces 相互独立，不让模型传任意路径。所有引用仍限定在当前 Run；不设计跨 Run 的文件继承或共享记忆。

| 内容 | 性质 | 能否单独充当结论证据 |
|---|---|---|
| 源资料片段 | 原文资料，可能包含错误或指令注入 | 可证明“资料写了什么”，不自动证明现实事实 |
| 计算结果 | 工具计算出的结构化值及输入摘要 | 可以证明对应输入和算法下的计算结果 |
| 阶段笔记/历史摘要 | 模型生成的辅助记忆 | 不能替代原始计算和用户确认 |
| 交付报告 | 当前目标下生成的产物 | 必须关联实际证据，不能自证正确 |

### 6.2 只增两个工作区工具

**saveWorkNote**：title、content、sourceRefs。保存简短的阶段结论、待办和疑问；程序生成 noteId，标注 MODEL_DERIVED。引用必须真实存在，但引用存在不意味着笔记描述正确。

**readWorkItem**：itemId、startLine、maxLines。回读当前 Run 已登记的工具结果、笔记或产物；返回实际行号、内容摘要、来源类型、hasMore 和 nextLine，不开放任意路径。

记录一旦落盘就不覆盖：修改笔记或报告生成新版本，旧版保留但不自动进入当前模型视图。任务简报和计划状态通过受控入口修改，不把自由笔记当控制文件。

### 6.3 工具结果过大时怎么处理

先区分两种上限：

- **计算/读取硬上限**：文件大小、行数、分组数等资源边界。超出仍拒绝，不因为可以落盘就无限放开。
- **给模型的内联上限**：允许工具生成有界完整结果，但单条返回超过内联阈值时保存为工作项。

落盘成功后，用同一个 callId 返回合法的结果信封：ok、itemId、内容摘要、原始字节数、类型、短预览、需要时如何回读。预览必须标为不完整，不能把截断后的数值表当完整结果。

计算证据存的是完整结构化结果，完成检查读证据表或受控存储，不依赖模型看过的预览。按需回读不等于重新执行原工具，更不能重做已经发生的写操作。

落盘失败就不能返回“已保存”；缺失、摘要不匹配或越界引用都返回明确错误。当前 Run 的工作区内容非授权变化属于失败，不自动采纳。

## 7. Context Engineering：历史不是每轮都要发送的输入

### 7.1 建立两个视图

- **执行记录**：原生对话、工具请求/结果、状态与引用，记录实际发生过什么。
- **本轮模型视图**：由当前目标、计划、必要证据、摘要和最近完整交互组成，决定这次让模型看到什么。

构造模型视图不改写工具账本，不改变 TaskBrief，也不让压缩摘要更新真实产物和计划。

即使完整历史暂时保存在内存，也不等于必须整段发送。总调用数和单次输出仍有硬限，避免变成无限历史容器。

### 7.2 按优先级组织模型输入

| 区块 | 内容 | 是否允许丢弃 |
|---|---|---|
| 稳定规则 | 工具边界、行为约束 | 不可 |
| 当前任务简报 | 目标版本、限制、交付要求 | 不可，必须程序注入 |
| 当前状态 | 计划、待回答问题、最近检查问题、有效证据索引 | 不可被摘要猜测覆盖 |
| 历史摘要 | 已处理事项、已否决路径、回读引用 | 可替换，但标为辅助且可核查 |
| 最近完整交互 | Assistant 工具调用与全部对应结果、必要用户消息 | 以完整组保留 |
| 本轮所需资料 | 工具回读的有界片段 | 根据步骤选取，不全量注入 |

文件内容、工具内容、笔记与摘要保持“数据”来源身份，不因为压缩而升级成系统指令。程序的稳定规则与真实用户约束单独保存，不把整个“记忆摘要”塞进最高优先级消息。

### 7.3 先做无需额外模型的整理

第一步只做：大结果引用化、去掉重复注入的说明、只放当前计划版本、用程序生成的证据索引替代重复大表。

这些规则可解释、可测试，应先于模型摘要实现。不要一上来就让另一个模型决定所有历史该留什么。

### 7.4 什么时候压缩

记本次模型可用输入预算为 B：

`B = min(配置的输入上限, 模型上下文窗口 - 预留输出 - 安全余量)`

消息、工具 Schema 与模型所需协议元数据都计入。建议达到 B 的 70% 时准备压缩，压缩后争取降到 50% 左右；这些是实验阈值，不是模型 API 的通用常数。

无精确 Tokenizer 时记录估算方式并保留更大余量；不能把字符数等同于精确 Token 数，也不在供应商拒绝后无界重试。

只有在一次完整工具批次已经回填、没有待回答控制调用的边界才能替换模型视图。WAITING_INPUT 期间不切断 requestClarification；用户回答配对完再压缩。

### 7.5 压缩协议

1. Runner 在下一次模型请求前检测阈值，固定当前 goalVersion 和计划版本。
2. 选出最老的若干**完整交互组**；保留当前控制状态和最近必要交互。
3. 对可安全引用化的结果先卸载；仍需摘要时，发起一次受控、无工具的摘要请求。
4. 摘要只接收选中的有界历史片段和必要参考，不把已经超出窗口的全量历史再次发送给摘要模型。
5. 摘要包括处理范围、已做事项、未决问题、来源引用、否决路径；必须验证结构、长度和引用存在性。
6. 采纳前核对 goalVersion、planRevision 和被处理历史范围仍与请求快照一致，且没有取消、超时或待确认目标修订；不符合则丢弃候选摘要，不覆盖当前视图，已消耗请求仍计入预算。
7. 由模型适配层构造新视图并重新计数，确认消息协议和输入预算合法后再使用；TaskBrief、当前计划和待办状态从程序状态重新注入，不从摘要恢复。

摘要请求使用相同供应商/模型也可以，但它是一次受预算控制的无工具转换，不是一个有自主循环的子 Agent。不开第二个调度器，不允许摘要器执行业务工具。

### 7.6 消息协议和失败处理

原生 Assistant 调用与全部 Tool 结果必须作为完整组移动或保留。仍保留的组，其 callId 和供应商必需元数据原样保存，不能只把文本拷进一个新消息。

删除旧组以后，不伪造历史工具响应；用明确的历史资料摘要和引用表达旧信息。若供应商会话依赖不可重建的服务端状态，必须通过其支持的方式建立新请求视图并做兼容测试，不假定直接删除本地消息就生效。

- 摘要内容失败或引用非法：不切换视图，旧视图仍在；能靠确定整理压到预算内则继续，否则 STOPPED/CONTEXT_LIMIT。
- 摘要仍太大：不在同一边界反复摘要；最多一次摘要尝试，必要时停止。
- 固定规则＋任务简报＋必要完整交互本身就放不下：明确停止，不偷偷删约束。
- 摘要里出现新结论、新权限或“用户已确认”：不更新真实状态；关键事实需要回读证据。
- 等待压缩时取消或超时：同样停止，迟到摘要不能复活任务。

以后每次压缩都保留底层证据引用；旧摘要可以被新摘要覆盖其展示位置，但不能成为原始证据的唯一保存处。

## 8. 用户中途调整目标：改变任务，而不是让旧答案换个标题

### 8.1 本阶段有限支持

只允许修改样例 Schema 已定义的范围：日期窗口、渠道集合、报告类型及是否需要附录。新增工具、扩大目录访问、修改源文件或完全不同的业务任务仍应新开 Run。

CLI 增加一个 `revise` 操作：可以用简单表单或结构化参数提交补丁，展示旧值→新值并明确确认；不要求本阶段实现任意自然语言的可靠目标解析。

模型可建议调整，但只有用户确认入口能推进 goalVersion。`/answer` 仍只回答问题，不隐式授予范围变更。

### 8.2 安全应用时机

1. 收到修订请求后，输入线程只登记 pendingRevision，Worker 暂停调度下一项工具；不立即改 TaskBrief 或取消旧问题。
2. 在途工具可能已经完成；先记录它的真实结果，不假装回滚。当前批次尚未执行的调用逐个记录并回填 NOT_EXECUTED_SCOPE_REVISION，不留下未配对的普通工具调用。
3. Worker 进入 WAITING_INPUT，并区分等待原因 GOAL_REVISION 与 CLARIFICATION。已有澄清问题仍保留其 callId，修订确认不能冒充该问题的答案。
4. 展示补丁的旧值→新值，只允许一个待确认修订。用户拒绝或补丁校验失败时，原目标、计划和旧问题均不变；若原有澄清问题则回到该等待，否则从完整消息边界重新决策。已跳过的普通工具不自动重放。
5. 用户确认且补丁校验通过后，才给旧的未回答澄清 callId 回填 QUESTION_SUPERSEDED，随后原子更新 TaskBrief、goalVersion 和完成检查条件。
6. 保留旧计划的历史版本，但不继续把它作为新目标的当前计划。PLANNED 模式在新计划获准前只允许 updatePlan 或 requestClarification，不执行普通业务工具；DIRECT 模式无此要求。
7. 新计划从旧计划提出必要修改，沿用未变事项的 stepId，并以新 goalVersion 和当前 expectedRevision 提交；planRevision 在本 Run 内持续递增，不因改目标归零。旧 done 项只有依据适用于新范围时才可保留。
8. 旧产物仍记录为原 goalVersion，不自动变成新目标的有效交付，再由模型选择必要的补查、计算与生成。

如果在途模型响应返回前已登记修订，不采用它的旧目标最终答案，也不执行其工具请求；合法调用按上述规则配对为未执行，再进入修订确认。取消、硬超时和协议错误优先于修订，不因新目标复活终态任务。

等待用户确认的时长不计主动执行时间，已有计数不清零。修订确认、取消、模型与工具返回都由同一个 Worker 串行推进状态；终态提交前必须检查是否有待处理修订，避免一边完成旧目标一边接受新目标。

### 8.3 证据与产物怎样重新使用

- 输入与分析结果是不可变事实，不因目标修订而删除。
- 只有范围、口径、输入摘要均满足新要求的旧证据，才可继续作为新目标的依据。
- 旧报告即使路径存在，也不能直接判新目标完成；新报告绑定新 goalVersion。
- 仅含局部预览的旧结果不够支持新范围时，先回读完整结果或重新计算。
- 新文件加入或原文件改动不在这个修订机制中接管，仍按 INPUT_CHANGED 的边界新开任务。

预算、错误计数和已发生副作用不因“修改目标”清零。

## 9. Verification：让失败反馈指向下一步行动

本阶段不默认加一轮“请反思一下”，而是把 CompletionCheck 变成有具体结果的检查：passed、可定位 issue 列表、对应产物与证据引用。

报告生成工具成功，仅说明文件落地；最终还需要检查：

1. 产物 kind 是 DELIVERABLE，goalVersion 等于当前目标。
2. 产物实际引用的分析覆盖当前范围与口径，而不是 Run 中碰巧存在另一份正确计算。
3. 证据引用、输入摘要、输出摘要有效，缺失与冲突有明确记录。
4. 声明的交付类型全部存在，计划状态不能替代产物。
5. 模型正文与程序附录区分；数字表格由程序输出，文本结论的质量通过专项评测检查。

提供一个只读的 `checkDeliverable(artifactId)` 工具，返回同一检查器的结果。即使模型没调用它，Runner 收到最终回答时也会执行检查，不能被绕过。

检查不通过时反馈例如 SCOPE_MISMATCH、MISSING_EVIDENCE、STALE_GOAL、MISSING_DELIVERABLE，而不是笼统“再想想”。在剩余预算内最多允许 2 轮产物修正；同一产物重复检查不算新成果，修正次数也不能通过换产物 ID 无限刷新。

所有交付产物维持只增版本、不覆盖。创建新文件不自动完成任务；新版本必须重新检查。

### 部分完成怎样表达

当前 RunResult 保留产物和未完成项。如果要求的核心资料无法确认，就 WAITING_INPUT；如果用户决定不补充或预算用尽，就 STOPPED 并列出限制，不标 COMPLETED。

只有用户明确把交付要求修订为“只需提交已知事实与限制说明”，并经新目标检查通过，才可按这个收窄目标完成。模型不能自行降低验收标准换取成功状态。

## 10. 预算与停止：增加能力不意味着无限运行

建议长任务实验从以下限制开始：

| 项目 | 建议起点 |
|---|---:|
| 全部模型请求 | 40 次，含摘要和最终回答 |
| 全部工具请求 | 80 次，含计划、笔记、回读与检查 |
| 总主动处理时长 | 900 秒，单次模型仍不超过 60 秒及剩余时长 |
| 每 Run 的摘要请求 | 最多 3 次，并计入上述 40 次 |
| 计划项数 | 最多 8 项 |
| 阶段笔记 | 单份最多 8 KiB |
| 工作项 | 单份最多 1 MiB、每 Run 总计最多 16 MiB |
| 模型内联工具结果 | 建议最多 4 KiB；回读单页最多 4 KiB |
| 产物修正 | 每 Run 最多 2 轮，不因目标修订而重置 |

原来的源文件、CSV 行数和分组计算上限不因卸载机制自动放大。模型输出上限按第一阶段选择的模型能力配置。

工作区总额、输入预算和模型调用预算分别检查；达到任一硬限就给明确停止原因，不能只控制 Token 而无限写文件。

除第一阶段相同请求循环检测外，加一个可解释的“无有效进展”计数：连续 6 轮主循环没有新增有效证据、有效产物或已确认用户信息，就停止。计划改字、写无来源笔记、反复读相同页、反复检查同一产物，都不能清零。

新引用要按源摘要＋范围＋操作标识比较语义内容，不能只因生成了一个新 ID 就算进展。此规则是实验启发式，保留全局预算作为最终边界。

## 11. 如何接在现有骨架上，而不是推倒重写

以下描述的是职责演进，不是本次源码清单：

| 现有职责 | 第二阶段建议演进 |
|---|---|
| agent：Runner、Spec、Snapshot | 增加 TaskBrief、PlanState、goalVersion 和待修订状态；保留一个执行循环 |
| model：Gateway、Session | 适配层增加估算输入和准备压缩视图的能力，保留原生消息组及元数据 |
| tool：Catalog、Outcome | 注册计划、工作笔记、回读与检查工具；错误沿用可继续/终止边界 |
| workspace：Workspace、Artifact | 增加 workRoot、工作项索引、产物 kind、来源与目标版本 |
| trace：Event | 增加计划修订、上下文压缩、目标修订、检查结果事件 |
| sample/analysis | 实现比较约束 Schema、证据适用性和报告检查，不把字段规则写进 Runner |

上下文策略可以是 model 包内的具体组件，不必马上建一个通用策略框架。Runner 向适配层提供当前简报/计划/索引，适配层掌握原生消息；不要同时在 Runner 和 ModelSession 维护两套互相漂移的 transcript。

如果压缩需要额外模型请求，先由 Runner 的统一预算授权并记录次数，适配器不能在 nextResponse 内隐藏几次额外调用。

继续单 Maven 模块、单进程、单任务串行执行。没有必要为增加工作区或计划引入 Python、数据库或图编排平台。

## 12. 学习资料及实施顺序

先按配套实验逐步实现：工作区引用 → 计划 → 确定性上下文整理 → 可选模型摘要 → 目标修订 → 交付修正。每一步回归阶段一，不一次性改完所有能力再排错。
