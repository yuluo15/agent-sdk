# 我们要搭什么主体

2026-09-15 · 重新聚焦版 · 只出方案，不写实现代码

## 1. 先把目标说准确

这是一套从零设计的系统，不以已有登录、组织、工单或企业业务系统为前提。

目标顺序是：

1. **通过亲自构建，理解现代 Agent 是怎么工作的。**
2. **搭出一个真正能完成任务、能扩展的 Agent 主体。**
3. 在主体成熟后，将它逐渐发展为可交付的企业级项目，而不止是一次性演示。

所以，我们现在要设计的不是一整套企业管理平台，而是一个 **Agent 引擎**。界面、登录、组织、计费、运营后台都不是当前主线；阶段数量由学习和能力依赖决定，不照搬 P0—P100。

## 2. 主体到底是什么

> Agent 接收目标，结合当前上下文决定下一步，调用工具获取信息或执行动作，再根据真实结果继续决策，直到完成、需要用户补充或触发停止条件。

它的骨架是：

**模型决策 → 执行工具 → 观察结果 → 更新上下文 → 再次决策。**

这与“发一次 Prompt，得到一段回答”不同，也与“预先写死 A→B→C，顺便让模型填参数”不同。固定工作流有价值，但学习 Agent 首先要看清：哪些步骤由程序规定，哪些下一步由模型根据结果选择。

“通用”不是不用设计业务就什么都能做，而是 **换工具和任务说明，不必重写执行引擎**。

## 3. 第一版主体架构

```text
用户目标
   │
   ▼
Agent Runner ───────────────────────────────────┐
   │                                           │
   ├─ Context：本轮要给模型看什么                │
   │       ↓                                   │
   ├─ Model：回答、请求工具，或请求补充信息        │
   │       ↓                                   │
   ├─ Tool Executor：检查并执行工具              │
   │       ↓                                   │
   ├─ Observation：把真实结果写回上下文 ──────────┘
   │
   └─ 输出：最终结果 / 补充问题 / 明确的停止原因

贯穿执行：Run State + Events
记录任务进展、工具调用、错误、用量和产物。
```

这是一段循环，不是一排微服务。第一版完全可以在一个 Java 进程中实现。

| 核心部分 | 现在解决的问题 |
|---|---|
| Agent 定义 | 这个 Agent 的目标、说明、模型、可用工具与执行限制是什么 |
| Runner | 谁控制循环，何时继续，何时停止 |
| Model 接入 | 如何把上下文发给模型，并接收结构化工具请求或回答 |
| Tool Executor | 如何把模型提出的调用转换为真实函数执行 |
| Context | 如何保留目标、消息和工具结果，而不无限堆积内容 |
| Run State / Events | 如何知道它做过什么，以及失败在了哪里 |

这些是逻辑职责，不要求建六个工程，更不要求首期建立六套注册中心。

## 4. 怎么调整原来的架构图

| 原图元素 | 新方案中的位置 |
|---|---|
| Agent Master / Supervisor | 先变成一个 Agent 的执行循环；真正需要委派时再引入 Supervisor |
| 餐饮、酒店、文旅 Agent | 后续用不同任务说明、工具和知识组成能力包，不先写三套系统 |
| Model Gateway | 初期一个模型适配入口即可，路由、负载均衡后置 |
| Prompt 管理、Agent Registry | 初期用简单配置表达，不做后台和注册服务 |
| Tool Registry | 初期是工具定义列表或本地注册表，不是独立平台 |
| Memory / 知识检索 | 先会话与任务上下文，后续分开引入 RAG、长期记忆 |
| MCP Gateway / Server | 先学会直接工具调用，再通过 MCP 接更多外部工具；不先造网关 |
| A2A | 独立 Agent 之间需要互操作时再研究，本地多 Agent 不必使用 |
| Observability | 先把每轮调用和结果看清楚，不先搭完整运维平台 |

关键变化：**不是删除能力，而是先把 Agent 中心建起来，再从它向外长。**

## 5. 核心机制的教学样板：任务型资料分析 Agent

建议用不依赖现成企业系统的任务验证基础机制：

> “分析工作目录里的本月、上月销售数据，找出变化最大的渠道，结合指标说明解释变化，生成一份带数据依据的报告。”

它需要发现文件、检查字段、计算指标、阅读说明、补查信息、生成报告，能实际暴露 Agent 的核心问题，而不是只做问答演示。

工具先控制在几个：列出工作目录、查看表结构、执行受限统计、读取说明、写入报告。

工作目录由用户指定，原始资料只读，产物写入单独输出目录。初期不开放任意系统命令，也不依赖登录或组织模块来保护本地文件边界。

数据分析只是练习载体，不把通用引擎做成报表系统。后续换成调研、知识助手或行业查询，应主要更换能力包。

实现前的应用方向比较见 [14-应用场景选型：为什么先做技术支持Agent](14-应用场景选型：为什么先做技术支持Agent.md)。当前已沿单产品技术支持的调查与回复草稿方向展开 [15-核心工作流](15-技术支持Agent：核心工作流与决策边界.md) 和 [16-工具契约与调用逻辑](16-技术支持Agent：工具契约、调用样例与验收.md)，保留销售样例作核心回归；新场景有独立契约，不替换旧验收，也不代表真实产品、接口和生产能力已经具备。

## 6. 哪些先不做，哪些不能完全不做

**明确后置：**登录、组织、租户、计费、可视化搭建器、完整管理后台、微服务拆分、集中式 MCP Gateway、复杂 A2A 网络。

**贴着核心保留：**工具范围、参数检查、循环上限、超时、取消、执行记录和少量任务测试。它们不是外围功能，而是防止 Agent 乱执行、死循环、无法排错的基本控制。

本地受控试验不需要先建企业身份系统；将来向多人或真实企业数据开放时，再补齐对应身份和授权，不能把“后置”理解为生产环境也不需要。
