# 应用场景选型：为什么先做技术支持 Agent

日期：2026-09-22  
定位：实现前的方向建议与首版范围，不是新增第六阶段，不包含实现代码。  
配套：[主体与目标](00-先读这个：我们要搭什么主体.md) · [总实施指南](13-总实施指南：从方案到可用Agent.md)

后续已按该方向展开 [15-核心工作流与决策边界](15-技术支持Agent：核心工作流与决策边界.md) 和 [16-工具契约、调用样例与验收](16-技术支持Agent：工具契约、调用样例与验收.md)。本稿保留选型依据；进入设计不等于真实产品、业务接口或生产能力已经具备。

## 1. 先给明确结论

**建议选择「企业软件产品的技术支持 Agent」，第一版定位为人工客服／技术支持人员的问题调查与回复助手。**

把它说得更具体一些：

> 支持人员交给它一个产品问题。它根据问题查阅对应版本的文档、查询被授权的任务状态，发现信息不足时提出补充问题，最后交付有证据的问题分析、客户回复草稿和必要的升级交接材料。

首个切口建议限定为：**单个软件产品中“资料导入失败，或导入后内容不可检索”这一类支持问题。**

首版是文字、异步、只读调查，草稿交人工审核；不直接接待所有客户，不接电话，不自动修复、发送回复或关闭工单。

这不是在“客服”和“知识库”之间各做一半，而是明确分工：

- **业务场景：**帮助支持人员处理产品问题。
- **知识库／RAG：**查找产品说明和排查依据的能力。
- **Agent：**根据中间结果选择调查、追问、补查或停止的执行主体。
- **人工支持人员：**确认建议适用性，负责实际对外沟通和后续操作。

选择它的主要理由不是“客服热门”，而是：**有自然的多步调查任务，结果可以核对，起步不必拥有生产写权限，并且有机会逐步进入真实工作流程。**

本稿给出首选建议和验证办法，不把建议写成你已经确认的业务决定，也不假设已经存在客户、工单数据或可用的业务接口。

## 2. 选择依据：什么已经知道，什么仍是假设

### 2.1 已明确的约束

1. 第一目标是通过构建理解 Agent，而不是最快发布一个聊天页面。
2. 第二目标是形成可扩展、可交付的主体，不止一次演示。
3. Java 为主，复用已有五阶段设计，不另起复杂平台。
4. 当前不以已有登录、组织、工单系统或生产 API 为前提。
5. 五阶段方案已经齐备，不等于代码实现和生产验收已经完成。
6. 本轮只选择场景、给方案，不修改项目代码。

### 2.2 需要验证的假设

- 能找到一个边界清楚的软件产品，以及对应版本的说明和排查知识。
- 其支持问题中确实存在“只查文档不够，还需要查当前状态”的一类任务。
- 后续能获得授权的只读状态查询，或者先由支持人员导出必要记录。
- 有熟悉该产品的人可以判断建议是否正确，而不只是让另一个模型打分。
- 人工审阅草稿的成本小于从头调查、撰写的成本。

这些不是已经证实的事实。前期可以用虚构夹具验证工程机制；要证明业务价值，仍需真实使用者、授权资料和独立复核。

**本次分析依据既有需求和通用工程经验，不是实时市场调研、竞品排名或客户访谈结果。**不使用未经验证的市场规模、节省比例或付费意愿作为结论依据。

## 3. 我们应按什么标准选，而不是按功能热度选

先过三道门槛：能获得或构造可核查资料；能定义完成与失败；能在当前条件下合法、安全地运行。过不了门槛，功能再先进也不适合作为首版。

过门槛后，按以下顺序比较：

| 标准 | 具体要问什么 | 对本项目的重要性 |
|---|---|---|
| 真实的 Agent 需求 | 下一步是否需要根据新观察变化，而不是永远固定检索再总结？ | 直接决定能否学到执行循环，而非只学 Prompt |
| 可验证的交付 | 结论能否对应原始记录、版本和正确处理方式？ | 否则很容易把流畅回答误当成功 |
| 数据与工具可得性 | 没有企业系统时能否起步，转向真实数据后是否有合理接入路径？ | 防止长期停在模拟演示 |
| 范围和副作用可控 | 能否先只读、少工具、单任务类型，错误是否可在对外生效前发现？ | 避免被外围集成和不可逆动作拖住 |
| 实际使用价值 | 谁使用、替代哪部分工作、谁复核、用什么判断值得保留？ | 防止只有开发者觉得有趣 |
| 扩展与复用 | 换产品主要改知识、工具和检查器，还是必须重写 Runner？ | 检验通用主体是否真的成立 |

不采用“给每个方向打到小数点后两位再加权”的做法。当前没有用户调研和测量数据，精确分数只会掩盖假设；下表是针对本项目的定性取舍，不是行业排名。

## 4. 候选方向比较

| 候选方向 | 最值得学习的部分 | 可验证性与起步条件 | 主要代价 | 本项目判断 |
|---|---|---|---|---|
| 纯智能知识库／文档问答 | 检索、引用、拒答、知识更新 | 文档容易准备；可标注答案和来源 | 不少任务一次检索即可，容易停留在 RAG 问答 | 适合作为基础能力，不作为首个产品定位 |
| 直接面向客户的文字自动客服 | 多轮澄清、业务查询、政策判断、转人工 | 需要真实政策、服务对象和可靠兜底；错误会直接触达客户 | 渠道接入、会话连续性、服务承诺与对象权限较早出现 | 有后续空间，但不是当前第一步 |
| 电话／实时语音客服 | 语音理解、打断、低延迟协作 | 要同时验证听懂、说对、时机对和业务处理 | ASR、TTS、线路和实时状态会分散核心学习精力 | 明确后置；复杂不等于更适合起步 |
| 单产品技术支持助手 | 动态调查、工具调用、证据核对、追问与升级 | 可构造已知故障；真实应用需要产品专家和状态记录 | 依赖文档质量，必须限制“看似合理”的错误诊断 | **首选：只读调查，人工审核草稿** |
| 经营数据分析助手 | 数据发现、计算、指标解释、报告 | 数字易核算；真实分析依赖稳定口径与数据质量 | 复杂接入容易变成 BI／数据治理项目，因果解释仍难验证 | **备选：固定口径、只读分析**；保留现有教学夹具 |
| 企业内部办事助手 | 动作确认、幂等、流程状态、失败恢复 | 有稳定业务 API 时结果较易核对 | 写权限、身份、审批和副作用处理早早成为前提 | 更适合主体稳定且有明确业务接入后 |
| 通用研究／调研助手 | 规划、长上下文、多来源综合 | 容易发起任务，难定义开放问题的完整性 | 来源时效、网页变化、范围失控、结果评价主观 | 可作能力实验，首版产品应进一步收窄 |
| 通用编码／运维助手 | 文件工具、执行反馈、测试与修正 | 有仓库和测试时可验证部分结果 | 环境和任务差异大；任意执行、生产运维需要更强隔离 | 不作为当前主线，避免先造安全执行平台 |

### 为什么不是直接选智能知识库

智能知识库本身有价值，但“检索到几段内容，再总结”不一定需要 Agent。若首版大部分问题都如此，普通检索问答可能更简单、便宜、稳定。

技术支持场景会自然提出额外问题：**文档说支持，为何这一次失败？是版本不匹配、任务尚未完成，还是状态根本查不到？**这才给模型根据真实观察决定下一步的空间。

### 为什么不是直接选全自动客服

“辅助支持人员”与“直接代表企业服务客户”是两个不同的责任边界。后者需要同时处理错误承诺、客户身份、上下文串线、投诉升级和真正的转人工，不是加一个聊天入口就完成。

人工审核可以降低错误对外生效的机会，但不保证安全或准确；资料权限、模型外发限制和内部信息隔离仍须程序控制。

### 为什么经营分析是备选，而不是首选

它和已有 CSV 实验衔接最好，数值也好验证。但若希望主要学习 Agent 而非数据工程，需要避免把精力集中到数据仓库、跨源 SQL 和指标治理。

若你后续能获得稳定、授权的经营数据，却找不到可信的产品支持资料与复核人员，应该改选经营分析。**真实可得的资源，比本稿的抽象推荐更有决定性。**

## 5. 推荐场景必须具体到一次工作

### 5.1 谁在使用

首个用户是负责某一产品的一线客服或技术支持人员；不是所有公司员工，也不是直接访问网页的任意客户。

本地实验中可以由你扮演支持人员，人工导入一个问题包。这里的“工单”只是一个待处理问题及其资料，不要求先建设工单流转系统、客服工作台、排班或 SLA 平台。

### 5.2 用户把什么任务交给它

典型输入：

> 用户反馈资料导入后无法检索。请根据这个案例的产品版本、任务记录和对应说明，判断目前能确认的情况，列出还缺什么信息，给出可审核的客户回复草稿；证据不足时准备升级材料，不要直接操作用户环境。

可信任务范围由应用注入：当前案例、可查询对象、允许资料集合、产品版本和交付要求。客户原话是待核实的信息，不会自动扩大权限。

### 5.3 第一版只处理什么

**一个产品，一类问题族，三类有依据的调查分支：**

1. 输入格式不受当前版本支持，上传已接收但解析失败。
2. 导入处理完成，但索引尚在构建或尚未发布。
3. 状态明确失败，现有证据不能定位更深原因，需要整理材料交给人工技术人员。

另保留版本不明、记录缺失、资料冲突、无权限等异常样本，用来验证追问与停止。不要把所有异常都强行归入上面三类。

这个切口的优点是：产品说明与运行状态各回答不同问题，且能用受控资料构造可重复的分支。不要求同时开发一个真正的导入／索引产品。

可沿用第三阶段的虚构“星舟知识助手”作为教学名称，但本稿新增的故障样例和状态工具都只是建议，尚未实现，也不是原有 LITE／LOCAL 选型资料已经承诺的功能。

### 5.4 交付给支持人员什么

一份可以回读、审核的处理包，分开保存或展示：

- **内部调查摘要：**已确认事实、引用、版本、状态观察时间、未确定问题。
- **客户回复草稿：**解释目前可确认的情况、下一步建议或需补充的信息，不暴露内部诊断细节。
- **升级材料：**仅在需要时提供，包含已查范围、问题缺口、相关任务标识和证据，不编造根因。

“建议重新导入”“建议转技术人员”只是建议，不表示系统已经执行。首版不会创建远端工单、修改状态或发送消息。

**Agent 完成的是辅助调查交付，不等于客户问题已经解决。**任务运行状态、调查结论、实际业务问题状态必须分别表达。

## 6. 一次任务为什么需要 Agent，而不是只有 RAG

以“资料导入后搜不到”为例，以下是可能路径，不是每次必须执行的固定顺序。

| 当前观察 | 下一步合理选择 | 不能直接得出的结论 |
|---|---|---|
| 问题没有产品版本或任务标识 | 向支持人员提出明确的补充问题 | 猜一个版本，或遍历所有客户任务寻找“相似案例” |
| 用户说“导入成功”，记录只显示上传被接收 | 继续核实解析／处理状态 | 上传成功等于内容可检索 |
| 解析状态为失败，错误码指向格式不支持 | 回读对应版本的格式说明，核对输入类型 | 不看版本便套用最新版支持列表 |
| 处理成功，索引仍在构建 | 查询该任务关联的索引状态，解释当前可见性限制 | 承诺几分钟后一定完成，或自动持续轮询 |
| 索引构建失败，但没有进一步诊断依据 | 汇总已确认失败位置和缺口，生成升级材料 | 自行断言磁盘不足、权限错误或数据库损坏 |
| 当前文档与状态互相矛盾 | 核对适用版本，必要时追问或升级 | 选择一份更像答案的材料掩盖冲突 |
| 状态查询超时或越权 | 如实记录无法确认，不扩大查询范围 | 把查不到解释为任务不存在或系统故障 |

一条正常实验路径可以是：

1. 支持人员交入案例，程序限制可访问对象。
2. Agent 发现缺少任务标识，提出问题，等待补充。
3. 查询任务后确认：文件已接收，但解析失败；结果包含输入格式和产品版本。
4. 回读同版本说明，核对该格式确实不受支持。
5. 生成草稿：区分上传与解析，说明当前证据支持的失败原因，给出文档允许的下一步；不说“已为您修复”。
6. 检查产物确实引用了该任务记录和相应文档，由支持人员审核。

同样的自然语言问题，换成“索引仍构建中”的状态，下一步和结论就应改变。这种**受证据驱动的分支变化**是重点，不是工具调用越多越好。

反过来，如果真实案例证明三步固定检查就足够，应让程序完成固定部分。简单政策问题走检索问答，明确错误码走确定性规则，只有存在调查空间的部分使用 Agent；不必先开发智能路由平台，实验时人工选择模式即可。

## 7. 首版的能力边界

### 7.1 需要什么，不需要什么

| 范围 | 首版建议 |
|---|---|
| 入口 | CLI 或本地案例输入；暂不做对客聊天渠道 |
| 输入资料 | 当前问题、必要补充信息、当前产品版本与受控对象范围 |
| 知识 | 少量已整理、带版本和来源的产品说明、错误码与处理边界 |
| 查询 | 只读获取任务状态和关联索引状态，返回有界字段 |
| 行动 | 自主选择必要查询、回读、追问与草稿生成 |
| 输出 | 本地产物，内部材料与对客草稿明确区分 |
| 不开放 | 任意 Shell／SQL、原始日志全文、自动重建索引、修改配置、发邮件、退款、关闭工单 |

工具层只需少量职责；以下是候选名称，不是本轮冻结的 API 或已存在的接口：

- `readSupportCase`：读取本次获准的问题包，不搜索全部客户历史。
- `getImportJob`：查询被授权任务的状态、版本、必要输入元信息和关联索引标识。
- `getIndexStatus`：仅查询该案例获准的关联索引状态。
- 知识读取：前期使用受控文件回读；第三阶段使用已有 `searchKnowledge`／`readKnowledge` 模式。
- 复用 `requestClarification` 和产物写入能力；第二阶段以后再按需使用工作区、计划和检查。

不为了“工具丰富”额外开放业务写接口。模型得到一个对象标识也不代表被授权查询该对象；每次读取都由工具端核验案例范围。

### 7.2 没有真实企业接口，怎么启动

先建立一个独立的虚构案例集和本地状态夹具，工具从中真实读取数据，返回带来源、版本和时间的结果。它是测试环境，不是把答案直接塞进系统 Prompt，也不能称为生产集成。

状态夹具与文档至少能分别改变：同一问题换版本、换任务状态或缺少一个字段，Agent 应据此采取不同路径。确定性检查器和标准答案不交给模型照抄。

后续接真实产品有两条路径：

- 经授权导出的资料与任务记录：足以验证一次基于快照的调查，但必须标明采样时间，不能声称它反映当前状态。
- 经批准的只读 API：工具适配器提供受限字段和对象级检查，才能验证在线状态调查。

MCP 是后续替换连接方式的实验，不是拿不到业务数据时的解决办法。不要为了连接协议先建设网关。

### 7.3 安全边界从这里就要存在

- 外部资料、客户描述和历史回复不能指挥工具越权，也不能覆盖系统规则。
- 返回诊断信息前移除凭据和无关个人信息；“只读”不等于没有数据泄露风险。
- 若使用外部模型，先明确哪些信息可以外发，不能把人工审核输出当成输入数据保护。
- 对客草稿不自动包含内部路径、原始日志或敏感标识；提交人工审核前也应做必要的字段与内容检查。
- 不把客户对话、任务状态或模型猜测自动沉淀为长期记忆。
- 转入真实多人或多客户环境前，必须补身份、对象级授权和隔离；本地单人实验的范围约束不等于生产权限体系。

## 8. 怎么证明它有用，而不是又一个演示

需要两条互不替代的证据链：**工程行为正确**，以及**实际帮助了支持工作**。

### 8.1 先做一组能反驳自己的案例

起步建议准备 24 个案例：12 个用于开发调试，12 个留作首次盲测。数量是小型实验建议，不是统计保证；同一案例换几种说法不算多个独立业务样本。

案例覆盖：格式不支持、索引处理中、失败但根因未知、缺任务信息、版本冲突、记录不可用、越权对象、恶意资料指令、用户表述与实际状态不符，以及一个只需知识问答的简单问题。

每个案例单独登记：

- 被允许读取的对象、版本和观察时间。
- 可以确认的事实及其证据；不可确认的事项。
- 合理的后续动作与必须询问的信息，不限定唯一工具顺序。
- 可接受的交付结果，以及禁止出现的断言或动作。

开发集和盲测集应包含不同的状态／版本组合，避免只换问题措辞。虚构案例的答案由夹具事实决定；进入真实试验后，需要产品人员独立复核。

### 8.2 三种方案必须同场比较

| 方案 | 内容 | 用来检验什么 |
|---|---|---|
| A：普通知识问答 | 只根据批准的产品资料回答 | 这类问题是否真的需要动态状态，而非更好的 RAG 就足够 |
| B：固定调查流程 | 程序按预设步骤读同样的状态和知识，再生成草稿 | 收益是否来自接入了工具，而不是来自 Agent 自主决策 |
| C：受控 Agent | 在相同批准工具和资料范围内选择调查、追问和结束 | 动态选择是否改善混合问题和信息不足问题的处理 |

A 缺少动态工具，天然信息不同，不能只靠 C 胜过 A 就证明 Agent 更好。**B 与 C 的比较才更接近检验自主调查的增量价值。**

B／C 使用相同模型、资料版本、对象权限、最大生成／工具预算与时间上限；实际调用、Token 和耗时分别记录，不要求用满额度。固定流程可以少用模型，不能故意把它做差。缺信息时给各方案相同的可获得补充材料，记录提问成本。

### 8.3 不只看“回答像不像”

| 指标 | 应怎样看 |
|---|---|
| 事实和证据准确性 | 关键事实是否由该案例、该版本的记录支持；不是只检查引用编号存在 |
| 适当结论 | 能确认时正确判断；证据不足时明确缺口，不把全部问题都升级来获取表面安全 |
| 不必要追问／升级 | 已有信息足够时是否仍把任务退给人，增加额外工作 |
| 草稿可采用程度 | 产品人员区分可直接采用、轻微修改、需重写；不能让模型自评替代 |
| 人工总耗时 | 包括补资料、审阅、纠错和重写，与原人工处理路径对比 |
| 时延与成本 | 完整任务的模型、工具、检索及重试开销，不只统计最后一轮 |
| 严重边界错误 | 越权读取、敏感内容泄漏、无依据承诺、伪造已修复或重复副作用，单独报告 |

人工选择案例、准备资料的时间也应记录，避免让 Agent 看起来省时、实际把工作转移给输入整理人员。对比人工处理时，避免让同一人刚做完原案例便立即做辅助版本而产生记忆优势。

### 8.4 完成检查与业务成功分开

场景自己的检查器至少核验当前案例与目标、真实产物、引用来源／版本、关键状态时效和交付类型；不能沿用销售样例的“必须有计算证据”规则。

可在已确认的 TaskBrief 中允许两种辅助交付：有依据的处理建议，或完成必要检查后仍有缺口的升级材料。后者不是故障已经解决，也不能用模板化“请联系技术人员”逃避本可完成的调查。

缺少可以补充的关键标识时，应先提问；工具故障无法继续时如实停止。只有满足预先定义的升级交付要求时，才可把升级材料作为本次辅助任务的完成结果。

结构检查不能证明自然语言诊断和建议完全正确，仍需真实模型测试与人工复核。

**保留 Agent 的条件：**在盲测及后续真实案例中，相比固定流程确有可解释的质量或人工总耗时收益，成本与时延可接受，且没有未解决的严重边界缺陷。若固定流程更好，就用固定流程，不为了名叫 Agent 而坚持复杂方案。

## 9. 怎样沿着已有五阶段推进

**方向可以现在选，能力仍按阶段实现。**不需要先做完五阶段再考虑用途，也不用推翻已有核心规格。

| 已有阶段 | 在支持场景中怎样检验 | 不应为了场景提前加入什么 |
|---|---|---|
| 一：薄循环 | 先通过已有核心协议和小工具测试；再以一个虚构支持案例验证状态读取、文档回读、澄清与本地草稿 | 不提前做向量库、客服渠道、自动修复 |
| 二：复杂任务 | 多条状态、长说明、版本冲突、补充信息；目标与工作区保持一致，草稿可检查和有限修正 | 不把每个简单问题都强制规划或压缩 |
| 三：能力复用 | 支持方法成为能力包；增加知识检索和只读状态 MCP 适配，验证原引擎不用产品分支 | 不把客户事实存成偏好，不自动安装工具 |
| 四：可选协作 | 仅在任务够复杂时，对照“知识核对”和“状态调查”的分工收益 | 不做“接待／情绪／质检／售后”一大组 Agent；简单首版可跳过 |
| 五：可靠执行 | 补充输入、暂停和重启后保留调查事实；草稿不重复写，已过期状态不能作为当前依据 | 不为了练副作用接生产写接口，继续用独立虚构回执实验 |

原销售分析与产品选型资料的定位也要明确：

- 销售 CSV 保留为确定性计算、消息回填与通用性回归夹具，不扩展成另一个 BI 产品。
- 原产品选型样例保留为知识／状态引用机制的回归，不要求围绕它另造商业产品。
- 支持场景是后续面向使用者的主线候选，不是把旧样例改标题就算完成新场景。

已有 03—12 的工具契约和验收不会被本稿自动替换。新增支持能力应有独立的任务范围、工具契约、检查器和场景测试；此时只需在各小步落实当前所需部分，不同时重做五阶段。

这意味着：先用现成夹具把基础机制跑对，再尽早让同一引擎处理支持案例；后续复杂能力优先在该案例族上验证。不是先做三套完整应用，最后才开始真正的产品。

通用性的底线仍是：**产品名、故障码、处理政策进入工具和能力配置，不能进入 Runner 的领域判断。**

## 10. 从学习样例走到实际使用，哪些证据不能缺

### 第一关：本地机制成立

虚构案例能够产生不同调查路径；有真实工具执行、引用和本地产物；缺信息、取消、查询失败和越权请求有正确行为。通过这一关只能证明工程机制。

### 第二关：资料与任务确实存在

找一个获准研究的真实产品，由支持人员提供一小批去敏案例、当时适用的说明与可核实记录。起步可以选 10—20 个不同案例做可行性核验，但要记录来源和选取方式，不能只挑容易题。

若始终拿不到资料、状态或可靠复核人，就不能声称已经进入真实业务验证。可继续学习，但应重新考虑产品场景，而不是不断增加模拟工具。

### 第三关：影子运行有净收益

支持人员照常处理，Agent 只给建议，不自动发送。比较建议正确性、人工审核与纠错总耗时、覆盖范围和失败原因；区分产品问题解决时间与草稿准备时间。

只有当它能稳定减少一部分调查或撰写工作，而不是把人变成模型错误审核员，才值得做更深接入。此处不预先承诺节省百分比。

### 第四关：按价值扩展，而不是按架构图扩展

有证据后再逐项考虑：接已有工单系统的只读入口、增加同产品的问题类别、接另一个产品，最后才评估保存草稿到外部系统、对客发送或有限业务操作。

每个外部写动作都单独定义权限、确认、幂等和未知结果核实；上一项通过不意味着下一项自动获准。也没有必须发展成全自动客服或语音客服的义务。

潜在的交付对象是需要重复进行产品问题调查、又能提供可维护资料和接口的支持团队。是否愿意采用、谁维护文档、接入和评测成本能否承受，必须实际验证；“企业都需要客服”不是购买理由。

## 11. 哪些条件出现时应改选或缩减

| 发现的实际情况 | 建议调整 |
|---|---|
| 大部分问题只是稳定文档中的直接问答 | 以知识检索问答为主，Agent只处理少数调查任务，甚至不默认启用 |
| 所有问题都有清晰、固定的检查顺序 | 用工作流组织检查，模型负责必要的理解和表达 |
| 拿不到产品资料、状态记录或合格复核人员 | 不承诺真实技术支持能力；若有可靠表数据，改为固定口径经营分析 |
| 问题只有获得生产管理员权限后才能排查 | 把首版缩至材料收集与人工交接，不先开放任意执行 |
| Agent 的主要成本是人反复纠错 | 缩小支持范围、改进资料和确定性检查，仍无改善则不继续产品化 |
| 有明确用户和资源只需要知识查询，不需要调查 | 用户需求优先，可以做知识产品，不为学习路线强加动态行动 |
| 已经获得完整且获准的客服渠道、政策与人工兜底 | 可重新评估文字客服，但仍应先做受限范围试点；不自动推出语音客服 |

本建议并不声称“技术支持永远比数据分析好”。它是在当前目标明确、真实业务资源未锁定时，兼顾学习与落地的一种起点；资源和证据变化时允许改选。

## 12. 最终建议与下一步

建议将项目的场景定位写成：

> **以通用 Agent 引擎为底座，先做服务人工支持人员的单产品技术支持助手；从资料导入与索引异常入手，完成证据驱动的调查、澄清和回复草稿交付，逐步用真实授权案例验证价值。**

先不做面向所有企业的万能助手，不做全渠道自动客服，也不把整个项目定位成只有检索问答的知识库。

该方向的核心流程与工具调用已在配套 15／16 中展开：从单案例、单目标任务和静态快照开始，定义调查分支、7 个工具、证据条件、回复草稿与升级材料。实现时先准备虚构案例并验证工具，不建设外围管理平台；真实产品与业务价值仍须经过前述验证。

**核心取舍：用“有证据的支持问题调查”学习 Agent 的行动能力，用人工审核限制首版责任，用真实任务对照决定是否值得继续，而不是用功能数量证明系统先进。**
